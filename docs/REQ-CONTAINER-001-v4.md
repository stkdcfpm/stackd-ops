# REQ-CONTAINER-001 — Container profile table: shared capacity/weight model for the Load Calculator and Quote feasibility check, including Reefer

**Status:** v4 — revises v3 after independent requirements-gate review round 3 (third confirmatory): **CONDITIONAL PASS**, 1 new blocking + 2 new advisory, all personally re-verified against live code before being accepted (§9c). All 6 of round 2's fixes (dropping the `40GP` default, correcting the `{profile,reason}` contract, closing the NaN validation hole, and the three advisory fixes) were independently re-confirmed accurate — including fresh reads of `qf-mode`'s option set, `vBlurCurrencyPos()`'s exact two-part shape, and a full-document grep confirming no stray "5 rows"/"40GP"/"max payload" references survived outside historical narration. The new blocking finding is in round 2's own fix: correcting `reason:'exceeds'` to always carry a real `profile` (closing round 2's finding #2) broke an implicit equivalence the live `calcFeasibility()` code relies on — its existing four-branch chain discriminates "exceeds" from "fits" by testing `!recContainer`, which only worked because the *old* inline ternary's only falsy case was exactly the exceeds case. Under the corrected contract, `profile` is truthy for both `'ok'` and `'exceeds'`, so a naive "replace `recContainer` with `profile`" migration — which is exactly what this REQ's own wording invited — would make the exceeds-warning branch permanently dead code and misreport a genuinely oversized load as "fits" whenever the freight-mode text happens to contain the oversized profile's own code. **Fixed:** an explicit instruction added that the replacement logic must branch on `reason` first, never on `profile`'s truthiness, with a dedicated test for the specific failure mode (AC-8 extended). Advisory, both fixed: the `maxCBM`-tie-break rule was specified only for the "fits" side, not the symmetric "largest tried" side of the `'exceeds'` case; and the `CON-GAP-005` analogy in §4 described the wrong direction of restore-path inconsistency (that gap is under-write-on-missing-key, this REQ's own gap is over-write-on-present-but-empty-array) — corrected to name both directions accurately.
**Type:** New reference entity + de-duplication of existing hardcoded logic. No change to `DB.inv`/`DB.qt`/`DB.sh` record shapes. No Supabase migration (local-only entity, same category as `DB.events`).

Operator's own priority ordering for data-model robustness work, set explicitly: "1, shipment<>invoice. 2, container profile table. 3, warehousing/storage cost concept." With REQ-SHIP-002 (clean PASS, implementation pending) and REQ-LI-002/SPEC-LI-002 (both clean PASS, implementation paused in preview) addressing item 1, this REQ addresses item 2. ## 1. Business context

### 1.1 What exists today (check-first)

- **Gap 1 — no container-profile data structure exists anywhere.** The only "model" of container capacity is two bare numbers — `25` and `65` (CBM) — hardcoded inline and duplicated verbatim in two unrelated places: `runLoadCalc()` (`index.html:13455-13456`: `totalCBM <= 25 ? '20GP' : totalCBM <= 65 ? '40HQ' : 'Multiple 40HQ'`) and the Quote feasibility check (`index.html:14157`: `totalCBM <= 25 ? '20GP' : totalCBM <= 65 ? '40HQ' : null`). No array, object, or constant of container types/capacities exists to extend — confirmed by direct read of both sites and a full-file search for "reefer"/"container" turning up nothing else.
- **Gap 2 — no Reefer container type exists anywhere.** Confirmed by search: the only container-type strings in the app are the free-text options on the Shipment form's `containerType` dropdown (`index.html:2582`: `20GP`/`40HQ`/`LCL`/`Other`) and the Quote's `freightMode` dropdown (`index.html:2760-2764`, `<select id="qf-mode" onchange="calcQte()">`, options `LCL`/`FCL 20GP`/`FCL 40HQ` — round-1 requirements-gate finding: v1 mis-cited this as `722-723`, which is actually two unrelated numeric rate-config inputs, `qr-fcl20GP`/`qr-fcl40HQ`, in Settings, not a dropdown and not the element `calcFeasibility()` reads) — neither has a Reefer option, and neither carries any capacity data (they're plain labels/pricing-mode selectors, not profiles).
- **Gap 3 — no weight-limit checking exists anywhere, despite a weight field already existing on Invoice.** `inv.wt` (`index.html:1186`, label "Est. Gross Weight", free-text like `inv.cbm`, e.g. "2200 KGS") is captured, saved, and displayed on invoices and documents, but nothing in the Load Calculator or the Quote feasibility check ever reads it. Both checks are CBM-only.
- **Gap 4 — the CBM-threshold logic is duplicated, not shared, so fixing one site's thresholds (e.g. correcting them, or adding a type) doesn't fix the other.** `runLoadCalc()` and the Quote feasibility check (`calcFeasibility()`, called from `index.html:14141`, body at `index.html:14144-14166`) each independently re-derive the same `<=25`/`<=65` recommendation from their own local `totalCBM`, with their own separately-written ternary chains. There is no shared function either calls.
- **`inv.cbm`/`inv.wt` parsing precedent, to reuse exactly.** Both are free-text fields (not typed numbers) parsed the same way in `runLoadCalc()` (`index.html:13444`): `parseFloat((inv.cbm||'').replace(/[^\d.]/g,'')) || 0`. This REQ's new weight check reuses the identical pattern against `inv.wt`, not a new parsing approach.
- **Precedent for "local-only, not Cloud-Data-synced" (the first half of what this REQ needs): `DB.events[]`.** Confirmed by direct read it is system-generated only — `logEv()` pushes (`index.html:4347-4351`), a 2000-entry FIFO trim, and no add/edit/delete UI exists anywhere for individual events. (**Round-1 requirements-gate finding, corrected:** v1 mischaracterized `DB.events` as "user-editable" in the same breath as calling it "an append-and-reference log" — those are contradictory; `DB.events` only supports the local-only half of this REQ's needs, not the multi-field-CRUD half. No single existing entity combines both properties `DB.containerProfiles` needs.) **Precedent for the wiring discipline itself (the second half): `DB.liPending[]`, as specified — not yet as built.** `SPEC-LI-002-v3.md` (§2, §11) specifies the identical 8-item `CLAUDE.md` checklist (`K`, `DB`, `EI`, `saveAll`, `showV fns`, `renderAll`, `expAll snap`, `doImport entities`) for `DB.liPending[]`, and that SPEC reached a clean PASS — but implementation is only partially landed as of this writing: confirmed by direct read that `K.lip`/`DB.liPending`/`saveAll()`'s `sv(K.lip,...)` call exist in `index.html` today, but `expAll()` (`index.html:13073-13104`), `doImport()` (`index.html:13108-13162`), and `tests/run.js`'s `resetDB()` (`:211-213`) have no `liPending` reference yet. This REQ's new `DB.containerProfiles[]` follows the *specified* wiring discipline (the SPEC's design), not the *currently-built* state of `DB.liPending` — and not the simpler flat-string-array pattern used by `customUOM`/`customPorts`/`customPaymentTerms` (`index.html:4716-4780`), because a profile needs multiple fields (type code, label, max CBM, max weight, isReefer) per entry, not a single string.
- **Settings tab already has a pattern for a small, user-managed list with add/edit/delete** — the custom Payment Terms / UOM / Ports lists (`index.html:4716-4780`, rendered in Settings) are the closest existing UI precedent, though those are flat string lists; this REQ's new UI needs its own small CRUD block (§2, LI-CONTAINER-002... see requirements) since each row carries more than one field.

### 1.2 Design decisions (resolved with the operator before drafting further)

**Decision 1 (operator-selected) — Container profiles are a new, user-editable top-level entity, not hardcoded constants.** `DB.containerProfiles[]`, seeded with built-in industry-standard defaults on first use, editable (add/edit/delete) via a new Settings sub-section — so FPM can add non-standard types or correct a limit without a code change.

**Decision 2 (operator-selected) — Weight is checked against each profile's `maxWeightKg`, using the existing `inv.wt` field, with the same severity pattern as the existing CBM/DG warnings.** Not a disclosed non-goal — built now, not deferred.

**Decision 3 (operator-selected) — Both existing call sites (the Load Calculator and the Quote feasibility check) are unified to read from the new profile table, closing Gap 4, rather than leaving the Quote feasibility check's own hardcoded thresholds as a second, now-inconsistent copy.**

### 1.3 What this REQ deliberately does NOT do

- Does not change `DB.inv`, `DB.qt`, or `DB.sh`'s own record shapes — `inv.wt`/`inv.cbm` are read as-is; Shipment's `containerType` free-text field is not replaced with a profile reference (that would be a larger, riskier change touching an existing field many other places already read — out of scope here; see Decision boundary below).
- Does not do real 3D bin-packing or multi-item load optimization — the recommendation logic stays a simple "does total CBM/weight fit within one profile's limits" threshold check, the same level of sophistication as today, just correctly modeled and de-duplicated instead of guessed.
- Does not warn about DG-cargo/Reefer compatibility (e.g. certain DG classes disallowed in reefer units) — Reefer is added here only as another profile with its own CBM/weight limits; the existing DG warning (unchanged) fires independently of container type.
- Does not change `Shipment.containerType`'s own free-text dropdown to reference a `DB.containerProfiles` id — Shipment keeps its existing plain string field; linking the two is a disclosed non-goal (§4), revisit if it proves to matter in practice.
- Does not backfill or re-run historical Load Calculator results — the calculator has never persisted its own output beyond the current in-memory `_lcResult` (`index.html:13456`), so there is nothing to backfill.
- Does not touch warehousing/storage costs or ExWorks incoterm tracking — that is REQ-CONTAINER-001's sibling, the next priority item, scoped separately.

## 2. Requirements

### CONTAINER-001a — New entity: `DB.containerProfiles[]`, fully wired, seeded with built-in defaults
```js
{ id: uid(), code: string, label: string, maxCBM: number, maxWeightKg: number, isReefer: boolean, builtIn: boolean }
```
Full wiring, per `CLAUDE.md`'s own new-top-level-entity checklist, mirroring `DB.liPending`'s own precedent exactly:
- `K.cp: 'st_cp'` added to `K`.
- `DB.containerProfiles: ldArr(K.cp)` added to `DB`'s init object; on first load, seed 4 built-in rows using the exact one-time-seed pattern of `st_fpm_repair_v1` (`index.html:15671,15698`: `if (localStorage.getItem('st_fpm_repair_v1')) return; ... localStorage.setItem('st_fpm_repair_v1', '1');`) — **round-1 requirements-gate finding, corrected:** v1 mis-cited `st_li_cloud_migration_ts`-style markers as the precedent; that family is a Cloud-sync completion gate read at a dozen sites to decide whether a Supabase refresh may overwrite local data, a different mechanism from the plain "run once, then set a flag" pattern this REQ actually needs. The new marker key is named explicitly: `st_cp_seeded_v1`. Seed check and logic: `if (!localStorage.getItem('st_cp_seeded_v1')) { DB.containerProfiles = [...the 4 rows below...]; localStorage.setItem('st_cp_seeded_v1', '1'); }` — unconditional on the array's own contents, so a device that already has 0 profiles (e.g. after the operator deleted every custom one) is never re-seeded once the marker is set; only a device that has never run this version is seeded. The 4 built-in rows (`builtIn: true`, not deletable, but editable — see CONTAINER-001b's validation floor below): `20GP` (max 25 CBM / 21,600 kg), `40HQ` (max 65 CBM / 26,000 kg), `20RF` (Reefer, max 22 CBM / 20,000 kg, `isReefer: true`), `40RF` (Reefer, max 55 CBM / 24,000 kg, `isReefer: true`). (Weight/CBM figures are standard industry nominal maximums — operator may edit any of them.) **Round-2 requirements-gate finding, corrected: no built-in `40GP` tier.** v2 had seeded a `40GP` row (max 58 CBM, between `20GP`'s 25 and `40HQ`'s 65) as a plausible real-world fourth type — but the Quote's own `freightMode` dropdown (`index.html:2760-2764`) only ever offers `LCL`/`FCL 20GP`/`FCL 40HQ`, no `40GP` option of any kind, and this REQ deliberately does not add one (that would need a new pricing-rate field alongside `qr-fcl20GP`/`qr-fcl40HQ` too, out of scope). With `40GP` seeded, any Quote with `25 < totalCBM <= 58` would get `recommendContainer()` returning the `40GP` profile, which `mode.indexOf(profile.code)` (CONTAINER-001c) can never match against any selectable `qf-mode` value — permanently triggering the mismatch-warning branch and making the `'ok, fits'` branch unreachable for that entire CBM range, contradicting AC-8's own "notice levels match pre/post for unedited defaults" claim. The built-in default set is restricted to exactly the two non-Reefer tiers the app's existing freight-mode selector already models (`20GP`, `40HQ`) plus the two Reefer tiers (used only by the Load Calculator's own toggle, never by the Quote call site) — an operator who wants a genuine `40GP` profile can still add one via Settings (CONTAINER-001b), it is simply not seeded by default, avoiding this mismatch out of the box.
- `sv(K.cp, DB.containerProfiles)` added inside `saveAll()`.
- `containerProfiles: DB.containerProfiles` added to `expAll()`'s export snapshot; a corresponding `doImport()` restore line added in the same style as every entity added after the original 7 (mirroring REQ-LI-002's own round-6/round-7 corrected precedent for this exact step — citing the real lines, not guessed ones, at SPEC time).
- `containerProfiles: []` added to `tests/run.js`'s `resetDB()`.
- No `EI.cp` entry — profiles are managed in a flat list UI (add/edit/delete inline), the same shape as the custom Payment Terms/UOM/Ports lists, not a modal-based single-record editor.
- Confirmed absent from `syncEnt()`/`pullAll()`/`pushAll()` — not Cloud-Data-synced, same category as `DB.events`.
- `showV fns`/`renderAll` — confirmed, not hedged (round-1 requirements-gate finding: v1 deferred this to SPEC time; checked now instead). The new management UI lives inside the existing Settings view/`rCfg()`. `fns.cfg: rCfg` is already present in `showV()`'s `fns` map (`index.html:5313`), and `renderAll()` (`index.html:5316`) correctly does **not** call `rCfg()` — Settings is rendered on-demand via tab navigation, like every other Settings sub-feature, not continuously. No new entry needed in either list.

### CONTAINER-001b — Settings UI: add/edit/delete container profiles, with a validation floor
A new sub-section in Settings (alongside the existing custom Payment Terms/UOM/Ports lists), listing all `DB.containerProfiles` rows (code, label, max CBM, max weight, Reefer flag) with inline edit and a delete button — disabled/hidden for `builtIn: true` rows' delete action specifically (built-in rows can be edited but not removed). An "Add profile" row/button creates a new `builtIn: false` entry.

**Validation (round-1 requirements-gate finding, closed — not deletability alone; round-2 finding, NaN hole closed):** non-deletability of built-in rows was stated as the reason "the Load Calculator always has at least one profile to recommend," but nothing stopped an operator from editing every row's `maxCBM`/`maxWeightKg` down to 0 or a negative number, defeating that guarantee while leaving 4 rows technically present. `maxCBM`/`maxWeightKg` are validated on every save (add or edit) using this codebase's own existing two-part positive-currency pattern, `vBlurCurrencyPos()` (`index.html:10498-10503`: `if (!val || +val <= 0) vErr(...); else if (!RX.currency(val)) vErr(...); else vOk(...);`) — **round-1's own fix text only specified the first half** (`maxCBM > 0`), which a literal reading leaves vulnerable to non-numeric input: `+'abc' <= 0` is `false` in JS (`NaN` comparisons are always false), so a value like `'abc'` would pass a bare `<= 0` check and be stored as `NaN`, defeating AC-11's own purpose the same way a `0` would. Both the blank/non-positive check **and** the `RX.currency()` format check are required, exactly mirroring `vBlurCurrencyPos()`'s own two-branch shape, not just its first branch. `code`/`label` are required (non-blank). AC-11 corrected to test the NaN case explicitly.

### CONTAINER-001c — Shared recommendation function, replacing both hardcoded sites
A new function, `recommendContainer(totalCBM, totalWeightKg, wantReefer)` — **round-1 requirements-gate findings, both closed by this revised contract:**

- **Return shape (closes the `null`-overload finding; `'exceeds'`'s own `profile` field corrected — round-2 finding):** returns `{ profile: <a DB.containerProfiles row> | null, reason: 'ok' | 'exceeds' | 'no_profiles' }`, never a bare profile-or-null. `reason:'no_profiles'` fires when `DB.containerProfiles.filter(...)` (after the Reefer/non-Reefer split below) is empty, and only then — this is the one case where `profile` is genuinely `null`. **`reason:'exceeds'` always carries a real `profile`, never `null`: the largest-capacity profile in the filtered set (by `maxCBM` descending), i.e. the one that came closest to fitting and was still exceeded.** (Round-2 correction: v2 paired `'exceeds'` with `profile: null`, which left AC-8's own requirement — build the exceeded-capacity message from "the real returned profile's own `maxCBM`/`label`" — with no profile to read from in exactly the branch that needed one. Returning the largest-in-set profile closes that gap: the exceeded message can now correctly say "exceeds the largest configured non-Reefer profile (40HQ, 65 CBM max)" using real data, not a guess.) This distinguishes "nothing configured, go to Settings and add one" (`'no_profiles'`, `profile: null`) from "every configured profile of this kind is too small for this load, consider split shipment" (`'exceeds'`, `profile` = the largest one tried).
- **Selection logic:** filters `DB.containerProfiles` to `isReefer === !!wantReefer` first (so `wantReefer:false`, the default, excludes Reefer profiles from ordinary recommendations — DG/ambient cargo should not be silently recommended into a refrigerated unit; `wantReefer:true` is the only path to a Reefer recommendation, used solely by the Load Calculator's explicit "This load needs refrigeration" toggle, §2 CONTAINER-001d). If the filtered set is empty, return `{ profile: null, reason: 'no_profiles' }` immediately — checked *before* anything else, so an empty set never falls through to `'exceeds'`. Otherwise, among the filtered set, find the smallest-capacity profile (by `maxCBM` ascending) whose `maxCBM >= totalCBM` **and** `maxWeightKg >= totalWeightKg`; if one exists, return `{ profile: <that profile>, reason: 'ok' }`. **Tie-break (closes the unspecified-tie finding; made symmetric — round-3 finding):** if two or more profiles share the same `maxCBM`, the one appearing first in `DB.containerProfiles`'s own array order wins — deterministic, no secondary sort needed. This applies identically on both sides: among profiles that *fit*, for the `'ok'` case, and among profiles tied for *largest* `maxCBM` in the filtered set, for the `'exceeds'` case below (round-2's fix specified the tie-break for the former only; a custom profile added via Settings that happens to duplicate an existing one's `maxCBM` could otherwise tie for largest with no stated resolution). If none fit, return `{ profile: <the largest-maxCBM profile in the filtered set, ties broken the same way>, reason: 'exceeds' }`.
- **Terminology (closes the "max payload" inconsistency):** the field is `maxWeightKg` throughout — this REQ does not use "payload" anywhere else, to avoid implying a distinction (tare vs. gross) the app's own `inv.wt` ("Est. Gross Weight") input doesn't actually carry.

**Both existing call sites switch to this one function:**
- `runLoadCalc()` (`index.html:13435-13472`): replace the inline `totalCBM <= 25 ? ... : ...` ternary with a call to `recommendContainer(totalCBM, totalWeightKg, reeferToggleChecked)`, where `totalWeightKg` is summed from each selected invoice's `inv.wt`, parsed with the identical `parseFloat(...).replace(/[^\d.]/g,'')` pattern already used for `inv.cbm` at `index.html:13444`, and `reeferToggleChecked` reads the new refrigeration checkbox (§2 CONTAINER-001d). On `reason:'exceeds'`, show the existing "exceeds, consider split shipment" wording; on `reason:'no_profiles'`, show a distinct "No container profiles configured — add one in Settings" message instead of a misleading capacity claim.
- The Quote feasibility check (`index.html:14149-14166`): replace its own `totalCBM <= 25 ? ... : ...` ternary with `recommendContainer(totalCBM, 0, false)` — Quote lines have no weight field today, confirmed absent from `cQL`'s line shape as built in `saveQte()` (`index.html:14202-14222`: `rid, supId, desc, qty, uom, cost, cbm, dg, dutyPct, markup, insRate` — no weight key), the identical line shape REQ-LI-002 already cited for its own "no `sku` key" finding — so this call always passes `0` for weight (never the limiting factor there) and `false` for `wantReefer` (Quote has no refrigeration toggle); this is a disclosed non-goal (§4), not a regression, since Quote genuinely has no weight data to pass. **The existing hardcoded "exceeds single 40HQ capacity (~65 CBM)" message (`index.html:14161`) is replaced with wording built from the actual returned profile's own `maxCBM`/`label`**, not a re-hardcoded literal — otherwise it would silently go stale the moment an operator edits the 40HQ profile's limit via Settings, defeating this REQ's own Decision 1/3 (see AC-8, corrected below).

  **Branch order (round-3 requirements-gate finding, closed — load-bearing, not optional phrasing):** the live code's four-branch `if`/`else if` chain (`index.html:14157-14166`) currently discriminates "exceeds" from "fits" by testing the truthiness of its local `recContainer` variable (`!recContainer` means "exceeds," because the old inline ternary's only `null` case was exactly the exceeds case). **That equivalence no longer holds once this REQ's corrected return contract is used** (§2 CONTAINER-001c's return-shape paragraph: `reason:'exceeds'` now always carries a real, non-null `profile`, same as `reason:'ok'`). An implementation that mechanically substitutes `profile` for `recContainer` in the existing branch shape — testing `profile`/`!profile` instead of `reason` — would therefore make the exceeds-warning branch permanently dead code, and a genuinely-oversized load whose freight mode text happens to contain the oversized profile's own `code` (e.g. `totalCBM=80`, `mode='FCL 40HQ'`, filtered-set largest is `40HQ`) would silently fall through to the final `else` and be reported as **"CBM 80.00 fits 40HQ"** — the exact wrong-feasibility-check failure mode this whole REQ exists to prevent. The replacement logic must branch on `reason` first, not on `profile`'s truthiness: `reason === 'exceeds'` → the exceeds-warning branch (using `profile.maxCBM`/`profile.label` for the message); `reason === 'no_profiles'` → the no-profiles branch (below); `reason === 'ok'` → test `mode.indexOf(profile.code) === -1` for the mismatch-vs-fits distinction, exactly as the old code tested `mode.indexOf(recContainer)` — `profile`'s mere presence or absence must never be read as a stand-in for whether the load fits.

  **`reason:'no_profiles'` (round-2 advisory, addressed explicitly, not left silent):** `calcFeasibility()` only runs this notice logic when `totalCBM > 0` (`index.html:14156`), and `DB.containerProfiles` only reaches empty if every built-in row is deleted — not possible per CONTAINER-001b's own non-deletability rule, so this branch is unreachable in practice from the Quote side specifically. It is still given the same `'no_profiles'`-aware `info`-level notice as the Load Calculator, for defense-in-depth and so the two call sites stay genuinely unified rather than one silently assuming a state the other explicitly guards against.

A new checkbox, "This load needs refrigeration," sits alongside the existing invoice checklist and is read as `wantReefer` in the `recommendContainer()` call (§2 CONTAINER-001c).

## 3. Acceptance criteria

- **AC-1 (corrected — round-2 finding, 4 rows not 5):** On first load after this version ships, `DB.containerProfiles` is seeded with exactly the 4 built-in rows (§2, CONTAINER-001a: `20GP`, `40HQ`, `20RF`, `40RF` — no `40GP`) if and only if the `st_cp_seeded_v1` marker was never set on that device — checked purely via the marker, not via the array's own contents, so a device that already has custom profiles from a prior session is never re-seeded or overwritten, and a device that has run this version before (even if the operator since deleted every profile down to zero) is never silently re-seeded either.
- **AC-2:** Adding a new profile via Settings persists it to `DB.containerProfiles` and makes it immediately selectable/recommendable by `recommendContainer()`.
- **AC-3:** Editing a built-in profile's `maxCBM`/`maxWeightKg` changes what `recommendContainer()` returns for loads near that boundary; the built-in row's Delete action is disabled/hidden.
- **AC-4:** Deleting a non-built-in profile removes it from `DB.containerProfiles` and from future recommendations.
- **AC-5 (corrected — round-1 finding, return shape; `'exceeds'`'s own `profile` corrected — round-2 finding):** `recommendContainer(totalCBM, totalWeightKg, false)` returns `{profile: <smallest fitting non-Reefer profile>, reason:'ok'}` when both CBM and weight fit; returns `{profile: <next-larger profile>, reason:'ok'}` when the smallest would fit on CBM alone but not weight; returns `{profile: <the largest non-Reefer profile configured>, reason:'exceeds'}` when no non-Reefer profile fits either dimension — `profile` is a real row here, never `null`; returns `{profile: null, reason:'no_profiles'}` when every container profile has been deleted (the only case `profile` is actually `null`, confirmed by a test that deletes all profiles and checks both `profile === null` and `reason === 'no_profiles'`, not just that `profile` is falsy). `recommendContainer(totalCBM, totalWeightKg, true)` performs the identical logic restricted to `isReefer:true` profiles only.
- **AC-6 (corrected — round-1 finding, "and/or" made deterministic):** `runLoadCalc()` with invoices whose total weight exceeds the CBM-recommended profile's `maxWeightKg` (but whose CBM would fit a smaller profile) recommends the next larger profile that fits both dimensions **and** shows a weight-specific note alongside it — both, not either, so the operator sees which dimension drove the upsize — never silently recommending the CBM-only answer.
- **AC-7:** `runLoadCalc()`'s Reefer toggle, when enabled, recommends only from `isReefer: true` profiles.

Opposite failure direction, same accepted principle: a destructive, operator-confirmed restore is not the place to silently second-guess what the backup file actually contains, in either direction.
