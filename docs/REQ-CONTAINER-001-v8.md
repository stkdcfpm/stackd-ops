**Status:** v8 — revises v7 after independent requirements-gate review round 7 (seventh confirmatory): **CONDITIONAL PASS**, 0 new blocking + 2 new advisory, both personally re-verified against live code before being accepted (§9g). Round 6's citation fixes, the AC-13 addition, the restore-path bypass disclosure, and the AC-6 dimension-aware extension were all independently re-confirmed correct and complete — including confirming `recommendContainer()`'s `{profile, reason}` contract genuinely gives a caller enough information (via `profile.maxCBM`/`profile.maxWeightKg` compared against its own locals) to build a dimension-aware message without needing a new sub-reason field, and confirming `doImport()` genuinely performs zero field-level validation for any entity, not a special gap introduced for this one. Round 7 is the third consecutive round with no blocking findings. The two new advisories, both fixed: (1) AC-13's scope for the `label`-blank case had narrowed itself to "new or custom profile" only, silently leaving open whether blanking a built-in row's `label` (freely editable, per CONTAINER-001b) should be rejected — widened to match AC-11's own "new, edit, built-in, or custom" scope, while correctly keeping the narrower "new or custom" scope for `code` specifically, since a built-in row's `code` can never actually be blank at save time given AC-12's read-only restriction. ## 1. Business context

### 1.1 What exists today (check-first)

- **Gap 1 — no container-profile data structure exists anywhere.** The only "model" of container capacity is two bare numbers — `25` and `65` (CBM) — hardcoded inline and duplicated verbatim in two unrelated places: `runLoadCalc()` (`index.html:13455-13456`: `totalCBM <= 25 ? '20GP' : totalCBM <= 65 ? '40HQ' : 'Multiple 40HQ'`) and the Quote feasibility check (`index.html:14157`: `totalCBM <= 25 ? '20GP' : totalCBM <= 65 ? '40HQ' : null`). No array, object, or constant of container types/capacities exists to extend — confirmed by direct read of both sites and a full-file search for "reefer"/"container" turning up nothing else.
- **Gap 2 — no Reefer container type exists anywhere.** Confirmed by search: the only container-type strings in the app are the free-text options on the Shipment form's `containerType` dropdown (`index.html:2582`: `20GP`/`40HQ`/`LCL`/`Other`) and the Quote's `freightMode` dropdown (`index.html:2760-2764`, `<select id="qf-mode" onchange="calcQte()">`, options `LCL`/`FCL 20GP`/`FCL 40HQ` — round-1 requirements-gate finding: v1 mis-cited this as `722-723`, which is actually two unrelated numeric rate-config inputs, `qr-fcl20GP`/`qr-fcl40HQ`, in Settings, not a dropdown and not the element `calcFeasibility()` reads) — neither has a Reefer option, and neither carries any capacity data (they're plain labels/pricing-mode selectors, not profiles).
- **Gap 3 — no weight-limit checking exists anywhere, despite a weight field already existing on Invoice.** `inv.wt` (`index.html:1186`, label "Est. Gross Weight", free-text like `inv.cbm`, e.g. "2200 KGS") is captured, saved, and displayed on invoices and documents, but nothing in the Load Calculator or the Quote feasibility check ever reads it. Both checks are CBM-only.
- **Gap 4 — the CBM-threshold logic is duplicated, not shared, so fixing one site's thresholds (e.g. correcting them, or adding a type) doesn't fix the other.** `runLoadCalc()` and the Quote feasibility check (`calcFeasibility()`, called from `index.html:14141`, body at `index.html:14144-14166`) each independently re-derive the same `<=25`/`<=65` recommendation from their own local `totalCBM`, with their own separately-written ternary chains. There is no shared function either calls.
- **`inv.cbm`/`inv.wt` parsing precedent, to reuse exactly.** Both are free-text fields (not typed numbers) parsed the same way in `runLoadCalc()` (`index.html:13444`): `parseFloat((inv.cbm||'').replace(/[^\d.]/g,'')) || 0`. This REQ's new weight check reuses the identical pattern against `inv.wt`, not a new parsing approach.
- **Precedent for "local-only, not Cloud-Data-synced" (the first half of what this REQ needs): `DB.events[]`.** Confirmed by direct read it is system-generated only — `logEv()` pushes (`index.html:4347-4351`), a 2000-entry FIFO trim, and no add/edit/delete UI exists anywhere for individual events. (**Round-1 requirements-gate finding, corrected:** v1 mischaracterized `DB.events` as "user-editable" in the same breath as calling it "an append-and-reference log" — those are contradictory; `DB.events` only supports the local-only half of this REQ's needs, not the multi-field-CRUD half. No single existing entity combines both properties `DB.containerProfiles` needs.) **Precedent for the wiring discipline itself (the second half): `DB.liPending[]`, as specified — not yet as built.** `SPEC-LI-002-v3.md` (§2, §11) specifies the identical 8-item `CLAUDE.md` checklist (`K`, `DB`, `EI`, `saveAll`, `showV fns`, `renderAll`, `expAll snap`, `doImport entities`) for `DB.liPending[]`, and that SPEC reached a clean PASS — but implementation is only partially landed as of this writing: confirmed by direct read that `K.lip`/`DB.liPending`/`saveAll()`'s `sv(K.lip,...)` call exist in `index.html` today, but `expAll()` (`index.html:13073-13104`), `doImport()` (`index.html:13108-13162`), and `tests/run.js`'s `resetDB()` (`:211-213`) have no `liPending` reference yet. This REQ's new `DB.containerProfiles[]` follows the *specified* wiring discipline (the SPEC's design), not the *currently-built* state of `DB.liPending` — and not the simpler flat-string-array pattern used by `customUOM`/`customPorts`/`customPaymentTerms` (`index.html:4716-4780`), because a profile needs multiple fields (type code, label, max CBM, max weight, isReefer) per entry, not a single string.
- **Settings tab already has a pattern for a small, user-managed list with add/edit/delete** — the custom Payment Terms / UOM / Ports lists (`index.html:4716-4780`, rendered in Settings) are the closest existing UI precedent, though those are flat string lists; this REQ's new UI needs its own small CRUD block (§2, LI-CONTAINER-002... see requirements) since each row carries more than one field.

### 1.2 Design decisions (resolved with the operator before drafting further)

**Decision 1 (operator-selected) — Container profiles are a new, user-editable top-level entity, not hardcoded constants.** `DB.containerProfiles[]`, seeded with built-in industry-standard defaults on first use, editable (add/edit/delete) via a new Settings sub-section — so FPM can add non-standard types or correct a limit without a code change.

**Decision 2 (operator-selected) — Weight is checked against each profile's `maxWeightKg`, using the existing `inv.wt` field, with the same severity pattern as the existing CBM/DG warnings.** Not a disclosed non-goal — built now, not deferred.

**Decision 3 (operator-selected) — Both existing call sites (the Load Calculator and the Quote feasibility check) are unified to read from the new profile table, closing Gap 4, rather than leaving the Quote feasibility check's own hardcoded thresholds as a second, now-inconsistent copy.**

### 1.3 What this REQ deliberately does NOT do

- Does not change `DB.inv`, `DB.qt`, or `DB.sh`'s own record shapes — `inv.wt`/`inv.cbm` are read as-is; Shipment's `containerType` free-text field is not replaced with a profile reference (that would be a larger, riskier change touching an existing field many other places already read — out of scope here; see Decision boundary below).
- Does not do real 3D bin-packing or multi-item load optimization — the recommendation logic stays a simple "does total CBM/weight fit within one profile's limits" threshold check, the same level of sophistication as today, just correctly modeled and de-duplicated instead of guessed.
- Does not warn about DG-cargo/Reefer compatibility (e.g. certain DG classes disallowed in reefer units) — Reefer is added here only as another profile with its own CBM/weight limits; the existing DG warning (unchanged) fires independently of container type.
- Does not change `Shipment.containerType`'s own free-text dropdown to reference a `DB.containerProfiles` id — Shipment keeps its existing plain string field; linking the two is a disclosed non-goal (§4), revisit if it proves to matter in practice.
- Does not backfill or re-run historical Load Calculator results — the calculator has never persisted its own output beyond the current in-memory `_lcResult` (`index.html:13457` — round-7 finding, corrected from an off-by-one citation of `:13456`, which is actually the `recNote` ternary one line above the real `_lcResult = {...}` literal), so there is nothing to backfill.
- Does not touch warehousing/storage costs or ExWorks incoterm tracking — that is REQ-CONTAINER-001's sibling, the next priority item, scoped separately.

### CONTAINER-001b — Settings UI: add/edit/delete container profiles, with a validation floor
A new sub-section in Settings (alongside the existing custom Payment Terms/UOM/Ports lists), listing all `DB.containerProfiles` rows (code, label, max CBM, max weight, Reefer flag) with inline edit and a delete button — disabled/hidden for `builtIn: true` rows' delete action specifically (built-in rows can be edited but not removed). An "Add profile" row/button creates a new `builtIn: false` entry.

**`code` is read-only on `builtIn: true` rows (round-5 requirements-gate finding, closed):** `label`/`maxCBM`/`maxWeightKg` remain freely editable on built-in rows (that is the entire point of Decision 1), but a built-in row's `code` field itself is not — its input is rendered disabled/read-only, the same visual treatment as the already-disabled delete button on those rows. Reason: CONTAINER-001c's Quote call site matches `mode.indexOf(profile.code)` against the fixed, un-editable `qf-mode` option strings (`'FCL 20GP'`, `'FCL 40HQ'`, `index.html:2760-2765`) — an operator renaming the built-in `20GP` row's `code` to something else, plausibly believing it as cosmetic as `label`, would silently and permanently break mode-matching for every future Quote using that profile, flipping "fits" to "mismatch warning" (or vice versa) with no error shown. Non-deletability alone doesn't protect against this, since the row survives intact with a different `code`. Custom (`builtIn: false`) rows keep a freely-editable `code`, since nothing in this REQ's own default behavior depends on matching a custom profile's code against `qf-mode`'s fixed strings — that linkage, if the operator wants one, is their own responsibility to get right, same as naming any other custom reference value in this app. New AC-12.

**Validation (round-1 requirements-gate finding, closed — not deletability alone; round-2 finding, NaN hole closed):** non-deletability of built-in rows was stated as the reason "the Load Calculator always has at least one profile to recommend," but nothing stopped an operator from editing every row's `maxCBM`/`maxWeightKg` down to 0 or a negative number, defeating that guarantee while leaving 4 rows technically present. `maxCBM`/`maxWeightKg` are validated on every save (add or edit) using this codebase's own existing two-part positive-currency pattern, `vBlurCurrencyPos()` (`index.html:10498-10503`: `if (!val || +val <= 0) vErr(...); else if (!RX.currency(val)) vErr(...); else vOk(...);`) — **round-1's own fix text only specified the first half** (`maxCBM > 0`), which a literal reading leaves vulnerable to non-numeric input: `+'abc' <= 0` is `false` in JS (`NaN` comparisons are always false), so a value like `'abc'` would pass a bare `<= 0` check and be stored as `NaN`, defeating AC-11's own purpose the same way a `0` would. Both the blank/non-positive check **and** the `RX.currency()` format check are required, exactly mirroring `vBlurCurrencyPos()`'s own two-branch shape, not just its first branch. `code`/`label` are required (non-blank). AC-11 corrected to test the NaN case explicitly.

### CONTAINER-001c — Shared recommendation function, replacing both hardcoded sites
A new function, `recommendContainer(totalCBM, totalWeightKg, wantReefer)` — **round-1 requirements-gate findings, both closed by this revised contract:**

- **Return shape (closes the `null`-overload finding; `'exceeds'`'s own `profile` field corrected — round-2 finding):** returns `{ profile: <a DB.containerProfiles row> | null, reason: 'ok' | 'exceeds' | 'no_profiles' }`, never a bare profile-or-null. `reason:'no_profiles'` fires when `DB.containerProfiles.filter(...)` (after the Reefer/non-Reefer split below) is empty, and only then — this is the one case where `profile` is genuinely `null`. **`reason:'exceeds'` always carries a real `profile`, never `null`: the largest-capacity profile in the filtered set (by `maxCBM` descending), i.e. the one that came closest to fitting and was still exceeded.** (Round-2 correction: v2 paired `'exceeds'` with `profile: null`, which left AC-8's own requirement — build the exceeded-capacity message from "the real returned profile's own `maxCBM`/`label`" — with no profile to read from in exactly the branch that needed one. Returning the largest-in-set profile closes that gap: the exceeded message can now correctly say "exceeds the largest configured non-Reefer profile (40HQ, 65 CBM max)" using real data, not a guess.) This distinguishes "nothing configured, go to Settings and add one" (`'no_profiles'`, `profile: null`) from "every configured profile of this kind is too small for this load, consider split shipment" (`'exceeds'`, `profile` = the largest one tried).
- **Selection logic:** filters `DB.containerProfiles` to `isReefer === !!wantReefer` first (so `wantReefer:false`, the default, excludes Reefer profiles from ordinary recommendations — DG/ambient cargo should not be silently recommended into a refrigerated unit; `wantReefer:true` is the only path to a Reefer recommendation, used solely by the Load Calculator's explicit "This load needs refrigeration" toggle, §2 CONTAINER-001d). If the filtered set is empty, return `{ profile: null, reason: 'no_profiles' }` immediately — checked *before* anything else, so an empty set never falls through to `'exceeds'`. Otherwise, among the filtered set, find the smallest-capacity profile (by `maxCBM` ascending) whose `maxCBM >= totalCBM` **and** `maxWeightKg >= totalWeightKg`; if one exists, return `{ profile: <that profile>, reason: 'ok' }`. **Tie-break (closes the unspecified-tie finding; made symmetric — round-3 finding):** if two or more profiles share the same `maxCBM`, the one appearing first in `DB.containerProfiles`'s own array order wins — deterministic, no secondary sort needed. This applies identically on both sides: among profiles that *fit*, for the `'ok'` case, and among profiles tied for *largest* `maxCBM` in the filtered set, for the `'exceeds'` case below (round-2's fix specified the tie-break for the former only; a custom profile added via Settings that happens to duplicate an existing one's `maxCBM` could otherwise tie for largest with no stated resolution). If none fit, return `{ profile: <the largest-maxCBM profile in the filtered set, ties broken the same way>, reason: 'exceeds' }`.
- **Terminology (closes the "max payload" inconsistency):** the field is `maxWeightKg` throughout — this REQ does not use "payload" anywhere else, to avoid implying a distinction (tare vs. gross) the app's own `inv.wt` ("Est. Gross Weight") input doesn't actually carry.

**Both existing call sites switch to this one function:**
- `runLoadCalc()` (`index.html:13435-13472`): replace the inline `totalCBM <= 25 ? ... : ...` ternary with a call to `recommendContainer(totalCBM, totalWeightKg, reeferToggleChecked)`, where `totalWeightKg` is summed from each selected invoice's `inv.wt`, parsed with the identical `parseFloat(...).replace(/[^\d.]/g,'')` pattern already used for `inv.cbm` at `index.html:13444`, and `reeferToggleChecked` reads the new refrigeration checkbox (§2 CONTAINER-001d). On `reason:'exceeds'`, show the existing "exceeds, consider split shipment" wording — **dimension-aware, not always CBM-phrased (round-6 finding):** the existing wording ("exceeds single 40HQ capacity (~65 CBM)") names CBM specifically, but at the Load Calculator (unlike the Quote call site, which always passes weight `0` and can never hit this) a load can reach `reason:'exceeds'` with comfortable CBM headroom purely because `totalWeightKg` exceeds every configured profile's `maxWeightKg` — the same "which dimension drove it" principle AC-6 already requires for the `reason:'ok'`-but-upsized case applies here too: the message must name whichever dimension(s) actually failed (CBM, weight, or both), not default to a CBM-phrased string regardless of cause. On `reason:'no_profiles'`, show a distinct "No container profiles configured — add one in Settings" message instead of a misleading capacity claim.
- The Quote feasibility check (`index.html:14149-14166`): replace its own `totalCBM <= 25 ? ... : ...` ternary with `recommendContainer(totalCBM, 0, false)` — Quote lines have no weight field today, confirmed absent from `cQL`'s line shape as built in `saveQte()` (`index.html:14202-14222`: `rid, supId, desc, qty, uom, cost, cbm, dg, dutyPct, markup, insRate` — no weight key), the identical line shape REQ-LI-002 already cited for its own "no `sku` key" finding — so this call always passes `0` for weight (never the limiting factor there) and `false` for `wantReefer` (Quote has no refrigeration toggle); this is a disclosed non-goal (§4), not a regression, since Quote genuinely has no weight data to pass. **The existing hardcoded "exceeds single 40HQ capacity (~65 CBM)" message (`index.html:14161`) is replaced with wording built from the actual returned profile's own `maxCBM`/`label`**, not a re-hardcoded literal — otherwise it would silently go stale the moment an operator edits the 40HQ profile's limit via Settings, defeating this REQ's own Decision 1/3 (see AC-8, corrected below).

  **Branch order (round-3 requirements-gate finding, closed — load-bearing, not optional phrasing; round-4 finding, LCL priority restored):** the live code's four-branch `if`/`else if` chain (`index.html:14157-14166`) currently discriminates "exceeds" from "fits" by testing the truthiness of its local `recContainer` variable (`!recContainer` means "exceeds," because the old inline ternary's only `null` case was exactly the exceeds case). **That equivalence no longer holds once this REQ's corrected return contract is used** (§2 CONTAINER-001c's return-shape paragraph: `reason:'exceeds'` now always carries a real, non-null `profile`, same as `reason:'ok'`). An implementation that mechanically substitutes `profile` for `recContainer` in the existing branch shape — testing `profile`/`!profile` instead of `reason` — would therefore make the exceeds-warning branch permanently dead code, and a genuinely-oversized load whose freight mode text happens to contain the oversized profile's own `code` (e.g. `totalCBM=80`, `mode='FCL 40HQ'`, filtered-set largest is `40HQ`) would silently fall through to the final `else` and be reported as **"CBM 80.00 fits 40HQ"** — the exact wrong-feasibility-check failure mode this whole REQ exists to prevent.

  **The correct replacement logic has two levels, not one — `mode === 'LCL'` must be checked first, before `reason` is consulted at all.** The live code's own guard clauses (`index.html:14158`: `... && mode !== 'LCL' && ...` — round-6 finding, corrected from a wrong citation of `:14157`, which is actually the `recContainer` ternary assignment the line above; `:14160`: `!recContainer && mode !== 'LCL'`) already make `mode === 'LCL'` take priority over *both* the mismatch warning and the exceeds warning, at every CBM level — an LCL quote with `totalCBM` large enough to "exceed" every profile still gets the plain "LCL mode · N.NN CBM total" info notice today, never an exceeds warning, because LCL cargo is consolidated and has no single-container limit to exceed. `recommendContainer()` itself takes no `mode` parameter and cannot know this — so the Quote call site's own wrapper logic must check `mode === 'LCL'` first and short-circuit straight to the LCL-info notice in that case, for every `reason` value, before branching on `reason` at all. Only once `mode !== 'LCL'` is confirmed does the `reason`-first branching apply: `reason === 'exceeds'` → the exceeds-warning branch (using `profile.maxCBM`/`profile.label` for the message); `reason === 'no_profiles'` → the no-profiles branch (below); `reason === 'ok'` → test `mode.indexOf(profile.code) === -1` for the mismatch-vs-fits distinction, exactly as the old code tested `mode.indexOf(recContainer)`. `profile`'s mere presence or absence must never be read as a stand-in for whether the load fits, and `mode === 'LCL'` must never be folded into the `reason`-based branching as if it were just another case of `'ok'` — it is a priority check that pre-empts `reason` entirely, exactly as it already pre-empts `recContainer` in the live code today.

  **`reason:'no_profiles'` (round-2 advisory, addressed explicitly, not left silent):** `calcFeasibility()` only runs this notice logic when `totalCBM > 0` (`index.html:14156`), and `DB.containerProfiles` only reaches empty if every built-in row is deleted — not possible per CONTAINER-001b's own non-deletability rule, so this branch is unreachable in practice from the Quote side specifically. It is still given the same `'no_profiles'`-aware `info`-level notice as the Load Calculator, for defense-in-depth and so the two call sites stay genuinely unified rather than one silently assuming a state the other explicitly guards against.

### CONTAINER-001d — Load Calculator surfaces weight alongside CBM, and gains a refrigeration toggle
`runLoadCalc()`'s result table gains a Weight column (per invoice, parsed from `inv.wt`) and a Total Weight row, displayed the same way the existing Total CBM row is. A new checkbox, "This load needs refrigeration," sits alongside the existing invoice checklist and is read as `wantReefer` in the `recommendContainer()` call (§2 CONTAINER-001c).

**`_lcResult`'s own shape must be extended (round-1 requirements-gate finding, closed — this was previously only implied).** `exportLoadSummary()` (`index.html:13474-13497`) reads *exclusively* from the module-level `_lcResult` object (confirmed by direct read — no separate data-gathering logic of its own), whose current literal (`index.html:13456-13457`: `{ invNums, lines, totalCBM, hasDG, rec, recNote }`) has no weight fields at all. `_lcResult` is extended with `totalWeightKg` and a per-line `wt` (alongside each line's existing `cbm`), and `exportLoadSummary()` includes both in its text export, in the same style as the existing CBM/container-rec lines.

## 3. Acceptance criteria

- **AC-1 (corrected — round-2 finding, 4 rows not 5):** On first load after this version ships, `DB.containerProfiles` is seeded with exactly the 4 built-in rows (§2, CONTAINER-001a: `20GP`, `40HQ`, `20RF`, `40RF` — no `40GP`) if and only if the `st_cp_seeded_v1` marker was never set on that device — checked purely via the marker, not via the array's own contents, so a device that already has custom profiles from a prior session is never re-seeded or overwritten, and a device that has run this version before (even if the operator since deleted every profile down to zero) is never silently re-seeded either.
- **AC-2:** Adding a new profile via Settings persists it to `DB.containerProfiles` and makes it immediately selectable/recommendable by `recommendContainer()`.
- **AC-3:** Editing a built-in profile's `maxCBM`/`maxWeightKg` changes what `recommendContainer()` returns for loads near that boundary; the built-in row's Delete action is disabled/hidden.
- **AC-4:** Deleting a non-built-in profile removes it from `DB.containerProfiles` and from future recommendations.
- **AC-5 (corrected — round-1 finding, return shape; `'exceeds'`'s own `profile` corrected — round-2 finding; wording tightened — round-4 advisory):** `recommendContainer(totalCBM, totalWeightKg, false)` returns `{profile: <smallest fitting non-Reefer profile>, reason:'ok'}` when a profile exists whose `maxCBM >= totalCBM` **and** `maxWeightKg >= totalWeightKg` simultaneously; returns `{profile: <next-larger profile>, reason:'ok'}` when the smallest would satisfy that pair on CBM alone but not weight; returns `{profile: <the largest non-Reefer profile configured>, reason:'exceeds'}` when no single profile satisfies both conditions at once — `profile` is a real row here, never `null`; returns `{profile: null, reason:'no_profiles'}` when every container profile has been deleted (the only case `profile` is actually `null`, confirmed by a test that deletes all profiles and checks both `profile === null` and `reason === 'no_profiles'`, not just that `profile` is falsy). `recommendContainer(totalCBM, totalWeightKg, true)` performs the identical logic restricted to `isReefer:true` profiles only.
- **AC-6 (corrected — round-1 finding, "and/or" made deterministic; extended — round-6 finding):** `runLoadCalc()` with invoices whose total weight exceeds the CBM-recommended profile's `maxWeightKg` (but whose CBM would fit a smaller profile) recommends the next larger profile that fits both dimensions **and** shows a weight-specific note alongside it — both, not either, so the operator sees which dimension drove the upsize — never silently recommending the CBM-only answer. The same dimension-awareness applies on the `reason:'exceeds'` side: invoices whose CBM comfortably fits every configured profile but whose total weight exceeds every profile's `maxWeightKg` produce an exceeds message naming weight as the cause, not the CBM-phrased default text; invoices failing on both dimensions simultaneously name both.
- **AC-7:** `runLoadCalc()`'s Reefer toggle, when enabled, recommends only from `isReefer: true` profiles.
- **AC-8 (corrected — round-1 finding, "identical" narrowed to the branching logic, not the literal exceeded-capacity text; round-2 finding, now actually true given the 4-row default set; round-3 finding, branch order made explicit; round-4 finding, LCL priority added):** The Quote feasibility check's `recContainer`/mode-mismatch **branching logic** (which of the four notice levels fires, given the same CBM input and `DB.containerProfiles` left at its unedited built-in defaults) is unchanged, now sourced from `recommendContainer()`'s `profile`/`reason` instead of the inline ternary — this is only true because the default non-Reefer set is exactly `{20GP, 40HQ}` (round-2 correction, §2 CONTAINER-001a), matching the old 2-tier model's own implicit structure; with the round-1 `40GP` default still in place this claim would have been false (see CONTAINER-001a's round-2 note). **Critically, this requires branching on `reason` first, never on `profile`'s truthiness** (round-3 correction, §2 CONTAINER-001c's Quote call-site bullet) — since `profile` is now non-null for both `'ok'` and `'exceeds'`, a naive substitution of `profile` for the old `recContainer` variable in the existing branch shape would silently make the exceeds-warning branch unreachable; a dedicated test confirms a genuinely-oversized CBM input (e.g. exceeding the 40HQ default) still produces the exceeds-warning notice, not a false "fits" notice, specifically when the freight mode text happens to contain the oversized profile's own code. **Also critically, `mode === 'LCL'` must be checked before `reason` at all** (round-4 correction, same bullet) — a dedicated test confirms a CBM input large enough to exceed every configured profile, with `mode` set to `'LCL'`, still produces the plain "LCL mode · N.NN CBM total" info notice, not the exceeds-warning, exactly as the live code's own `mode !== 'LCL'` guard clauses already ensure today; getting this wrong would be a real, user-visible regression for every LCL quote above the largest configured profile's capacity. The `'exceeds'` branch's **message text** is deliberately *not* required to stay byte-identical: it must now be built from the real returned profile's own `maxCBM`/`label` (now always present for `'exceeds'`, per the corrected return shape above — or the `'no_profiles'` case's own distinct message), so that editing the 40HQ profile's limit via Settings correctly changes what this notice says — the opposite of "identical" for that one string, and the whole point of Decision 1/3. A test confirms all four: notice *levels* match pre/post for unedited defaults on non-LCL modes, the exceeds-case specifically does not regress to a false "fits," the LCL-priority case specifically does not regress to a false "exceeds," and the *message text* correctly reflects an edited profile's new limit when one is edited.
- **AC-9:** `expAll()`/`doImport()` round-trip `containerProfiles` correctly (export includes it; restoring a backup with a different set replaces the in-memory list, not silently discarded).
- **AC-10:** `tests/run.js`'s `resetDB()` includes `containerProfiles: []`.
- **AC-11 (new — round-1 finding; round-2 finding, NaN case added):** Attempting to save a profile (new or edit, built-in or custom) with `maxCBM <= 0`, `maxWeightKg <= 0`, blank, **or non-numeric (e.g. `"abc"`)** is rejected with an inline validation error and no write to `DB.containerProfiles` — the non-numeric case specifically proving the validation mirrors `vBlurCurrencyPos()`'s full two-part check, not just its positivity half. A valid positive numeric edit to a built-in row's limits succeeds and is reflected in `recommendContainer()`'s next call.
- **AC-12 (new — round-5 finding):** A built-in row's `code` field renders disabled/read-only in the Settings UI and cannot be changed; `label`/`maxCBM`/`maxWeightKg` on that same row remain editable and the edit succeeds. A custom (non-built-in) row's `code` field remains freely editable.
- **AC-13 (new — round-6 finding; scope corrected — round-7 finding):** Attempting to save **any** profile — new, edit, built-in, or custom, matching AC-11's own scope exactly — with a blank `label` is rejected with an inline validation error and no write to `DB.containerProfiles`; attempting to save a **new or custom** profile with a blank `code` is likewise rejected (a built-in row's `code` can never actually be blank at save time, since AC-12 makes it read-only and all 4 seeded codes are non-blank — so the `code`-blank case is only meaningfully reachable for new/custom rows, and this AC's scope narrowing for `code` alone, unlike `label`, is intentional, not an oversight). The "`code`/`label` are required (non-blank)" clause in CONTAINER-001b's validation floor (§2) was previously stated but never covered by an AC; v7's own first attempt at this AC incorrectly narrowed the `label` case to "new or custom" too, silently leaving open whether blanking a built-in row's freely-editable `label` should be rejected.

## 4. Explicitly out of scope for v8

No linkage between `DB.containerProfiles` and `Shipment.containerType`'s own free-text field (§1.3) — a Shipment's recorded container type is not validated against, or auto-filled from, a profile; this is a disclosed non-goal, revisit if the operator wants that integration later. The Quote feasibility check's weight input is always `0` (Quote lines carry no weight field) — a disclosed limitation, not a regression, since no weight data exists on Quote lines to pass. No DG/Reefer compatibility warnings (§1.3). No 3D load optimization (§1.3). No historical backfill (§1.3, nothing to backfill). **No re-seed path if a restored backup's own `containerProfiles` array is empty or garbage (round-2 advisory, disclosed, not fixed; analogy direction corrected — round-3 finding):** once the `st_cp_seeded_v1` marker is set, `doImport()`'s restore line (§2, CONTAINER-001a's `doImport()` sibling, mirroring the `con`/`buy`/`ord`-style restore lines) will faithfully replace the 4 seeded rows with whatever a hand-edited or malformed backup's `containerProfiles` array contains, including `[]` — leaving every `recommendContainer()` call returning `reason:'no_profiles'` until the operator manually re-adds one in Settings, with no automatic recovery. This is a *different* direction from the already-accepted `CON-GAP-005` (`docs/known-gaps.md:544-546`: a backup file **missing** the `con` key causes `doImport()` to **preserve**, i.e. under-write, live Contact data rather than clearing it) — this REQ's own gap is a backup **containing** an empty/garbage array causing the restore to **overwrite**, i.e. replace good seeded data with nothing. Opposite failure direction, same accepted principle: a destructive, operator-confirmed restore is not the place to silently second-guess what the backup file actually contains, in either direction. **Named explicitly (round-6 finding): the same restore path is also the one way to bypass CONTAINER-001b's new `code`-is-read-only-on-built-in-rows protection.** An operator can export a backup, hand-edit a `builtIn:true` row's `code` directly in the JSON, and re-import it — `doImport()`'s restore line has no awareness of which fields on which rows the Settings UI treats as read-only, since it replaces the array wholesale. This is the identical "a destructive, operator-confirmed restore is trusted at face value" principle already accepted above, not a new kind of risk, but worth naming on its own given this is the specific protection round 5 just added — a hand-edited backup can still defeat it, same as it can already defeat the seeding/count guarantees.
