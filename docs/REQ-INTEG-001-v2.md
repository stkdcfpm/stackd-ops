# REQ-INTEG-001 (Phase 1) — Order Request/RFQ → Quote → Invoice Referential Integrity: Traceability & Staleness Detection

**Status:** v2 — supersedes v1. Independent requirements-gate review of v1 returned CONDITIONAL PASS (1 blocking finding, 3 advisory) — all four addressed below; see §7 for the full review-resolution log.
**Fixes:** `ORD-GAP-003`, `PO-GAP-003` (`docs/known-gaps.md`)
**Scope:** Phase 1 of 4. Traceability and read-only staleness warnings only. No buyer-approval capture (Phase 2), no payment-request entity (Phase 3), no automation/email/AI action-block work (Phase 4), no auto-fixing of stale records.

---

## 1. Business context

Investigation of the proforma → email → approval → invoice/deposit workflow (prior session, verified by direct code read, logged as `ORD-GAP-003`/`PO-GAP-003` in PR #88) found two live gaps:

1. When an Order Request's committed RFQ response is converted into a Quote (`ordConvertToQuote()`), the resulting Quote line carries no back-reference to the Order Request line or the specific `rfqResponses[]` entry it came from. If the operator later commits a *different* RFQ response on that same Order Request line, the existing Quote has no way to be flagged as stale — nothing links back to it.
2. When an Invoice's line items produce auto-generated Purchase Order(s) via `autoPos()`, the PO(s) are only ever generated once, on the invoice's first save. If the invoice is edited afterward — price, quantity, or line items added/removed — the already-generated PO(s) are never re-validated, and nothing warns that they've diverged. (`docs/known-gaps.md`'s `PO-GAP-003` entry names all three drift types explicitly; v1 of this REQ only covered the first two — see §7.)

This phase closes both gaps by adding the missing back-reference fields and a read-only warning banner wherever the affected records are viewed/edited. It deliberately does **not** attempt to fix, auto-update, or block saving of a stale record — surfacing the divergence to the operator is the entire scope.

### 1.1 Facts established during check-first re-verification (against `main` @ current HEAD, 521/521 tests passing) that shape this REQ

- **`rfqResponses[]` entries are append-only and immutable once created.** `saveRfqResponse()` (`index.html:2958-2980`) only ever `.push()`es a new entry (`2969`); no function anywhere edits an existing response's `cost`/`currency`/`cbm`/etc. after creation (the only in-place mutation found anywhere is `delCon()` nulling a response's `contactId` when the linked Contact is deleted — `index.html:10545` — not a price change). **Consequence for this REQ:** "the committed RFQ response has changed" (as this phase's staleness check needs to detect) can only mean "the operator committed a *different* response" — i.e. `ord.lines[i].committedResponseId` no longer equals the value captured when the Quote line was created. It cannot mean "the same response's values were edited," because that scenario does not exist in the current data model. REQ-INTEG-001e below is written against this exact, narrower, correct definition.
- **Order Request lines cannot be deleted once added** (`ordAddLine()` exists, `index.html:3099`; no corresponding delete-line function was found). Order Requests themselves *can* be deleted wholesale (`delOrd()`, `index.html:2795-2798`) — a bare filter with no cleanup of any Quote that may reference it. **Consequence:** the only "source no longer exists" case on the Order Request side is the whole Order Request being deleted, not an individual line.
- **Invoices can be deleted** (`delInv()`, `index.html:6416-6430`) with no cleanup of any PO's `invId`/`invNum` back-reference. **Consequence:** a PO generated by `autoPos()` can end up pointing at a deleted Invoice — this phase's PO staleness check must handle "source Invoice no longer exists" as a distinct case from "source Invoice's line items changed," not crash or silently pass.
- **`saveQte()`'s line mapping is an explicit field allowlist, not a passthrough.** `lines = cQL.map(function(l){ return { rid:l.rid, supId:..., desc:..., qty:..., uom:..., cost:..., cbm:..., dg:..., dutyPct:..., markup:... }; })` (`index.html:10252-10265`) constructs a brand-new object per line, naming every field explicitly. **Consequence, load-bearing for this REQ:** simply adding the three new source fields to the object pushed in `ordConvertToQuote()` (`index.html:2809-2812`) is not sufficient — the very next save (whether the immediate save that creates the Quote, or any later edit-save) will silently strip them unless `saveQte()`'s mapping is *also* updated to carry them through. Both the initial-create path and every subsequent edit-save path go through this one function, so one fix covers both, but it must not be missed.
- **No Quote → Invoice conversion path exists anywhere in the codebase.** Confirmed by direct search, twice independently (prior investigation and this REQ's requirements-gate review): `create_invoice`'s AI action payload (`index.html:8648` onward) has no quote-reference field; the only "New Invoice" entry point, `openInv()`, always starts with `cIL=[]`; both CSV import paths build Invoice records with no quote reference; the only `quoteId` field anywhere in the file is on POs (`qteToPoConvert()`, `index.html:10603`), never on Invoices. Per explicit user decision this session, **REQ-INTEG-001g below scopes the Invoice-side field as schema-only** — added to the Invoice record shape so it round-trips correctly through edit/save, but with no UI or automatic trigger writing it in this phase. It exists for forward-compatibility with a future phase that may add a real Quote→Invoice or Quote-aware Invoice-creation path; until then it stays empty on every invoice.
- **`autoPos()`'s per-supplier grouping (`index.html:5564-5582`) is directly re-runnable at staleness-check time**, which is what makes REQ-INTEG-001f's "new line added" detection (§7, B-1 fix) possible without any new *count*-tracking field: `sm[supId]` (`5565-5569`) groups the invoice's current line items by the `supId` resolved from each line's `lid` via the `DB.li` catalogue lookup — the exact same grouping can be re-derived from the *current* invoice state at any later point and diffed against the `lid`s already present on a given PO's `lineItems`.
- **`po.lineItems[].cost` is the catalogue cost (COGS) captured at generation time, not the invoice's own unit price/sell price (`up`).** Read directly at `index.html:5568`: `cost:r.cost||0` where `r` is the `DB.li` catalogue record, never `li.up`. **Consequence:** a PO's own stored `cost` cannot be compared against the invoice's current `up` for price-staleness — they are never expected to be equal even when nothing has drifted, since one is COGS and the other is sell price. A dedicated new field capturing the invoice's `up` at generation time is required for the price-comparison leg (see REQ-INTEG-001f). No equivalent new field is needed for the *quantity* leg — `po.lineItems[].qty` already equals the invoice line's `qty` at generation time (same line, `5568`) and can be compared directly against the current invoice's `qty` for that `lid`.

### 1.2 Design decision: reject timestamp-only staleness detection

`saveInv()` sets `inv.updAt = new Date().toISOString()` (`index.html:5436`) on **every** save, regardless of whether line items changed. A staleness check that simply compared "has `inv.updAt` changed since the PO was generated" would produce a false positive on unrelated edits (e.g. changing shipping notes, payment terms, or Incoterms without touching a single line item) — the test plan (§6) explicitly requires no false positives on unrelated/unchanged records. **This REQ requires the drift check to compare the specific fields that matter (line item presence/`lid`, `qty`, and unit price) captured at PO-generation time against their current values, not a blanket "anything changed" timestamp comparison.**

## 2. Requirements

### REQ-INTEG-001a — Quote line source fields
Each line pushed onto `cQL` by `ordConvertToQuote()` (`index.html:2809-2812`) for a committed RFQ response must additionally carry:
- `sourceOrdId` — the Order Request's `id`
- `sourceOrdLineId` — the Order Request line's `id`
- `sourceRfqResponseId` — the committed `rfqResponses[]` entry's `id` at the moment of conversion

Quote lines added manually via `addQteLine()` (`index.html:10071-10074`) must **not** carry these fields (they have no source to reference) — they remain absent/undefined on manually-added lines, exactly as today.

### REQ-INTEG-001b — `saveQte()` must carry the new fields through
`saveQte()`'s line-construction mapping (`index.html:10252-10265`) must be extended to include `sourceOrdId`, `sourceOrdLineId`, `sourceRfqResponseId` when present on the working line (`cQL[i]`), for both the initial save that creates the Quote and every subsequent edit-save. A line with no source fields (manually added) must continue to save with no source fields (not `null`, not empty string placeholders — genuinely absent, matching the codebase's existing convention of omitting rather than null-padding optional fields).

### REQ-INTEG-001c — Quote line source fields are immutable after creation
Once a Quote line has `sourceOrdId`/`sourceOrdLineId`/`sourceRfqResponseId` set, no UI in this phase edits or clears them. (Removing a Quote line entirely via `removeQteLine()` removes the whole line, which is existing, unchanged behavior — not a mutation of the source fields themselves.)

### REQ-INTEG-001d — FM-1 compliance confirmation
REQ-INTEG-001a/b/f/g are new fields on existing entities (Quote, PO line items, Invoice) with no new Sheets sync mapping. Confirmed by direct check of all three relevant field maps in `index.html`:
- `FIELD_MAPS.qt` (`index.html:3804`) — relevant to a/b — does not reference `sourceOrdId`/`sourceOrdLineId`/`sourceRfqResponseId`, and does not need to; it already omits other existing local-only Quote fields (`approvedBy`, `approvedReason`, `approvedAt`, all set in `saveQte()` at `10306-10310`), establishing the precedent that an unsynced field on an already-synced entity is a safe, already-used pattern.
- `FIELD_MAPS.po` (`index.html:3801`) — relevant to f — is header-level only (no line-item mapping exists for POs at all, sync or otherwise); the new per-line `sourceInvUp` field (or whatever spec-gate finalizes it as) sits inside `po.lineItems[]`, entirely outside this map's scope.
- `FIELD_MAPS.inv` (`index.html:3799`) — relevant to g — does not reference `sourceQuoteId`, and does not need to.

**Confirmed: this phase requires no `FIELD_MAPS` change, no new Apps Script tab, no new `syncEnt` key** — FM-1 exception category 2 (new fields on existing entities) applies.

### REQ-INTEG-001e — Quote staleness detection (fixes ORD-GAP-003)
On opening a Quote for editing (`editQte()`, `index.html:10034`), for every line with a `sourceOrdId`/`sourceOrdLineId`/`sourceRfqResponseId` set:
1. Look up `DB.ord` for `sourceOrdId`. If not found, the source Order Request has been deleted — render a warning distinguishing this case ("source Order Request no longer exists") from a live-value mismatch.
2. If found, look up the line by `sourceOrdLineId`.
3. Compare that line's **current** `committedResponseId` to the Quote line's stored `sourceRfqResponseId`. If they differ (including if the Order Request line's commitment has been cleared entirely, i.e. `committedResponseId` is now `null`), the Quote line is stale.
4. If **any** line on the Quote is stale by the above test, show one visible warning banner on the Quote (wording per the original brief: *"Source pricing has changed since this Quote was created — review before sending"*), reusing the existing visual convention `renderQteRatesWarn()` (`index.html:10733-10744`) already establishes for a comparable "warn on open, targeted `<div>` in the Quote modal" pattern.
5. A Quote with no lines carrying source fields at all (i.e. built entirely from manually-added lines, or built before this phase shipped) shows no banner — never a false positive from the absence of traceability data.
6. A Quote with a mix of manually-added and source-tracked lines is evaluated per line, exactly as in 1-3 above, for each source-tracked line only — a stale source-tracked line still triggers the banner even if other lines on the same Quote have no source fields at all (see AC-15).
7. **Exact granularity of the banner (one Quote-level banner vs. per-line indicators) and its precise placement in the modal are left to spec-gate** — this REQ mandates that a stale condition is detected and surfaced, not the pixel-level UI.

### REQ-INTEG-001f — PO staleness detection (fixes PO-GAP-003)
`autoPos(inv)` (`index.html:5564-5582`) must additionally capture, per generated PO line item, the Invoice line's `up` (unit price) *as it existed at PO-generation time* — call this `sourceInvUp` for concreteness; exact field name is for spec-gate to finalize. No new field is required for quantity — `po.lineItems[].qty` (already stored, `index.html:5568`) already equals the invoice line's `qty` at generation time and serves that comparison directly (see §1.1's last bullet for why this is asymmetric with price).

On opening a PO for editing (`editPO()`, `index.html:6442-6451`), for a PO with `invId` set (i.e. an `autoPos()`-originated PO — **not** a `qteToPoConvert()`-originated PO, which has `quoteId` instead and is explicitly out of scope for this REQ, see §4):
1. Look up `DB.inv` for `invId`. If not found, the source Invoice has been deleted — render a warning distinguishing this case from a live-value mismatch, per the same principle as REQ-INTEG-001e.
2. If found, for each **existing PO line item** with a `lid`, find the matching current Invoice line item by `lid` in `inv.lineItems`. The PO line is stale if: the matching Invoice line is no longer present at all, or its current `qty` differs from the PO line's own `qty`, or its current `up` differs from the PO line's captured `sourceInvUp`.
3. **Additionally**, re-derive the current invoice's line items whose resolved catalogue `supId` (via `DB.li`, same lookup `autoPos()` itself uses) matches this PO's `supId`. If that current set contains any `lid` **not present** among this PO's own `lineItems[].lid`, the PO is also stale — a new line item was added to the invoice, for this same supplier, since the PO was generated.
4. If the PO is stale by either 2 or 3, show one visible warning banner on the PO (equivalent wording to REQ-INTEG-001e, adapted for POs — e.g. *"Source Invoice has changed since this PO was generated — review before proceeding"*). The banner does not need to distinguish which of the two conditions triggered it (both are "the invoice diverged from what this PO was built from") — spec-gate may choose to differentiate the copy if useful, but this REQ does not require it.
5. A PO with no `invId` at all (manually created, or `qteToPoConvert()`-originated) shows no banner from this check — never a false positive from an unrelated PO.
6. A PO line item added manually via `addPLI()` (`index.html:6452`, which sets `lid:''`) is not evaluated by step 2 (no `lid` to match against) and is correctly ignored — it neither causes nor suppresses a staleness finding on the PO's other, `autoPos()`-originated lines (see AC-17).
7. Per §1.2, this must be a field-level comparison (line presence/qty/price per matched line, plus the reverse "new line" check in step 3), **not** a comparison of `inv.updAt` or any other blanket "has this invoice been saved" signal.

**Residual gap, explicitly accepted and not fixed by this phase (see §4):** if an invoice gains a line item for a **brand-new supplier** that had no line items on the invoice at `autoPos()`-generation time, there is no PO at all for that supplier to attach a banner to — step 3 above only re-checks suppliers a PO already exists for. This is a real, known limitation of a detection-only, non-regenerating design (Phase 1 explicitly never re-runs `autoPos()`), disclosed here in the same spirit as `docs/known-gaps.md`'s own `PO-GAP-002` entry discloses its residual scope rather than silently omitting it.

### REQ-INTEG-001g — Invoice `sourceQuoteId` field (schema-only, descoped from automatic population)
Add an optional `sourceQuoteId` field to the Invoice record shape in `saveInv()` (`index.html:5413-5562`), defaulting to `''` on a brand-new invoice and preserved unchanged from the existing record on every edit-save (mirroring the existing preserve-pattern already used for `inv.pos` at `index.html:5448-5467`). **No UI, no automatic trigger, and no AI-action wiring sets this field in this phase** — per explicit user decision, this is intentionally a schema-only addition, present so a future phase (2, 3, or 4) that adds a real Quote-aware Invoice-creation path does not require a second schema migration. It will read as empty on every invoice created under this phase and remain so until a later phase writes to it.

## 3. Acceptance criteria

| AC-2 | A Quote line created via REQ-INTEG-001a, then the Quote is re-opened and re-saved with no changes | The Quote is re-saved (`saveQte()`) | The source fields are still present and unchanged (proves REQ-INTEG-001b's fix — this is the exact scenario that would silently fail without it) |

| AC-6 | A Quote whose source Order Request has been deleted entirely | The Quote is opened for edit | A "source no longer exists" message is shown, distinguishable from AC-5's mismatch message |

## 4. Explicitly out of scope

- Buyer-approval capture of any kind (Phase 2).
- A payment-request entity or action (Phase 3).
- Any automation, email, or AI action-block work referencing these new fields (Phase 4). The AI Assistant's `create_invoice`/`create_quote` actions are not modified in this phase.
- Auto-fixing, auto-updating, or blocking the save of a stale Quote or PO. Detection and a visible warning only — the operator decides what to do.
- `qteToPoConvert()`-originated PO staleness (i.e. a PO drifting from the Quote it was converted from). PO-GAP-003, which this REQ closes, is specifically about the `autoPos()`/Invoice-origin case. A comparable Quote↔PO gap was not logged and is not in scope here — if wanted, it should be logged as its own gap first, in a future session.
- Any change to `qteToPoConvert()` itself, which already stores `quoteId`/`quoteNum` on the PO — that back-reference already exists and needs no work.
- Retroactive backfill of source fields onto Quotes/POs created before this phase ships. AC-7 and AC-12 above are the explicit acknowledgment that pre-existing records simply show no banner, by design, not by oversight.
- **A brand-new-supplier line added to an invoice after `autoPos()` already ran, with no PO ever generated for that supplier** — see REQ-INTEG-001f's residual-gap disclosure and AC-18. Closing this fully would require either re-running PO generation (out of scope — no auto-fixing/regeneration in this phase) or a new Invoice-level banner surface (not briefed; a candidate for a future phase or a separately-logged gap, not silently built here).

## 7. Requirements-gate review resolution log (v1 → v2)

An independent requirements-gate review of v1 returned **CONDITIONAL PASS** with 1 blocking finding and 3 advisory findings, all addressed in this v2:

- **B-1 (blocking):** v1's PO staleness mechanism only compared PO line items against their matching current-invoice line by `lid` — it structurally could never detect a *newly added* invoice line item, one of the three drift types `PO-GAP-003`'s own text names (price, quantity, added/removed line items). **Fixed:** REQ-INTEG-001f.3 adds the reverse check (re-derive the invoice's current per-supplier line set and diff against the PO's own `lineItems[].lid`), and the one still-unclosed residual case (a brand-new supplier with no PO at all) is now explicitly disclosed as an accepted, tested-absent limitation (§4, AC-18) rather than silently uncovered.
- **A-1 (advisory):** v1's FM-1 reasoning in REQ-INTEG-001d checked the wrong field-map table for one sub-requirement and never checked `FIELD_MAPS.inv` at all, even though its conclusion was correct. **Fixed:** REQ-INTEG-001d now attributes each field map to the specific sub-requirement it's actually relevant to.
- **A-2 (advisory):** v1's open-questions list (§5) only asked for exact banner copy on the Quote modal, not the PO modal. **Fixed:** §5 item 1 now covers both.
- **A-3 (advisory):** v1 had no acceptance criteria for mixed-line scenarios (a Quote with both manual and source-tracked lines; a PO with both `autoPos()`-originated and manually-added lines). **Fixed:** AC-15 and AC-17 added.

A-4 (a pre-existing, unrelated bug noticed during review — `qteToPoConvert()` builds POs with a `lines` key while every other PO code path reads `lineItems`) is out of scope for this REQ (it affects only `qteToPoConvert()`-originated POs, which this REQ explicitly excludes) and is not addressed here; it may warrant its own `known-gaps.md` entry in a future session.
