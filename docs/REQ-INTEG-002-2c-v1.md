## 0. Scoping

This is **sub-phase 2c** of the in-flight Payment Allocation build (`REQ-INTEG-002`): 2a a Supplier Payment ledger (shipped v2.9.62, stabilized through v2.9.63–v2.9.65) → 2b the Invoice→PO enumeration fix making `Invoice.pos[]` authoritative (shipped v2.9.66) → **2c, this REQ** → 2d a full allocation link (still unscoped, comes after this REQ).

Unlike 2a/2b, 2c has no prior scoping pass at all — `STACKD_CONTEXT.md` flags it as "unbriefed... likely needs a scoping/investigation pass first, similar to how 2a/2b began, rather than assuming a specific design" (corrected per requirements-gate round 2, A5 — an earlier draft attributed this phrasing to `docs/requirements-tracker.md` too, which only names 2c as a bare label inside the 2a→2b→2c→2d chain, with no "unbriefed"/"needs scoping" language of its own). A check-first investigation was run before drafting this REQ, and its central finding reframes what "2c" actually needs to be:

**Buyer payments already support multiple partial payments against one invoice today — this predates 2a.** `DB.payments`/`savePayment()`/`getInvPayments()`/`renderPaymentsTab()` (all pre-existing, `index.html:13021-13217`) place no restriction on how many payment records exist against one invoice; the UI already lets an operator add payment rows one at a time. In fact 2a's own Supplier Payment ledger was explicitly built *mirroring this already-existing buyer ledger* (`docs/REQ-INTEG-002-v2.md` §1.1). So "buyer payment tranches" cannot mean "let a buyer pay in installments" — that already ships. What it can defensibly mean, and what this REQ scopes it to, is: **closing the real parity gaps between the buyer payment ledger and the now-more-mature Supplier Payment ledger**, plus fixing one confirmed-live bug found along the way that tranche-style usage (more payment rows, more edits/deletes per invoice) makes materially more likely to surface. See §1 for the specific gaps and §3 for what is explicitly not being built.

This REQ does **not** touch Cloud Data — `DB.payments` is not in Cloud Data scope (Phase 3, still unbriefed) and nothing here changes that. Every change in this REQ is local-only, same as `DB.payments` behaves today.

**On `inv.pos[]`/2b's own relationship to this REQ (requirements-gate round 1, B5):** `STACKD_CONTEXT.md`'s own backlog entry for this phase states `inv.pos[]` is "now the authoritative Invoice→PO link, a prerequisite for **2c/2d's** payment-allocation logic" — grouping 2c with 2d, not framing all allocation-linking work as 2d-only. This REQ's own changes (§2) never read or write `Invoice.pos[]`/`getInvoicePOs()` at all: closing the buyer/supplier ledger parity gap (currency awareness, purpose, centralized reconciliation) and fixing `deletePayment()`'s status bug are entirely about the *shape* of a payment record and how it reconciles against its own invoice — they do not need to know which Purchase Order(s) fund that invoice. The "2c/2d" phrasing is read here as acknowledging that `inv.pos[]` is a prerequisite *available to* both 2c and 2d, not as a mandate that 2c must consume it — the actual cross-entity allocation work (tying a specific buyer payment to a specific PO/line item, which is where `inv.pos[]` would actually get used) is exactly what "full allocation link" in 2d's own name describes, and remains deferred there.

After this REQ ships, **2d (full allocation link)** remains the next, still-unscoped step in the Payment Allocation build — not started by this REQ, per the same "don't assume the next phase's design" discipline this series has followed throughout the Cloud Data migration.

## 1. Business context

### 1.1 What already works today

`DB.payments` (key `K.pm`) holds buyer-payment records shaped `{ id, invId, invNum, date, amount, method, reference, notes, type:'buyer_payment', creAt }` (`addPaymentFromForm()`, `index.html:13172-13204`). `savePayment(payment)` (`index.html:13030-13089`, already `async` since REQ-CLOUD-005) upserts by id, recomputes `inv.dep` from `getInvTotalPaid(invId)` (`index.html:13026-13028`, a raw currency-agnostic sum), and auto-transitions `inv.status` to `Partially Paid`/`Paid` once the recomputed total crosses `inv.calc_grandTotal` — mutating `inv.status` directly, bypassing `canTransitionStatus()`'s forward-only guard entirely (only `saveInv()`'s own form-save path checks it, `index.html:7031-7032`). `deletePayment(id)` (`index.html:13091-13110`) removes a record and recomputes `inv.dep`, but — confirmed by direct reading, not assumption — **never re-evaluates `inv.status`** (§1.3). `renderPaymentsTab(invId)` (`index.html:13112-13170`) inside the `ov-payments` modal, opened via a per-row "$" button on the Invoices list (`index.html:7569`), already renders every payment row against one invoice, is available regardless of the invoice's own lock state, and is already exported via `acctPmtCSV`/`acctPmtJSON`/`acctFACSV` (`index.html:11172-11248`) and read by `_aiExecTool('get_payments')`.

**Two more `DB.payments` push sites exist beyond `addPaymentFromForm()` (requirements-gate round 5, advisory): `saveInv()`'s goodwill-credit handling (`index.html:7075-7079`) and `saveCN()`'s own goodwill-credit handling (`index.html:10022-10025`).** Both push a differently-shaped record (`ref` instead of `reference`, no `type` field at all) representing an internal accounting entry, not an operator-recorded buyer payment — these will permanently, not just pre-this-REQ, lack `purpose`/`currency` (§2a/§2b's "no backfill... renders as a dash" language describes only genuinely legacy `addPaymentFromForm()`-created records aging out, not these two ongoing, always-shapeless-in-this-respect entries). This doesn't threaten the currency math anywhere in §2c: a currency-less record still correctly defaults to `inv.cur` per B1, which is exactly right for an internal same-currency credit. Not fixed here — out of scope (§3) — but disclosed so a SPEC author isn't surprised these two sites exist alongside the one already described above.

### 1.2 The real gap: buyer payments have zero currency awareness

Every read site treats a buyer payment's amount as implicitly denominated in the invoice's own currency — there is no `currency` field on a `DB.payments` record at all. `cInv(inv)`'s own inline reconciliation (`index.html:4763-4768`) sums `DB.payments` amounts **raw**, with no currency check whatsoever; `editInv()` (`index.html:6822`) calls the shared `getInvTotalPaid(inv.id)` directly rather than duplicating the sum inline — it is one of the three call sites named in REQ-INTEG-002-2c-c, not a second copy of `cInv()`'s logic (corrected per requirements-gate round 1, B4 — an earlier draft of this REQ mischaracterized it as a duplicate). Compare to the Supplier Payment ledger post-2a: `saveSupPayment()`'s records carry a `currency` field and a `rateLock` object (`lockFxRate(amount, currency)`, `index.html:4847-4865`, snapshotting all three static FX rates at save time so a later reconciliation against a *different* currency uses the historically-locked rate, not today's live rate) — `getPOTotalPaidNative(po)` (`index.html:13225-13243`) sums same-currency payments raw and pivots any different-currency payment through that record's own locked GBP-equivalent via `fromGBPLocked()`, and `getPOEffectiveDepInfo(po)` (`index.html:13251-13262`) returns `{value, source}` — `'ledger'`, `'legacy-no-records'`, or `'legacy-unsupported-currency'` (gated on `PO_DEP_RECONCILE_CURS = ['USD','GBP','RMB','CNY','BBD']`, `index.html:13219`) — as a single point of truth, never mutating `po.dep`. Nothing equivalent exists for `DB.payments`. If a buyer genuinely pays in a currency other than the invoice's own, today's code silently sums the wrong number.

**Currency-set scope, decided here rather than left open:** the Invoice currency dropdown (`if-cur`, `index.html:1150`) offers six options — USD/GBP/EUR/BBD/NGN/GHS — two more than the PO dropdown's four (`pf-cur`, `index.html:2358`: USD/CNY/GBP/EUR) (corrected arithmetic, requirements-gate round 1, A1). But `toGBP()`/`fromGBP()` (`index.html:4827-4845`), the only FX pivot mechanism that exists anywhere in this codebase, supports exactly the same four real currencies as `PO_DEP_RECONCILE_CURS` (GBP/USD/RMB-or-CNY/BBD) and silently no-ops (returns the input unchanged, not an error) for anything else — EUR is already a logged, deliberately-not-fixed gap (`PROC-GAP-002`), and **NGN/GHS have the identical unlogged gap**, confirmed by this REQ's own research. This REQ reuses `PO_DEP_RECONCILE_CURS` as-is for Invoice reconciliation (§2c) — it does **not** extend FX coverage to EUR/NGN/GHS, matching this series' own precedent of treating that as a separate, larger currency-infrastructure gap, not something a payment-ledger REQ silently absorbs.

**Legacy-record currency default (requirements-gate round 1, B1 — blocking): a missing `currency` on an existing pre-REQ payment record must default to the invoice's own currency (`inv.cur`), never a bare `'USD'`.** `getPOTotalPaidNative(po)` itself defaults a missing `p.currency` to `'USD'` (`index.html:13226-13229`), but that default is dead code on the Supplier Payment side — `DB.supPayments` was born currency-aware in 2a via a real, always-populated `<select id="spm-cur">` (`index.html:13348-13350`), so no currency-less supplier-payment record has ever existed. `DB.payments` is different: it has years of real, pre-this-REQ production records against invoices in every one of the six currencies named above, none of which carry a `currency` field today. If `getInvTotalPaidNative(inv)` copied the `'USD'` default verbatim, then for any existing non-USD invoice with payment history, every legacy payment would be misread as USD, trigger the cross-currency pivot branch, find no `rateLock` on the legacy record either, and contribute **zero** to the reconciled total — silently zeroing out the paid amount on a previously-`Paid` GBP/EUR/BBD/NGN/GHS invoice the moment this REQ ships. `getInvTotalPaidNative`/`getInvEffectiveDepInfo` must default a missing `currency` to `inv.cur` instead, so a legacy record with no `currency` at all is read as "paid in the invoice's own currency" (same-currency path, summed raw, no pivot, no `rateLock` needed) — the historically correct assumption, since that was the only currency a buyer payment could implicitly be in before this REQ existed. See AC-3a.

### 1.3 The real bug: `deletePayment()` never reverses `inv.status`

Confirmed by direct reading of `deletePayment()` (`index.html:13091-13110`): it recalculates `inv.dep` but leaves `inv.status` untouched. Today this is a narrow, low-frequency latent bug — deleting a payment is rare. A tranche-oriented feature (more payment rows recorded over an invoice's life, more chance of correcting a wrongly-entered one) makes it a real, live defect worth fixing in the same change that touches this function, not a separately-scoped follow-up: an invoice can end up permanently stuck at `Paid` or `Partially Paid` — both `LOCKED_STATUSES` (`index.html:2850`) — with a `dep`/status pairing that no longer reflects reality, and no way to correct it short of manually editing `localStorage`.

### 1.4 The "purpose" field gap

Supplier Payment records carry a required `purpose` field, a closed three-option select — `Deposit`/`Balance`/`Other` (`index.html:13351`, enforced by `vSupPay()`, `index.html:13284-13286`). Buyer payment records have no equivalent. Without it, a buyer-payment "tranche" is an undifferentiated amount+date+method — there is no way to record or report on *why* a given tranche was paid (a deposit vs. a balance vs. something else), which is the one piece of information that actually distinguishes a genuine tranche-tracking feature from the ad-hoc partial-payment recording that already exists (§1.1).

### 1.5 What this REQ deliberately does not touch

The FPM-funded-deposit auto-recovery block inside `savePayment()` (`index.html:13059-13083`, extended most recently by `REQ-CLOUD-005` to route through `persistPOChange()`/`refreshPOFromSupabase()` when Purchase Order has migrated) is business-logic-orthogonal to buyer-payment tranches — FPM funding is a supplier-side deposit concept, buyer payments are receivables — but it is **not code-orthogonal**: it lives in the same function, immediately after the auto-status logic this REQ's §1.3 fix touches, and fires only on the `prevStatus !== 'Paid' → 'Paid'` transition. Any change to `savePayment()`'s status-derivation logic must leave this block's trigger condition and Cloud Data branch completely untouched, exactly the same caution `REQ-INTEG-002`'s own 2a explicitly declared as a non-goal (`REQ-INTEG-002h`) for the analogous duplicated-logic question on the supplier side.

## 2. Requirements

**REQ-INTEG-002-2c-a.** Add a required `purpose` field to buyer payment records — a closed select, `Deposit`/`Balance`/`Other`, mirroring Supplier Payment's own field exactly (same three options, same "required, non-empty" validation shape). `vPay(date, amount, invId, purpose)` gains a purpose check mirroring `vSupPay()`'s (`index.html:13284-13286`); `addPaymentFromForm()` reads a new `pm-purpose` select (mirroring `spm-purpose`, `index.html:13351`) and includes `purpose` in the record it builds. Existing payment records with no `purpose` (pre-dating this REQ) render as a dash/blank in any table that shows the column, exactly how Supplier Payment's own pre-existing records would if that field were ever added retroactively there — no backfill migration.

**REQ-INTEG-002-2c-b.** Add `currency` + `rateLock` fields to buyer payment records, reusing the existing `lockFxRate(amount, currency)` helper (`index.html:4847-4865`) verbatim — no new locking mechanism. `addPaymentFromForm()` gains a new `pm-cur` select offering exactly `['USD','GBP','RMB','BBD']` (requirements-gate round 2, A7 — underspecified in an earlier draft; this is `spm-cur`'s own exact option list, `index.html:13349`, not the Invoice currency dropdown's six or `PO_DEP_RECONCILE_CURS`'s five, since `RMB` and `CNY` are the same real currency and `spm-cur` already established the precedent of listing it once — deliberately excludes EUR/NGN/GHS, the currencies `lockFxRate()`/`toGBP()` cannot meaningfully pivot, so an operator is never offered a payment-currency choice that would silently mis-convert), defaulting to the invoice's own currency (`inv.cur`) when that currency is itself in the list. The select still allows choosing a different supported currency for the rarer cross-currency-payment case.

**When `inv.cur` is itself not in `PO_DEP_RECONCILE_CURS` (EUR/NGN/GHS), `pm-cur` is disabled and the payment's `currency` field is set to `inv.cur` itself — not a substitute from the four-option list (requirements-gate round 5 — blocking; round 4's fix, which locked such a payment to a *different*, arbitrary supported currency like `'USD'`, didn't actually make the reconciliation correct, only internally consistent among new records — it still disagreed with how a pre-existing legacy record on the very same invoice defaults, per §1.2/B1, to `inv.cur`).** No `rateLock` is generated for such a payment (there is nothing to lock a rate for — `lockFxRate()` is never called). This makes every payment against an unsupported-currency invoice, legacy or new alike, carry the identical `currency` value (`inv.cur`) by true construction, not merely by coincidence of the raw-sum branch's own currency-blindness (§2c) — there is no cross-currency choice being suppressed here, since `inv.cur` itself was never a real option in `pm-cur` to begin with.

**REQ-INTEG-002-2c-c.** New `getInvTotalPaidNative(inv)` (takes the invoice object, mirroring `getPOTotalPaidNative(po)`'s signature exactly — not an id, unlike the old `getInvTotalPaid(invId)` it supersedes) and `getInvEffectiveDepInfo(inv)` (mirroring `getPOEffectiveDepInfo(po)`'s `{value, source}` contract and its three `source` values verbatim: `'ledger'`, `'legacy-no-records'`, `'legacy-unsupported-currency'`).

`getInvTotalPaidNative(inv)`'s own behavior, in full (consolidated after five requirements-gate rounds each refining a piece of this — see §8 for the round-by-round history): for a *supported* `inv.cur` (normalized, `CNY`→`RMB`, per `PO_DEP_RECONCILE_CURS`), it sums same-currency payments raw and pivots any different-currency payment through that payment's own locked `rateLock`, exactly mirroring `getPOTotalPaidNative(po)` — except a payment record with no `currency` field at all (a legacy, pre-this-REQ record) is read as paid in `inv.cur` itself, never defaulted to `'USD'` (§1.2/B1: copying `getPOTotalPaidNative`'s own `'USD'` default verbatim would misread every legacy record on a non-USD invoice as USD, forcing a bogus pivot that zeroes out its contribution). For an *unsupported* `inv.cur` (EUR/NGN/GHS), the function never reaches `fromGBPLocked()` at all — every payment is summed raw regardless of its own `currency`, the same degraded, no-pivot-attempted behavior the pre-this-REQ `getInvTotalPaid()` always used for every invoice. This is safe, not merely convenient, because §2b guarantees every payment against such an invoice — legacy (defaults to `inv.cur`) or new (explicitly set to `inv.cur`, never a substitute currency) alike — carries the identical `currency` value: there is exactly one currency in play for that invoice, it just happens to be one this codebase's FX pivot cannot convert, which is exactly why this branch never tries to.

This makes `getInvTotalPaidNative(inv)` safe to call directly from any context, which matters because `savePayment()`'s own `totalPaid` computation (`index.html:13041`) and `deletePayment()`'s recompute (`index.html:13103`) both call it **directly**, not via `getInvEffectiveDepInfo(inv).value` — the *no-records* fallback branch is genuinely never reachable from `savePayment()` (`DB.payments.push(payment)` runs before the total is computed, `index.html:13032-13034`) and, when reachable from `deletePayment()` after an invoice's last payment is removed, correctly resolves to `0` via the same function's own empty-array sum, needing no special-casing. Every *other* reconciliation site — `cInv()`'s inline logic (`index.html:4763-4768`), `editInv()` (`index.html:6822`, only the `depField.value = getInvTotalPaid(inv.id).toFixed(2);` clause of that line — the two other clauses on the same line and the surrounding badge-count/readOnly-toggle code at 6814-6821/6823-6826 are untouched), and three more raw, currency-blind `DB.payments` sums independently found beyond these two — `renderStatement(buyer)`'s per-invoice `paid` (`index.html:8099-8100`), `prevStmtPdf()`'s identical duplicate (`index.html:8166`), and `saveCN()`'s `totalPayments` feeding `linkedInv.calc_balanceDue` (`index.html:10039-10042`) — all switch to `getInvEffectiveDepInfo(inv).value` instead, **not** `getInvTotalPaidNative(inv)` directly: these are read-only reporting sites running against arbitrary invoices, not a just-mutated ledger, so an invoice with a real, manually-typed `inv.dep` and zero payment records (the `if-dep` field stays editable exactly when this is true, `index.html:6820-6826`) must fall back to that raw `inv.dep` rather than showing a self-contradictory hard `$0` next to an already-correct `Balance Due`.

Leaving any of these five sites on the old `getInvTotalPaid(invId)` while others became currency-correct would have introduced a fresh cross-screen inconsistency this REQ itself is responsible for — the Buyer Statement/PDF or a Credit-Note-applied balance-due figure showing a different, wrong number than the invoice's own edit form for the exact same invoice. `getPOTotalPaidNative(po)` on the Purchase Order side is deliberately left unchanged — it has no direct caller outside `getPOEffectiveDepInfo()`'s own currency gate today, so it carries no equivalent live risk, and retrofitting it is out of scope for a buyer-payments REQ (§3).

The old `getInvTotalPaid(invId)` (`index.html:13026-13028`) is removed, not kept as a compatibility wrapper, once every call site above is migrated — confirmed via repo-wide grep that no other call site exists anywhere, including `tests/run.js`/`tests/fixtures.js`.

**REQ-INTEG-002-2c-d.** Fix the bug in §1.3: `deletePayment()` gains the same auto-status re-derivation `savePayment()` already performs — recompute `totalPaid` via `getInvTotalPaidNative(inv)`, compare against the **identical grand-total expression `savePayment()` already uses**, `(+inv.calc_grandTotal || cInv(inv).grand)` (`index.html:13047` — not `inv.calc_grandTotal` alone; requirements-gate round 1, B2, flagged that omitting `cInv(inv).grand`'s fallback would let a stale/zero `calc_grandTotal` trivially satisfy `paid >= grand` and force a wrong `'Paid'` status) — but scoped narrowly — only re-derive `inv.status` when its *current* value is `Partially Paid` or `Paid` (i.e., a status this exact derivation logic could itself have produced); never touch `Draft`, `Pro-forma`, `Sent`, or `Cancelled`. When the recomputed total drops to 0, the status reverts to `Sent` — the last pre-`Partially Paid` status in `STATUS_ORDER`'s own ordering (`index.html:2851` — not `LOCKED_STATUSES`, an unordered membership set with no progression semantics; corrected per requirements-gate round 1, A3) — via a direct assignment, the same way `savePayment()`'s own auto-status logic already bypasses `canTransitionStatus()`'s forward-only guard (a deliberate backward move correcting a wrongly-entered payment, not a violation of the guard's own intent, which governs `saveInv()`'s form-driven status field specifically).

**REQ-INTEG-002-2c-e.** `renderPaymentsTab(invId)` (`index.html:13112-13170`) needs three changes, not just the column addition an earlier draft described (requirements-gate round 6 — blocking; the render layer had the same legacy-record/cross-currency coexistence gap §2c-c was fixed for five times over, just never closed here):

1. **The top summary box's own inline raw sum is a sixth currency-blind `DB.payments` total, independently found and previously undisclosed.** `var totalPaid = payments.reduce(function(s,p){ return s+(+p.amount||0); }, 0);` (`index.html:13118`) feeds both the "Total Received" and "Balance Due" figures (`index.html:13125-13129`), displayed using the invoice's own currency (`cur = inv.cur`, `index.html:13120`). This switches to `getInvEffectiveDepInfo(inv).value` — the same function `cInv()`/`editInv()`/`renderStatement()`/`prevStmtPdf()`/`saveCN()` already use (§2c-c) — which is always expressed correctly in `inv.cur`, unlike the raw sum it replaces.

2. **The per-row Amount column** (`fmt(pm.amount,cur)`, `index.html:13140`, currently using the same table-wide `cur` as the summary box) is repointed to each row's own **resolved effective currency** — `pm.currency || inv.cur` (the same `pm.currency`-defaults-to-`inv.cur` rule B1 established for reconciliation, applied here to display) — mirroring how `renderPOPaymentsTab()` already does this correctly (`fmt(pm.amount, pm.currency)`, `index.html:13329`, since every Supplier Payment record has always had a `currency`). Before this REQ, using the table-wide currency for every row was harmless (every buyer payment was implicitly in `inv.cur`); after §2b makes a genuinely different `pm.currency` possible, showing a GBP amount with a `$` symbol next to a Currency column correctly labeled "GBP" on the same row would be a direct, visible self-contradiction.

3. **A Purpose column** (mirroring `renderPOPaymentsTab()`'s own table shape, `index.html:13322-13338`) and a **Currency/GBP-equivalent column pair**, shown only when at least one rendered payment's *resolved effective currency* (`pm.currency || inv.cur`, same rule as item 2) differs from the invoice's own — mirroring how the Supplier Payment tab always shows both columns (Supplier Payment's own currency choice is far more routinely cross-currency than Buyer Payment's is expected to be, per §2b's differing default), so an all-same-currency invoice's payment table stays as uncluttered as it is today. The GBP-equivalent cell reads `pm.rateLock.gbpEquiv` when present (a genuinely cross-currency, post-this-REQ payment, which always has one per §2b), guarded the same way `renderPOPaymentsTab()` already guards it (`(pm.rateLock&&pm.rateLock.gbpEquiv)||0`, `index.html:13330`) — but falls back to a **live** `toGBP(pm.amount, pm.currency||inv.cur)` computation, not a bare `0`, for a row with no `rateLock` at all (a legacy record, which never has one) — the same "current-rate, not historically-locked, and that's an accepted, disclosed difference for pre-this-REQ data" reasoning `fromGBPLocked()`'s own code comment already documents for its analogous fallback case. On an unsupported-currency (EUR/NGN/GHS) invoice, every payment's *resolved effective currency* is `inv.cur` itself (§2b) — this column pair correctly never appears there either, since "differs from the invoice's own" is never true for any row.

**REQ-INTEG-002-2c-f.** `acctPmtCSV` (`index.html:11172-11184`, corrected off-by-one per requirements-gate round 2, A4) and `acctFACSV` (`index.html:11235-11248`) each already have a "Currency" column, but it is sourced from the *linked invoice's* `inv.cur` (`index.html:11180`), not any payment-level field — once REQ-INTEG-002-2c-b gives a payment its own `currency` that can legitimately differ from `inv.cur`, that existing column is repointed to read `pm.currency` directly (falling back to `inv.cur` only for a legacy record with no `currency` of its own, per §2c's default), and both gain a new "Purpose" column. `acctPmtJSON` (`index.html:11190-11192`) is a raw `JSON.stringify({...,payments})` pass-through of the payment objects themselves — it needs no code change at all, since a new field on a `DB.payments` record already flows through automatically (corrected per requirements-gate round 1, A2 — an earlier draft of this REQ listed it alongside the two CSV exporters as needing the same field-list edit, which overstated the work there). `_aiExecTool('get_payments')` gains `purpose`/`currency` in its own explicit per-payment field list. (No Supplier Payment CSV/JSON export or `_aiExecTool` equivalent actually exists anywhere in the codebase to "match" — confirmed by requirements-gate round 3 via a full grep of every `acct*CSV`/`acct*JSON` function and every `_aiExecTool` tool name; an earlier draft's claim that this REQ's export changes "match their Supplier Payment equivalents' shape" was therefore unverifiable and has been removed. The actual precedent worth mirroring is `renderPOPaymentsTab()`'s existing Purpose/Currency UI columns, §2e, not any export function.)

## 3. Out of scope

- **A scheduled/expected-payment-plan feature** (e.g., "30% deposit due on order, 70% balance due on shipment," with due dates, reminders, or an expected-vs-actual comparison) — the word "tranche" in this sub-phase's name could be read this way, but nothing in the existing roadmap language (`docs/requirements-tracker.md`, `STACKD_CONTEXT.md`) commits to it, and it is a materially larger, separate feature with its own UX design questions. This REQ closes the parity/bug gaps in the ledger that already exists (§1); a scheduled-payment-plan feature, if the business wants one, is its own future REQ.
- **2d (full allocation link)** — the next, still-unscoped step in the Payment Allocation build; not started here.
- **`PROC-GAP-002`** (EUR excluded from `toGBP()`/`fromGBP()`) and the identical, newly-confirmed NGN/GHS gap (§1.2) — both pre-existing, unrelated to buyer payments specifically, not fixed here. Log the NGN/GHS half as a new entry in `docs/known-gaps.md` at ship time (it was previously unlogged, confirmed by this REQ's own research), cross-referenced to `PROC-GAP-002` as the same defect class.
- **Real-time per-save Sheets sync for `DB.payments`** — `savePayment()`'s own comment (`index.html:13088`, "Payments not synced to Sheets yet — handled in v3.0.0") already defers this explicitly; bulk sync via `syncAll()`/`pullAll()`/`pushAll()` already covers `DB.payments` today (per `REQ-INTEG-002-v2.md` §1.1) and is unaffected by this REQ.
- **Cloud Data migration for `DB.payments`** — Phase 3, unbriefed, not started by this REQ (§0).

## 4. Acceptance criteria

- **AC-1.** A new buyer payment cannot be saved without selecting a `purpose` (`Deposit`/`Balance`/`Other`) — `vPay()` blocks with a toast, mirroring `vSupPay()`'s own purpose check exactly.
- **AC-2.** The `pm-cur` select offers exactly `USD`/`GBP`/`RMB`/`BBD` and defaults to the invoice's own currency when that currency is one of those four; the select can be changed to record a genuinely cross-currency payment; the saved record carries both `currency` and a `rateLock` object shaped identically to a Supplier Payment's own (`amount`/`currency`/`gbpEquiv`/`ratesUsed`/`ts`).
- **AC-2a (requirements-gate round 4 — blocking, new; corrected round 5).** When the invoice's own currency is not one of those four (EUR/NGN/GHS), `pm-cur` is disabled and the saved payment's `currency` is set to `inv.cur` itself, not a substitute from the four-option list — no `rateLock` is generated for such a payment. This means every payment against such an invoice, whether it predates this REQ (defaults to `inv.cur` per B1) or is newly recorded (explicitly set to `inv.cur` here), carries the identical currency value, eliminating the possibility of two payments against the same unsupported-currency invoice ever disagreeing on currency and being silently summed together as if they matched — demonstrated with both a legacy (no stored `currency` field) and a newly-recorded payment coexisting on the same EUR invoice.
- **AC-3.** `getInvTotalPaidNative(inv)` sums same-currency payments raw (zero FX rounding) and pivots any different-currency payment through that payment's own locked `rateLock`, never today's live rate — demonstrated with at least one same-currency and one different-currency payment on the same invoice, both on a supported (`PO_DEP_RECONCILE_CURS`) invoice currency.
- **AC-3a.** A non-USD invoice (e.g. GBP) with pre-existing payment records that carry no `currency`/`rateLock` field at all (simulating real production data that predates this REQ) reconciles to its correct historical total via `getInvTotalPaidNative(inv)` — the legacy record is read as paid in the invoice's own currency, not defaulted to `'USD'` and incorrectly pivoted to `$0`.
- **AC-3b (requirements-gate round 3 — blocking, new; broadened round 4/5).** `getInvTotalPaidNative(inv)` never reaches `fromGBPLocked()` for an invoice whose own currency is not in `PO_DEP_RECONCILE_CURS` (EUR/NGN/GHS) — every payment against such an invoice is summed raw regardless of its own `currency`, exactly the degraded, no-pivot-attempted behavior the pre-this-REQ `getInvTotalPaid()` always used — demonstrated by saving, then deleting, **two separate** payments against a EUR invoice, one of them a pre-existing legacy record (no stored `currency`, defaults to `inv.cur` per B1) and one newly recorded (explicitly `inv.cur` per AC-2a — both therefore the same value, `'EUR'`, not two different ones), confirming `inv.dep`/`inv.status` reflect the correct combined raw sum at every step, never a silently mis-pivoted or mis-summed number. This is the path round 3 found completely untested by AC-3/AC-3a/AC-6 in an earlier draft (where `savePayment()`/`deletePayment()` had no internal currency gate at all) and round 5 found still under-tested by round 4's own first pass at this AC (which only exercised two *new* payments, missing the legacy-vs-new combination that round 4's original, since-superseded fix would have gotten wrong).
- **AC-4.** `getInvEffectiveDepInfo(inv)` returns `'legacy-no-records'` (raw `inv.dep`) when zero payments exist, `'legacy-unsupported-currency'` (raw `inv.dep`) when the invoice's currency isn't in `PO_DEP_RECONCILE_CURS` (e.g. EUR/NGN/GHS) even though payment records exist, and `'ledger'` (the reconciled native total) otherwise — all three cases tested.
- **AC-5.** `cInv()`, `editInv()`, `renderStatement()`, `prevStmtPdf()`, `saveCN()`'s `linkedInv.calc_balanceDue` computation, and `renderPaymentsTab()`'s own top summary box (requirements-gate round 6 — a sixth site, independently found, previously undisclosed) all read the invoice's paid-total figure via `getInvEffectiveDepInfo(inv).value`; `savePayment()`/`deletePayment()` call `getInvTotalPaidNative(inv)` directly, relying on that function's own internal currency gate (AC-3b) *and* on every payment against an unsupported-currency invoice genuinely sharing one currency value, `inv.cur` itself (AC-2a) rather than either alone (corrected per requirements-gate round 2 — an earlier draft of this AC left all five sites' choice of function ambiguous, and the underlying REQ text briefly specified the wrong one for the three round-1-B3-added sites; further corrected per round 3 — the direct-call exception for `savePayment()`/`deletePayment()` is only safe because `getInvTotalPaidNative()` itself is now currency-gated; further corrected per round 4 — that gate alone is only safe because payments against such an invoice can't disagree on currency; further corrected per round 5 — round 4's own first fix locked new payments to an arbitrary *different* currency than `inv.cur`, which still disagreed with a legacy record on the same invoice; AC-2a now sets `inv.cur` itself, the only value that's true by construction across legacy and new records alike). No remaining raw, currency-blind `DB.payments` sum anywhere in the codebase, no remaining silent-mis-pivot path, and no remaining silent-mis-sum path for an unsupported-currency invoice.
- **AC-6.** Deleting a payment that had pushed an invoice to `Paid` or `Partially Paid` correctly re-derives `inv.status` (down to `Partially Paid`, or all the way back to `Sent` if the deleted payment was the only one) — demonstrated for both cases, on a supported-currency invoice; deleting a payment on an invoice in `Draft`, `Pro-forma`, or `Cancelled` status leaves `inv.status` completely untouched.
- **AC-7.** The FPM-funded-deposit auto-recovery block inside `savePayment()` (`index.html:13059-13083`) is demonstrated unaffected by every change in this REQ — same trigger condition (`prevStatus !== 'Paid' → 'Paid'`), same Cloud Data branch, verified by a regression test that predates this REQ still passing unmodified.
- **AC-8.** `renderPaymentsTab()` shows a Purpose column for every payment row; shows Currency/GBP-equivalent columns only when at least one row's *resolved effective currency* (`pm.currency||inv.cur`) differs from the invoice's own, matching §2e exactly; on a EUR/NGN/GHS invoice, that column pair does not appear even after recording a payment (since every payment's resolved currency is `inv.cur` itself, never differing — requirements-gate round 5, demonstrating that the fix in AC-2a genuinely prevents the misleading-GBP-equivalent regression round 4's now-superseded design would have caused here).
- **AC-8a (requirements-gate round 6 — blocking, new).** On a *supported*-currency invoice (e.g. USD) with one pre-existing legacy payment (no `currency`/`rateLock` at all) and one newly-recorded genuinely cross-currency payment (`currency:'GBP'`, with a `rateLock`): the table renders without error; the Amount column shows the legacy row in USD and the cross-currency row in GBP (its own resolved currency, not the table-wide one — §2e item 2); the Currency/GBP-equivalent column pair appears (since the GBP row's resolved currency differs from the invoice's own); the legacy row's GBP-equivalent cell shows a live `toGBP()`-computed value, not a crash and not a bare `0`; the cross-currency row's GBP-equivalent cell shows its own locked `rateLock.gbpEquiv`, not today's live rate.
- **AC-9.** `acctPmtCSV`'s and `acctFACSV`'s existing "Currency" column reads `pm.currency` (falling back to `inv.cur` only for a currency-less legacy record), both gain a "Purpose" column, `acctPmtJSON`'s unmodified pass-through already carries both new fields with no code change (corrected per requirements-gate round 1, A2), and `_aiExecTool('get_payments')` includes `purpose`/`currency` in its own field list (corrected per requirements-gate round 3 — no Supplier Payment equivalent of any of these three exists to "match," so this AC verifies each field is present rather than comparing against a nonexistent counterpart).
- **AC-10.** Full pre-existing-test-suite audit: every direct test-suite call site of `savePayment()`/`deletePayment()`/`getInvTotalPaid()` (the function this REQ removes, along with every one of the six call sites named across §2c-c and §2c-e — corrected per requirements-gate round 6, which found the sixth, inside `renderPaymentsTab()` itself) traced and either updated to the new `getInvTotalPaidNative()`/`getInvEffectiveDepInfo()` names or confirmed unaffected.
