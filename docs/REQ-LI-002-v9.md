# REQ-LI-002 — Supplier-linked Line Item catalogue: stop silent data loss on quick-add, auto-queue catalogue promotion on Quote acceptance, and fix the picker/library UX

**Status:** v9 — revises v8 after independent requirements-gate review round 8 (eighth confirmatory): **CONDITIONAL PASS**, 2 new blocking + 0 new advisory, both personally re-verified against live code before being accepted (§9h). Round 7's citation corrections and both advisory fixes (the intra-loop dedup clarification, the restore-dialog disclosure) were all independently re-confirmed accurate. Both new blocking findings hit v8's own newest mechanism, `_liApproveCtx` (LI-002f), and both are the same bug class this REQ has already demonstrated it knows about: (1) v8 specified the "mark `'approved'`" step at a single insertion point in `saveLI()`, but `saveLI()` has the identical two-branch-with-early-return shape `delLI()` already needed LI-002h corrected for (round 4) — its Cloud Data branch returns at `index.html:7986`, before ever reaching the local branch's code the single insertion point was placed in, so any operator who has migrated Line Items to Cloud Data would get candidates stuck `'pending'` forever with a false "success" toast; (2) `_liApproveCtx`, set before calling `openLI()`/`editLI()`, could leak across an unrelated, reachable `openLI()` call — the AI Assistant's `create_line_item` action opens the same `ov-li` modal without touching `_liApproveCtx`, and its chat overlay isn't modal-exclusive with `ov-li` (the AI FAB sits at a higher z-index than any `.ov` overlay) — so an abandoned Approve flow followed by an unrelated AI-driven Line Item creation could falsely mark the original candidate `'approved'` with no real review, violating Decision 2. **Both fixed outright:** (1) duplicates the approved-marking step into both of `saveLI()`'s branches, mirroring LI-002h's own established dual-branch pattern exactly; new AC-9c. (2) inverts the ordering — `openLI()`/`editLI()` now clear `_liApproveCtx` as their first statement, and Approve sets it *after* calling them (the same ordering already used for the `lf-cur` currency fix, for the identical reason); new AC-9d.
**Type:** Entity-relationship + workflow feature, phased. Extends Invoice line items (`cIL`), `quickAddLine()`, `rILT()`, the Invoice form; extends `saveQte()`, `delQte()`, and `delLI()`; adds a new local-only top-level entity `DB.liPending[]` (fully wired per this codebase's own new-entity checklist — not a lightweight Settings field) and its UI; extends `openPicker()` and `rLI()`. No schema change to `DB.li` itself. No Supabase migration.

## 0. How this REQ came to be scoped this way

Operator asked, mid-conversation about an unrelated Shipment↔Invoice gap, to review the Line Items (product catalogue) feature for the same class of problem, and stated the governing principle directly: entities in this app should retain real, auditable relationships, not loosely-coupled text references, and the data model should be robust and scalable as the business grows. Direct code read found three concrete gaps (§1.1). The operator then ran this through this project's LLM Council (`docs/councils/README.md`) before deciding scope; the council verdict (reproduced in this session's transcript) was: fix Line Items as scoped, sequenced work now, don't block on a full app-wide review, but close the actively-destructive quick-add gap first, before anything else. The operator confirmed "proceed based on the feedback" and resolved three further scoping questions (§1.2) before v1 was drafted.

## 1. Business context

### 1.1 What exists today (check-first)

- **Gap 1 — nothing in the live quoting/ordering pipeline ever touches the catalogue.** Every `DB.li.push(...)` call site: `saveLI()` (`index.html:7948-7992`, entirely DOM-form-coupled), CSV import (`index.html:10929`, `index.html:11252`), and the one-time demo seed (`index.html:5584`). Nothing else.
- **Gap 2 — Invoice quick-add discards real pricing data and has no supplier field at all.** `quickAddLine()` (`index.html:8173-8194`) builds `cIL.push({ rid:uid(), lid:'', desc:desc, uom:uom, qty:qty, up:up, unitCost:uc, lineType:lt })` — no `supId` key anywhere. The quick-add form (`index.html:1202-1207`) has no supplier selector. `rILT()` (`index.html:8215-8254`) has no supplier column. The only existing gate, `invLineHasCostBasis(li)` (`index.html:8169-8172`), says nothing about supplier attribution. `vInv()` already has a save-time backstop reusing this same helper (`index.html:10672-10679`, confirmed by direct read) — the precedent this REQ's new supplier check (LI-002b) sits alongside.
- **Gap 3 — the "Import from Library" picker (`openPicker()`, `index.html:8255-8266`) has no search and no grouping**, unlike the main Line Items tab (`rLI()`, `index.html:7874-7910`), which already has `li-q`/`li-sf` (`index.html:291-292`) — just not visual grouping.
- **Line Items already require a supplier** (`vLI()`, `index.html:10611-10628`).
- **The CSV importer's existing Line Item match logic is the precedent to reuse** (`index.html:10915-10929`): match by `sku && supId` if a SKU is present, else by `desc.toLowerCase() === existing.desc.toLowerCase() && supId === existing.supId`. Quote lines never carry a `sku` (confirmed — `cQL`'s line shape built in `saveQte()`, `index.html:14202-14222`, has no `sku` key), so the promotion matcher (LI-002d) always uses the desc+supId fallback branch.
- **`saveQte()`'s real persistence sequence, read in full, changes where promotion-queueing can safely be inserted (round-1 finding 1 — corrected below).** `qt.id` is only the client-generated placeholder (`index.html:14252`, `EI.qt || uid()`) until the Cloud Data branch reassigns it to the real Supabase id (`index.html:14299`, `qt.id = qtResult.data.id;`) — and that branch can return early without ever reaching that line, on a cancelled login (`index.html:14280`) or a failed insert/update (`index.html:14298`). The existing code already solves exactly this problem for its own post-persist side effects: Contact-status conversion and Order-Request-stage advancement (`index.html:14311-14335`) are placed *after* both persistence branches complete, specifically so they use the real, finalized `qt.id`/`qt.num` and never run at all if the save failed or was cancelled — confirmed this is deliberate, not incidental, by the existing test proving the Supabase-assigned id (not the placeholder) is what gets used downstream (`tests/run.js:9487-9507`). **LI-002d's insertion point is corrected to the same place: after `index.html:14335`, as one more post-persist side effect, never before.**
- **`saveQte()`'s existing versioning loop already computes the exact per-line sell price this REQ needs — reuse it, don't recompute it (round-1 finding 2 — corrected below).** `index.html:14233-14235`: `var calcR = lineCalcs[i]; var effM = qteEffectiveMargin(l, markup); var sellP = +(calcR.landed * (1 + effM/100)).toFixed(2);` — `calcR.landed` already includes freight, DG surcharge, insurance, and duty (`cQteLine()`, `index.html:13823-13844`), not just raw cost. v1's formula (`cost * (1 + qteEffectiveMargin(line, quoteMarkup)/100)`) dropped all four of those and also referenced a variable, `quoteMarkup`, that doesn't exist in `saveQte()`'s scope — the real local variable (`index.html:14227`) is named `markup`. **LI-002d now captures the already-computed `sellP` per line (keyed by `rid`) during this existing loop and reuses it verbatim as `suggestedPrice` — no new formula, no risk of it diverging from what the Quote itself actually quoted.**
- **Quote currency and Line Item currency are independently selectable, and `openLI()` always resets to USD (round-1 finding 3 — corrected below).** `qf-cur` (`index.html:2773`-adjacent) offers USD/GBP/EUR/BBD; `lf-cur` (`index.html:1139`) offers USD/GBP/EUR/BBD/NGN/GHS — a superset, so every Quote currency is always a valid Line Item currency, but `openLI()` (`index.html:7930-7935`) unconditionally sets `G('lf-cur').value='USD'` regardless of context. A candidate sourced from a non-USD Quote, approved via `openLI()` unmodified, would silently mistag the catalogue record's currency.
- **This codebase's own documented convention for adding a new top-level entity, and v1's Decision 5 understated it (round-1 finding 5 — corrected below).** `CLAUDE.md`'s "Key coding conventions" section: "Adding a new top-level entity requires entries in: `K`, `DB`, `EI`, `saveAll`, `showV fns`, `renderAll`, `expAll snap`, `doImport entities`." Confirmed by direct read that today none of `K` (`index.html:3020`), `DB` (`index.html:3033`), `saveAll` (the `const saveAll = () => {...}` arrow function at `index.html:4335`, listing 12 `sv(K.x,...)` calls), `expAll()`'s export snapshot (`index.html:13072-13097`), or `doImport()`'s restore logic (`index.html:13107-13162` — round-6 finding, missed in every gap analysis through v6) have any `liPending`/`lip` entry — and `tests/run.js`'s `resetDB()` (`tests/run.js:211-213`) has no `liPending: []` either. **v1's Decision 5 cited `SS.webhookRules[]` as precedent for "no extra wiring needed," but that field lives inside the already-wired `SS` settings object — a lighter-weight category than a genuine new top-level `DB.*` array with its own growing record set and resolved/unresolved lifecycle, which `DB.events[]` (an append-and-reference log, never Cloud-Data-synced either) is the more accurate precedent for.** This REQ now specifies the full wiring (LI-002e), including the restore side that v1 through v6 all omitted from the checklist walk-through despite quoting "`doImport entities`" verbatim as one of the eight required items.
- **Deleting a Quote has no cascade awareness of anything queued from it (round-1 advisory 1).** `delQte()` (`index.html:14341-14368`) removes the Quote and reverts any converted Contact's status, but nothing else — a pending promotion candidate referencing a since-deleted `quoteId` would otherwise display against a dangling reference with no indication the source is gone.

### 1.2 Design decisions (resolved with the operator before drafting further)

**Decision 1 (operator-selected) — Quick-add's new supplier requirement applies to Product lines only.** Unchanged from v1.

**Decision 2 (operator-selected) — Catalogue promotion from a Quote fires on acceptance, and is review-gated, never silently automatic.** Unchanged from v1.

**Decision 3 (operator-selected) — Forward-only; no historical backfill.** Unchanged from v1.

**Decision 4 (this REQ's own, revised) — The suggested catalogue price on promotion is the exact, already-computed per-line Quote sell price (`sellP`), not a recomputed formula.** Corrected per round-1 finding 2 above — see §1.1. This is a *stronger* guarantee than v1's own stated intent ("a number the Quote already stood behind"): v1's formula approximated that number incorrectly; v2 reuses the literal value.

**Decision 5 (this REQ's own, revised) — `DB.liPending[]` is a fully-wired local-only top-level entity, not Cloud-Data-synced, and not modeled on `SS.webhookRules[]`.** Corrected per round-1 finding 5 above. "Not Cloud-Data-synced" (the genuinely load-bearing part of the original decision — nothing in this REQ's scope demands this queue survive a device switch mid-review) stands; the implied "therefore minimal wiring" does not, and is retracted. Full wiring is specified in LI-002e.

**Decision 6 (this REQ's own, disclosed, new in v2) — Candidate currency is captured and threaded through the Approve flow explicitly.** Per round-1 finding 3 — see LI-002e/LI-002f.

**Decision 7 (this REQ's own, disclosed, new in v2) — Queueing a `'new'` candidate checks already-pending candidates too, not just the live catalogue, to prevent duplicate-candidate creation when two Quotes for the same not-yet-catalogued desc+supId are both accepted before either is reviewed.** Per round-1 finding 4 — see LI-002d.

### 1.3 What this REQ deliberately does NOT do

- Does not change the `DB.li` record shape at all — no new fields on Line Item itself, no Supabase migration.
- Does not make quick-add require a supplier for Pass-through or Charge lines (Decision 1).
- Does not auto-write anything to the catalogue without an explicit operator approval action (Decision 2).
- Does not retroactively backfill supplier attribution on any existing invoice's quick-add lines (Decision 3).
- Does not refactor `saveLI()` into a parameterized, non-DOM function — the promotion-approval flow works by pre-filling the existing form instead, specifically to avoid introducing a second, parallel Cloud-Data-aware persistence path (same reasoning as v1, unchanged).
- Does not add promotion-on-acceptance for Purchase Orders — PO lines already source from an Accepted Quote's own lines, so a second trigger at PO-conversion time would just re-queue the same data with no new information (unchanged from v1).
- Does not touch the Load Calculator, container profiles, or any warehousing concept.
- Does not merge/link multiple pending candidates that happen to describe the same real item across different Quotes beyond the simple duplicate-prevention in Decision 7 — if a third, later Quote also targets the same not-yet-reviewed desc+supId, it is likewise skipped (not merged, not tracked as "3 sources"); the first-queued candidate is still the only one surfaced, and approving it is unaffected by how many Quotes would have produced the same suggestion. Tracking multiple source Quotes per candidate is a disclosed, deliberate non-goal — it would add real complexity for a case (the exact same unreviewed item quoted three times before anyone looks at the queue) that isn't the common path this REQ is built for.

### LI-002d — `saveQte()` queues eligible lines for catalogue review, after persistence completes, using the real sell price, with duplicate-candidate protection
**Insertion point (corrected — round-1 finding 1):** immediately after `index.html:14335` (after both the Cloud Data and local persistence branches, and after the existing Contact/Order-Request post-persist side effects), gated on the `isAccepted && !wasAccepted` booleans already computed earlier (`index.html:14249-14250` — still valid references, since persistence doesn't change them). Placed here, the logic automatically inherits the same correctness the existing Contact/Order-Request side effects already have: it never runs if the save failed or was cancelled (both early-return paths exit before this point), and it always has the real, finalized `qt.id`/`qt.num`/`qt.currency`.

**Per-line sell price (corrected — round-1 finding 2):** inside the existing versioning loop (`index.html:14229-14241`), capture `sellP` into a `rid`-keyed map (e.g. `var sellPByRid = {}; ...; sellPByRid[l.rid] = sellP;` added to the loop body) rather than letting it go out of scope — the promotion-queueing logic reads from this map, never recomputing it.

**Matching and queueing, for each line with a non-blank `supId`:**
1. Resolve a catalogue match using the CSV importer's own desc+supId fallback (`index.html:10915-10929`) against live `DB.li` — same comparison, exactly: `desc` compared case-insensitively (`.toLowerCase()` both sides), `supId` compared exactly.
2. Match found, cost and `sellPByRid[l.rid]` both already agree with the existing record → nothing queued.
3. Match found, either differs → **(corrected — round-2 finding, closes new blocking finding on `'update'` dedup)** check `DB.liPending` for an existing `status:'pending'`, `kind:'update'` entry with the same `matchedLiId`; if one already exists, queue nothing (a second proposed update to the same not-yet-reviewed record would only leave the review banner showing two competing, increasingly stale proposals — resolving the first is always the more current one in any ambiguous case); otherwise queue an `'update'` candidate referencing the matched id.
4. No match in `DB.li` → check `DB.liPending` for an existing `status:'pending'`, `kind:'new'` entry with the same `desc`+`supId`, **using the identical case-insensitive-desc/exact-supId comparison as step 1** (round-2 finding — v2 left this comparison unspecified, risking a differently-cased duplicate slipping past the exact check this REQ exists to add); if one already exists, queue nothing; otherwise queue a `'new'` candidate.
Lines with a blank `supId` are skipped entirely.

**Clarified — round-7 finding: the per-line loop processes lines one at a time against the live, currently-mutating `DB.liPending`, not a snapshot taken before the loop starts.** Steps 3/4's dup-check must see any candidate a *prior line in this same `saveQte()` call* already queued, not just candidates that existed before this Quote's acceptance was processed — i.e. each line's check and (if it queues) its `DB.liPending.push(...)` both happen before the next line's check runs, exactly as if `DB.liPending` were checked and mutated line-by-line in the same forward pass rather than batched. Without this, a single Quote with two lines sharing the same new desc+supId (or two lines proposing an update to the same `matchedLiId`) could queue two competing candidates from its own one acceptance — the same duplication this REQ's cross-Quote dedup (AC-8b/8c/8d) already exists to prevent, just within one Quote instead of across two. New AC-8e.

**Disclosed non-goal (new in v3, closes round-2 advisory 1): a dismissed candidate is never automatically re-queued, even for the same Quote.** Because the trigger is the genuine one-time `isAccepted && !wasAccepted` transition (AC-7), a Quote cannot normally re-fire queueing for its own lines without first leaving and re-entering Accepted status. If the operator dismisses a candidate and later decides the item should be catalogued after all, the existing manual `saveLI()` path remains available — this REQ does not add a "reconsider a dismissed candidate" mechanism, the same deliberate scope boundary Decision 7 already draws around multi-source tracking. A *different* Quote later targeting the same desc+supId for the first time is unaffected and queues normally (the dup-check in steps 3/4 only ever blocks on still-`'pending'` entries, never on `'dismissed'` ones).

**Disclosed non-goal (new in v4, closes round-3 advisory 1): a pending candidate is never re-validated against the live catalogue between queue time and approval time.** Two related races are accepted, not built around: (a) while a `'new'` candidate is `'pending'`, an operator could independently add the identical desc+supId to the catalogue through the ordinary `saveLI()` form (`vLI()`, `index.html:10611-10628`, has no duplicate-desc+supId check of its own, and this REQ does not add one to it) — approving the stale candidate afterward would then create a second, genuinely duplicate `DB.li` record; (b) while an `'update'` candidate is `'pending'`, the live record it targets could be independently edited via `saveLI()` — approving the candidate afterward applies its queue-time `cost`/`price`/`currency` regardless, silently overwriting that intervening edit. Both are real, narrow races, not eliminated by Decision 2's human-review gate alone (the operator sees the queued numbers, but nothing in the UI tells them the live record may have moved since the candidate was queued). Closing them fully would mean either adding a duplicate-check to `vLI()` itself (affecting every manual Line Item save, not just promotion, a materially larger change than this REQ's own scope) or re-resolving each candidate against the live catalogue at the moment Approve is clicked rather than at queue time (a real design option, but one this version doesn't adopt, given both races require two independent operators or sessions acting on the same specific item inside the same short review window — judged acceptable for v1 of this feature, revisit if it proves to matter in practice).

### LI-002f — Review UI: a banner on the Line Items tab, Approve opens the real form pre-filled (now currency-aware), Dismiss just marks it done
Unchanged from v1's core mechanism, plus the currency fix: Approve sets `G('lf-cur').value` from the candidate's own `currency` field *after* calling `openLI()`/`editLI()` (both of which would otherwise leave or reset it to USD) and *before* the operator sees the form, so the pre-filled form never silently shows the wrong currency. Pre-fill desc/supplier/cost/suggested-price for `'new'`; pre-fill only cost/price for `'update'`, leaving every other field as the existing record's own data; Dismiss marks `'dismissed'` with a confirm() naming the candidate's description — all unchanged from v1. **"Mark `'approved'` on successful save" and "`notes` entry naming the source Quote" are given an explicit mechanism below (round-7 finding — every version through v7 stated both as outcomes with no specified way to reach them, and `saveLI()`'s own history-note text is hardcoded with no field to carry a Quote reference through).**

**New in v8, closes round-7 advisory (the missing Approve→`saveLI()` link); corrected in v9 for two round-8 blocking findings (both `saveLI()`'s own two-branch shape and `openLI()`/`editLI()` re-entrancy):** a new session-scoped variable `_liApproveCtx` (`null` when not approving a candidate) carries `{ candidateId: c.id, quoteNum: c.quoteNum }` through the Approve flow. `saveLI()` (`index.html:7948-7991`) is extended at its two existing history-note sites (`index.html:7957`, create; `:7959`, update, both shared by both of `saveLI()`'s branches since they run before the branch split at `:7966`) to check `_liApproveCtx`: if set, the note text becomes `'Initial catalogue price (from Quote ' + _liApproveCtx.quoteNum + ')'` / `'Catalogue price updated (from Quote ' + _liApproveCtx.quoteNum + ')'` instead of the existing hardcoded text; an ordinary manual save (`_liApproveCtx` is `null`) is completely unaffected.

**Round-8 correction 1 — `saveLI()` has the identical two-branch-with-early-return shape as `delLI()` (LI-002h's own precedent), and the approved-marking step must be duplicated in both, not placed once.** `saveLI()`'s Cloud Data branch (`index.html:7966-7987`, gated the same way as `delLI()`'s) calls `closeM('ov-li')` at `:7982` and `return`s at `:7986` — it never reaches the local branch's code at `:7989-7991`. New AC-9c, the Cloud-Data variant of AC-9b.

**Round-8 correction 2 — a stale `_liApproveCtx` could leak across an unrelated `openLI()`/`editLI()` call and cause a false approval with no real review.** `openLI()` is also called from the "+ New Line Item" button (`index.html:293`) and from the AI Assistant's `create_line_item` action (`index.html:12351`, inside `handleAIAction()`) — and the AI Assistant's chat overlay is not modal-exclusive with `ov-li`: the floating `#ai-fab` button (`index.html:2822`) sits at `z-index:900`, above every `.ov` overlay's `z-index:200` (`index.html:99`), and `openAIChat()` (`index.html:12196`) never closes any other open modal. An operator could click Approve (opens `ov-li`, sets `_liApproveCtx`), abandon it without saving or cancelling, use the still-clickable AI FAB to create an unrelated Line Item (which calls `openLI()` on the same modal, repopulating its fields but — in v8's wording — never touching `_liApproveCtx`), and then Save: `saveLI()` would find the stale `_liApproveCtx` still set, write a false "from Quote …" note onto the unrelated record, and silently mark the original, never-actually-reviewed candidate `'approved'` — violating Decision 2's "review-gated, never silently automatic" guarantee. **Fixed by inverting the ordering, not by adding a new clearing site:** `openLI()` and `editLI(id)` (`index.html:7927`, `:7936`) each get `_liApproveCtx = null;` as their first statement — `editLI()`'s before its own `if(!li) return;`, so even a call that fails to find the record still clears stale context — and Approve's own flow is correspondingly changed to set `_liApproveCtx` *after* calling `openLI()`/`editLI()`, at the same point it already sets `lf-cur` after the call for the identical reason (the call itself would otherwise wipe out a value set beforehand). Every entry point into the form — Approve, "+ New Line Item," or the AI Assistant — now starts by clearing any leftover context, and only the Approve path re-establishes it immediately afterward. `closeM(id)`'s existing cancel-path clearing (`index.html:5316`, alongside `if (id === 'ov-inv') _invEditSnapshot = null;`) is unchanged and still closes the ordinary cancel case. New AC-9d covers the re-entrancy scenario directly.

**New in v6, closes round-5 advisory 1 (cross-device staleness on `matchedLiId`):** `DB.liPending` is deliberately not Cloud-synced (Decision 5), while `DB.li` is, once a device has migrated (`refreshLIFromSupabase()`, `index.html:6192-6211`, rebuilds `DB.li` wholesale from Supabase on every refresh). LI-002h's `delLI()` cascade only clears a `DB.liPending` entry on the *same device* that performed the delete — a different device, whose local `DB.liPending` was never touched, can still hold a `'pending'` `'update'` candidate whose `matchedLiId` no longer resolves in its own (now Cloud-refreshed) `DB.li`. Clicking Approve on that candidate today would call `editLI(matchedLiId)` (`index.html:7936`), which silently does `if(!li) return;` with no toast or error — reproducing the exact "stuck candidate, no path to approved, no error shown" failure mode LI-002h exists to prevent, just reached by a different, cross-device path. Approve for a `'kind':'update'` candidate now checks `DB.li.find(function(x){return x.id===c.matchedLiId;})` *before* calling `editLI()`; if not found, it shows `toast("This update suggestion's line item no longer exists — dismissing it.")`, sets that `DB.liPending` entry's `status` to `'dismissed'` with `notes` recording the reason (e.g. `'Auto-dismissed: matched line item was deleted'`), and does not open the form at all. This is a single guard clause reusing data already in memory — no new entity, no cross-device sync, no change to `DB.liPending`'s local-only nature (Decision 5 stands).

### LI-002g — `delQte()` cascades to pending candidates (closes round-1 advisory 1)
`delQte(id)` (`index.html:14341-14368`) additionally removes any `DB.liPending` entries with `quoteId === id` and `status === 'pending'` — `'approved'`/`'dismissed'` entries are left untouched (they already served their review purpose and are kept as resolved history, same as LI-002e's own rule; deleting the source Quote afterward doesn't retroactively make a past review decision meaningless). This prevents the review banner from ever displaying a candidate against a Quote that no longer exists.

**Note (round-6, non-blocking): `quoteId` does not need a cross-device staleness guard the way `matchedLiId` does (LI-002f).** The candidate's `quoteNum` is captured directly on the record at queue time (LI-002e's schema) and is only ever displayed, never re-resolved against a live `DB.qt` lookup the way `matchedLiId` is re-resolved against `DB.li` via `editLI()` — so a Quote deleted on a different device cannot make Approve silently no-op the way a cross-device-deleted Line Item could. ### LI-002h — `delLI()` cascades to pending `'update'` candidates, and warns about them, duplicated in both branches like `delCon()` — not a single insertion point like `delQte()` (corrected — round-4 finding)
`DB.liPending` has two foreign keys, not one: `quoteId` (closed by LI-002g) and `matchedLiId` (set only on `kind:'update'` entries, pointing at the live catalogue record being proposed for an update). `delLI(id)` (`index.html:7993-8018`) has no awareness of either today. **Round-4 correction: `delLI()` is NOT shaped like `delQte()`, and "mirrors LI-002g exactly" was the wrong precedent.** `delQte()`'s two branches (Cloud Data and local) both fall through to shared code afterward (`rQte()`/`toast(...)`), which is why LI-002g's cascade can be a single insertion point placed after the branch. `delLI()`'s Cloud Data branch instead ends in its own unconditional `return` right after `toast('Deleted')` (`index.html:8013`) — it never reaches the local branch's code below it. **The correct, already-existing precedent in this codebase is `delCon()`** (`index.html:14593-14633`), which has the identical two-branch-with-early-return shape and duplicates its own analogous local-only cascade (clearing a deleted Contact's id out of `DB.ord`) verbatim in both branches for exactly this reason — confirmed by the existing test proving that local cascade still fires even when the Contact itself is deleted via the Cloud path (not reproduced here verbatim, but the same shape this REQ's own cascade needs). `delLI(id)`'s `DB.liPending` cascade (`filter` removing entries with `matchedLiId === id && status === 'pending'`, then `sv(K.lip, DB.liPending)`) is placed **once in each branch** — inside the Cloud Data branch, before its `toast('Deleted'); return;`, and inside the local branch, alongside its own `DB.li.filter(...)`/`sv(K.l,...)` line — never as a single point after both, which would silently skip the Cloud Data path entirely.

**Also new in v5: the existing reference-warning dialog is extended to mention a pending candidate, closing round-3's second new advisory.** `delLI()` already counts and names invoice/PO references in its `confirm()` message (`index.html:8000-8004`, the `warns` array).
