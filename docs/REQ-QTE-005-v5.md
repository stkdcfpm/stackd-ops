# REQ-QTE-005 — Customer-facing Quote document (and the internal costing sheet it must stop being confused with)

**Status:** v5 — **requirements-gate round 3: CONDITIONAL PASS, no blocking findings** (condition: the currency confirmation below). v5 folds in its four should-fix text corrections and six tidy-ups (§12); earlier maps in §10 and §11. **One operator confirmation is still outstanding: the currency (§4 REQ-QTE5-005) — the SPEC must not start until it arrives.**
**Type:** Feature + safety fix. **Phase 1 needs no schema change** (renders from existing quote fields). Phase 2 (stored issued copies) needs one additive Supabase column and is specified separately in §7 so Phase 1 can ship first.
**Operator decisions (2026-11-28):** per-line selling price; the three existing overhead lines (origin / destination / admin) are the separate charge lines — **enough as is**, free-form charge lines are not needed now; **currency: **OUTSTANDING** (the answer was cut off after "use" — working assumption USD, not a decision); a one-line **price basis** is printed; catalogue descriptions are clean of supplier references (the supplier-name safeguard in REQ-QTE5-006 stays as a backstop).
**Why now:** the operator needs to send a real container-load quote to a buyer and the app has no buyer-facing quote document.

---

## 1. The finding that triggered this

`prevQteDoc()` (`index.html:16155`, opened by the Quote modal's Preview button `3037`) is an **internal costing sheet**. Every line prints the **supplier name, cost, freight, insurance, duty and landed cost** (per-line cells `index.html:16159-16168`, table header row `16183`; the page header is `16177`), the overhead charges are listed, and only the grand **Sell Price** is shown — in **both USD and GBP** (`index.html:16190-16191`) — followed by the quote **Notes** whenever present (`16193`). A buyer who receives it can compute FPM's margin (Sell − Landed − overhead) and can see exactly which factory to contact directly. It is not labelled internal. There is no per-line selling price, no payment terms, no bank details and no address header (its header prints `AS.name · AS.email` only, `index.html:16177`). Nothing is stored: the document is built in memory and opened in a new tab, so there is no record of what a buyer was actually sent (the invoice documents behave the same way, by design — `docs/user-guide.md` Invoices section).

There is also **no Quote → Invoice conversion** (the schema-only `sourceQuoteId` was removed in v2.9.58), so today the only buyer-facing document in the app is an invoice at Pro-forma status, with every unit price typed by hand.

## 2. How the pricing maths constrains the document (must be understood before design)

`cQteLine()` (`index.html:14930`) builds **landed = cost + freight + insurance + duty (+ DG surcharge)** per line, and the per-line selling price is **landed × (1 + markup%)** (`qteSellTotals()` `14971`); the three overhead components (origin, destination, FPM admin) are added **at cost, never marked up**. So:

- A per-line selling price **already contains** the international freight, insurance and destination duty for that line. A customer document that *also* listed "freight" as a separate line would double-charge unless the lines were re-split — which changes the engine's presentation and **exposes the markup on freight** (forwarder rates are discoverable, so a buyer can compare the freight line to a market quote). That is the main way a "separate freight line" leaks margin.
- The **only** charges that are genuinely separate in the maths today are the three overhead components. "Local freight and taxes are known" maps onto the existing **Destination Charges** (and, if used, Origin Charges / Admin) per-quote overrides (`REQ/SPEC-QTE-002`).

## 3. Decision on charge lines (operator confirmed: enough as is)

The customer document prints, after the product lines, **only the overhead components that are non-zero**, each as its own line with a buyer-facing label: *Origin charges*, *Destination charges (local freight & taxes)*, *Handling & admin*. International freight, insurance and duty stay **inside the per-line selling prices** and are never itemised. Free-form extra charge lines (any description, any amount) are Phase 2 because they need a new stored field.

## 4. Requirements (Phase 1)

**REQ-QTE5-001 — Separate entry points, honest names.** There are **two** places that open the internal sheet and both are changed: the Quote modal's Preview button (`#qt-prev-btn`, `index.html:3037`, shown only for saved quotes, hidden for a new one `15052`/`15083`) and the Quote **list row** icon button (`index.html:15016`, calls `prevQte()`). The modal button is relabelled **"Internal costing sheet"**; the list-row icon gets the tooltip "Internal costing sheet (not for the client)" and a second icon/label **"Customer quote"** is added beside it. The modal gains a **"Customer quote"** button with **the same visibility rule as Preview** (saved quotes only). The internal sheet's `<title>` and a print-visible banner read **"INTERNAL — contains supplier and cost information. Do not send to the client."**

**REQ-QTE5-002 — Source of the document: the SAVED record, never the live form.** `prevQteId()` renders the saved `DB.qt` record (`index.html:16147`), and so does the customer document. The Quote modal has no dirty tracking today (`openQte()` `15033` and `editQte()` `15061` just set fields), so this REQ defines one: at the end of `openQte()`/`editQte()` the modal captures a **form snapshot** string = JSON of the *normalised* values — header fields (number, client, date, valid-until, currency, freight mode, markup as number-or-blank, the four override fields as trimmed strings, status, trimmed notes, approved-by, approval note) and, per line (read through the same `qlFld()` source `saveQte()` uses): `supId`, trimmed `desc`, `qty`/`cost`/`cbm`/`dutyPct` as numbers rounded to 6 dp, `uom`, `dg` as a boolean, `markup`/`insRate` as number-or-blank, and — from `cQL`, not the DOM — `lid`, `costManual`, `cbmManual`. The transient version note is excluded. **Scope of the guard:** it applies **only when the Quote modal `#ov-qt` is open for the clicked quote** (the modal's own *Customer quote* button); the stored snapshot is **discarded whenever the modal closes** (cancel, save, X), so a list-row click — where the modal is closed — never compares and never prompts: it goes straight to the pre-send dialog for the saved record. Within the modal, *Customer quote* compares a fresh snapshot to the stored one; if they differ it shows: "You have unsaved changes. The customer quote shows the saved version — Save first?" with **Save and continue** / **Continue with saved version** / **Cancel**. The record is identified by `EI.qt` **captured at click time** (the button exists only for saved quotes). **Save and continue** calls `saveQte()`; success is detected by the modal having closed (`saveQte()` closes `#ov-qt` only after a completed save — `vQte()` failure and a cancelled Cloud Data login both return early with the modal open), and only then is the document dialog opened for the captured id; on any failure **no document opens** and the operator stays in the modal. **Accepted limitation (stated, not hidden):** if the operator clicks Cancel in the modal while `saveQte()` is still awaiting a Cloud Data call, the modal closes without a completed save and the closed-modal signal reads as success; the document is then built from whatever the record holds, and the dialog's drift warning and printed Total remain visible. **Save and continue is the operator's own explicit save** — it may create price-history versions and queue catalogue promotions exactly as the normal Save button does; REQ-QTE5-008's "no side effect" applies to *generating* the document only.

**REQ-QTE5-003 — Customer document contents.** Header from `buildPdfHeader()` (`11003`) — logo/name, address, branding email/phone, reg/VAT — using exactly what `buildPdfHeader()` prints (**no `AS.email` fallback** — `rCfg()` pre-fills a personal address and a fallback could print it on a buyer document unnoticed; the pre-send dialog shows which contact details will print instead, REQ-QTE5-006); `buildPdfHeader()` itself is **not modified** (it is shared with invoices and purchase orders); title **QUOTATION**; quote number, date, **Valid until** (only when set), client, and `Shipping: <freight mode>` (LCL / FCL 20GP / FCL 40HQ) under the client line (open §8 b); a product table with exactly: **Description, Qty, UOM, Unit price, Line total**; the non-zero overhead lines (§3); a single **Total**; **Price basis** (REQ-QTE5-010); **Notes** (only when included, REQ-QTE5-006) under the heading "Notes" immediately after the Total and Price basis; **Terms & conditions** from the new `AS.quoteTerms` setting (REQ-QTE5-010 — **not** `AS.terms`, which holds invoice payment wording such as "Payment due within 30 days of invoice date…" that does not belong on a quotation, `index.html:3282`/`13646`); bank details (`fmtBankHtml(AS.bank)`, `11038`) when configured, otherwise nothing; the company footer (`buildPdfFooter()` `11020`); a page footer with the quote number and "Page x of y" (invoice print-CSS technique).

**REQ-QTE5-004 — Prices the buyer can reconcile.** Per line, with the **Qty used = `+l.qty > 0 ? +l.qty : 1`** (this normalised value is also the **Qty printed**, trailing zeros trimmed, so Qty and Unit price always agree): **selling price** S = `landed × (1 + effective markup%)` from the **live recomputation `cQte(q)`** (`index.html:14981`), not the stored `calc_*` fields (fixed at save time, `15617`). **Unit price** U = `Number((S ÷ Qty).toFixed(4))`, displayed with trailing zeros trimmed to a minimum of 2 decimals (12.7 → `12.70`, 12.7143 → `12.7143`); **Line total** = `round2(U × Qty)` where `round2(x) = Math.round(x × 100) / 100` (half-up on binary floats; accepted). Overhead (charge) lines are `round2` of the engine's overhead components and the **Total is the sum of the printed line totals and printed charge lines**. A buyer multiplying the printed Unit price by the printed Qty therefore gets the printed Line total to ±0.005. **Stated bound:** the printed Total differs from the engine's unrounded sell total (`qteSellTotals()` `14971`) by at most `Σ over product lines (0.00005 × Qty + 0.005) + 0.005 × (number of printed charge lines)` — about 25 cents on a 5,000-unit line; the difference is neither printed nor written back to the record.

**REQ-QTE5-005 — Currency: USD (operator to re-confirm).** The document is issued in USD, every amount carries a `USD` label, and no GBP total is printed. **The operator's answer was cut off after "use"** — read as USD; it must be confirmed before the SPEC starts (Barbados trade makes BBD or GBP plausible, and neither is supported). **The quote Currency field is not reliable** (`QTE-GAP-004`, `docs/known-gaps.md`): an Order-Request-converted quote fills line costs in the quote's own currency (`ordConvertToQuote()`, `index.html:3703-3712`) while the engine treats the Cost column as USD, so a non-USD-labelled quote may hold non-USD numbers. Therefore: **if the quote Currency is not USD the pre-send dialog (REQ-QTE5-006) shows an acknowledged warning** "This quote's currency is X. The engine prices in USD, so these amounts may not be USD — check the line costs before sending." — Generate stays disabled until its tick-box is ticked, with **Cancel** always available; nothing is silently relabelled.

**REQ-QTE5-006 — One pre-send dialog, not a chain of confirms.** Clicking *Customer quote* (after REQ-QTE5-002) opens an in-app modal (`#ov-qdoc`, placed after `#ov-qt` — all `.ov` share one z-index) listing, for the saved quote: **(1) the price-basis text** (pre-filled from `AS.priceBasis`, editable for this document only — REQ-QTE5-010); **(2) an "Include quote Notes" checkbox**, shown only when the quote has Notes, **unchecked by default** (Notes have always been internal-by-habit); **(3) a warnings list** (terminology used throughout: a **warning** is listed and does not stop Generate; an **acknowledged warning** additionally needs its tick-box ticked before Generate is enabled — only the currency warning and the live-vs-saved-total warning are acknowledged warnings; a **block** disables Generate and is used only for a Total of 0), each item naming the offending line: a line description mentioning a Supplier's name (case-insensitive substring, `DB.sup` names of ≥ 3 characters) or the SKU of its linked catalogue item (SKUs of ≥ 4 characters only, to avoid false positives; a linked `lid` whose catalogue record no longer exists is skipped); no validity date ("open-ended"); a line with no cost basis (cost 0); a line with a selling price of 0; the currency warning (REQ-QTE5-005, acknowledged); quote status Declined or Expired; a live total that differs from the saved `calc_sellUSD` by more than 0.01 (**skipped — no warning — when the saved `calc_sellUSD` is absent or not a finite number**, as for quotes pulled from Sheets, `FIELD_MAPS.qt` carries no `calc_sellUSD`, or created by the AI) (rates or catalogue changed since saving — shows both figures; acknowledged); the dialog also **shows the Total that will print** (computed by the same function as the document, so the operator sees any difference from the on-screen price before Generating) and **the effective header that will print**, exactly as `buildPdfHeader()` (`11003-11018`) renders it: name = branding name, else `AS.name`, else the hard-coded "FPM International Ltd"; address = branding address, else `AS.addr` (which `rCfg()` defaults to "Brighton, UK", `13644` — shown so the operator sees it before sending); **email and phone print only when the branding email is set** (the phone is concatenated inside the email conditional); reg/VAT as branding holds them. When no email prints the dialog shows the warning "No email or phone will print — set an email in Settings → Company Branding" (a warning, not a block: a quote without a contact method is an operator choice). A quote whose **Total is 0 is a block** (Generate disabled, message shown). Buttons: **Generate** / **Cancel**. Because the document is opened from the Generate click itself, the browser's pop-up rule is satisfied. **If `window.open` returns null** the operator sees "Pop-ups are blocked — allow pop-ups for this page, then click Generate again" and the dialog stays open. The leak check is a **backstop, not a guarantee** (it does not catch abbreviations or brand names); the REQ states this in the user guide.

**REQ-QTE5-007 — No internal content can appear.** The customer document contains **no** supplier name, SKU/catalogue reference, cost, freight, insurance, duty, landed value, markup/margin percentage, DG surcharge amount, per-line version note, line `note`, or price-history data. The only line text printed is the line **Description**. Tested with a sentinel quote: every internal field holds a unique sentinel string, the description holds a distinct *printable* sentinel which **must** appear, and none of the others may.

**REQ-QTE5-008 — No status or data side effect; escaping.** Generating the document changes no record (status, notes, anything) — the operator sets status to Sent themselves; a one-line hint after generation reminds them. Every free-text value is `san()`-escaped; the page title is `<quote number> — Quotation`; the document is an in-memory blob like the other previews.

**REQ-QTE5-009 — Docs and assistant.** `AI_SYSTEM_PROMPT` and `docs/user-guide.md` explain the two documents, the internal-only warning, the charge lines, the dialog and its warnings, that international freight, insurance and import duty are **inside** the line prices, the rounding rule, and that a reprint reflects today's Settings, rates and catalogue until Phase 2 stores issued copies; changelog, three version strings, tracker rows.

**REQ-QTE5-010 — Two new local Settings fields, wired end to end.** `AS.priceBasis` ("Price basis") and `AS.quoteTerms` ("Quote terms & conditions") are new local settings values (stored in `AS`, key `K.as`; never on the quote; no quote schema change). The existing settings save is **not** automatic: `saveCfg()` (`index.html:13747`) rebuilds `AS` from a fixed whitelist of eight fields and **drops any other key**, `rCfg()` (`13641`) loads only those, and restoring a backup replaces `AS` wholesale (`data.company`, `~14202`). Therefore the REQ requires: two inputs in the Settings form, `rCfg()` populating them, `saveCfg()` carrying them, backup/restore carrying them (and an old backup lacking them leaving them blank, never `undefined` text on the document), and tests for each. `AS.priceBasis` is limited to 300 characters with newlines collapsed to single spaces (the dialog edit follows the same rule); `AS.quoteTerms` is limited to 2,000 characters with newlines preserved as line breaks. **Enforcement:** the Settings inputs and the dialog textarea carry `maxlength`; `saveCfg()` and the backup-restore path **silently truncate** an over-long value to the limit (never reject, never store more), and the document builder applies the same truncation as a final guard. Blank `AS.priceBasis` omits the Price-basis line; blank `AS.quoteTerms` omits the Terms section. The placeholder shown in Settings for Price basis describes what the engine actually prices: "Line prices include international freight, insurance and import duty. Origin, destination and handling charges are itemised separately." — **no Incoterm** (the maths are not CIF: insurance is a % of cost+freight, and destination duty is included). The per-document edit in the dialog is not remembered anywhere (no session carry-over) and the Settings value is the only default. GDPR: both fields are business text in local storage and the existing backup JSON; no personal data.

## 7. Phase 2 (separate REQ/SPEC): stored issued copies
`quotes.issued_docs` (nullable `jsonb`, additive migration — all four Cloud Data touchpoints: insert, update, refresh mapping with the bare `!= null` guard, migration function — plus `schema-migration-reviewer`): an **Issue quote** action stores an immutable snapshot (`{n, issuedAt, quoteNum, clientName, lines[{desc, qty, uom, unit, total}], charges[], total, currency, termsText, bankText, headerText, validUntil}`) so a reprint is byte-for-byte what the buyer received regardless of later Settings/catalogue/rate changes; re-issuing increments `n`; the quote status moves to Sent on issue (with confirm); a read-only "Issued copies" list on the quote. GDPR: the snapshot holds the buyer name already on the quote and company/bank text already in Settings; no new external transmission. Further Phase 2 points the gate raised: `saveQte()` rebuilds the quote from a literal (`index.html:~15600`), so `issuedDocs` must be carried forward explicitly on every save; quotes are Sheets-synced (`'qt'` in the sync entity list, `FIELD_MAPS.qt`) — `issued_docs` is **not** mapped and survives a pull via `mergePulledWithLocal()`'s `Object.assign({}, local, pulled)` shape, which the SPEC must cite; backup/restore carries `DB.qt` as-is. **GDPR correction:** for a Cloud-Data-migrated quote the snapshot **is** transmitted to Supabase (buyer name and commercially sensitive pricing) — the same exposure the quote's `lines` already have; an immutable snapshot also cannot be erased through the app (SEC-GAP-022 — no GDPR erasure path on Cloud Data exists today), to be disclosed. Open: size limit per quote; whether to also store the rendered HTML.

## 9. Risks (stated plainly)
- **Per-line selling prices still reveal structure.** A buyer comparing lines can spot inconsistent markups, benchmark against known market prices (these are commodity products), or compare unit prices across quote versions with different quantities (freight is allocated per CBM, so bulky lines carry more freight). Showing fewer, rounder prices or a single total hides more; per-line is the operator's decision.
- A separate freight line (if later added) exposes freight markup — hence §3.
- Reprints are not reproducible until Phase 2.
