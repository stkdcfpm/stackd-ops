**Status:** v4 DRAFT — resolves requirements-gate round 2 (v3: CONDITIONAL PASS, findings 1-7, D6/D7). **D6 still needs the operator's answer** (§8); D7 is changed on the gate's evidence and also needs the operator's confirmation.

**Operator decisions (2026-11-28):** freight at cost (no markup); print the CBM estimate labelled "Freight (estimate)" with a tick; insurance on cost only; existing quotes stay Included; ships after the current container quote (interim workaround meanwhile). **Open:** D6 (`excluded` insurance) and confirmation of D7 (DG surcharge now rides in the freight figure) — see §8.

## 1. Problem (verified against live code)
`cQteLine()` (`index.html:14980`) computes `landed = cost + freight + dgAmt + ins + duty` (`14999`): freight from the line's CBM and the Freight Mode (`14984-14990`), `ins = (cost + freight) × rate` (`14997`), `duty = cost × dutyPct` (`14998`), `dgAmt = QR.dgSurcharge` for a DG line (`14991`). A line's selling price is `landed × (1 + effective markup%)` (`qteSellTotals`, `15021`; `qteCustomerModel`, `16224`), so international freight, and the insurance charged on it, are **always inside every line's price and carry the line's markup**. The customer document has no freight row (`16232-16236`); the three overhead overrides never touch freight.

## 2. Treatment field
`Quote.freightTreatment`: **`'included'`** (default; today's behaviour), **`'separate'`**, **`'excluded'`**. Stored **only for `separate`/`excluded`**; for `included` the key is **omitted** (never stored as `'included'`, never `undefined`) — identical rule in the local record, the form, the Cloud column (`freight_treatment` is `null` for included) and every test. `Quote.freightAmount` (USD, number): present only for `separate` and only when the operator typed a value (a typed `0` is stored); blank = key omitted.

## 3. Engine contract (resolves gate findings 1-3)
**3.1 Signature.** `cQteLine(line, qr, freightMode, totalCBM, quoteInsRateRaw, freightTreatment)` — new 6th parameter; `undefined`/`'included'` = exactly today's arithmetic. **Callers:** `rfqLandedGBP` (`4263`, four arguments) is unchanged and stays on `included` — RFQ landed-cost ranking needs freight; `cQte` (`15036`) passes `qt.freightTreatment`; the three form-driven paths `rQLT` (`15428`), `calcQte` (`15529`) and `saveQte` (`15629`) read the new form field and pass it, so editor, saved record and document cannot disagree. A test enumerates every `cQteLine(` call site and fails if one is added without a decision.
**3.2 `separate` / `excluded` line arithmetic.** `freight` is still computed per line (returned as `freightEst` for display) but **excluded from `landed`**; `ins = cost × insPct/100` (**base is cost only**; the per-line `Ins %` and quote-level `qf-insRate` cascade is unchanged, only the base changes); `duty` unchanged; **`dgAmt` leaves `landed` and belongs to the freight figure (D7, gate round 2)**: it is a carrier-side surcharge, so for `separate` the estimate is `Σ line freight + Σ line dgAmt`, passed through at cost; for `excluded` it is dropped with the rest of freight; a typed amount replaces the whole figure (the operator's forwarder number already includes DG). Landed = `cost + ins + duty`. The per-line return keeps the existing keys: **`.freight` stays the per-line freight estimate (always computed, never zeroed)**, `.dgAmt` stays the per-line DG amount, `.landed` is ex-freight and ex-DG for non-included treatments; new key `.freightTreatment` echoes the normalised treatment. `qteFreightTreatment(v)` normalises `undefined`, `''` and any unknown string to `'included'`; it is the only place the three values are interpreted.
**3.3 Totals.** `cQte()` returns two new fields: `freightEst = Σ (line.freight + line.dgAmt)` and `freightLine` = `0` for `included`/`excluded`; for `separate`, the typed `freightAmount` if present else `freightEst`. `qteSellTotals(lines, lineCalcs, quoteMarkup, overheadTotal, fxGBPUSD, freightLine)` — the new argument is **6th**, default 0, so the three existing callers are unchanged (`included` passes 0). Then: `totalLanded = Σ line landed` (ex-freight for non-included); `quotedTotal = totalLanded + freightLine + overhead`; **`sellUSD = Σ line sell + freightLine + overhead`** (freight is added **unmarked**, like overhead); `sellGBP = sellUSD / fx`. `qteSellTotals()` gains a `freightLine` argument (default 0). `saveQte` stores `calc_totalLanded`, `calc_sellUSD`, `calc_sellGBP` from these, so `qteCustomerModel.engineTotal` (`16238`) and the stored value agree and the drift acknowledgement (`16307`) does not fire falsely. REQ-QTE6 regression: every existing `cQte()` output is pinned for `included`; new fixtures pin `separate` and `excluded`.
**3.4 Worked example** (1 line, cost $10,000, CBM 20 at $100/CBM LCL → freight est $2,000, insurance 0.5%, duty 0, markup 20%, **no DG line**, no overhead; a DG line adds `QR.dgSurcharge` to `included` landed and to the `separate` freight figure instead, never to a separate line price):

| | Included | Separate (amount blank → estimate) | Separate (typed $1,800) | Excluded |
|---|---|---|---|---|
| ins | (10,000+2,000)×0.5% = 60.00 | 10,000×0.5% = 50.00 | 50.00 | 50.00 |
| landed | 12,060.00 | 10,050.00 | 10,050.00 | 10,050.00 |
| line sell (×1.20) | 14,472.00 | 12,060.00 | 12,060.00 | 12,060.00 |
| freightLine | 0 | 2,000.00 (est.) | 1,800.00 | 0 |
| **sellUSD / printed Total** | **14,472.00** | **14,060.00** | **13,860.00** | **12,060.00** |
| quotedTotal | 12,060.00 | 12,050.00 | 11,850.00 | 10,050.00 |

## 4. Requirements
