## 1. Problem (all verified by reproduction on `main`, 2026-11-09)

**D-1 — the modal never opens.** `openAcctExport()` (`index.html:13430`) ends with `openM('ov-acct-exp')` (`index.html:13443`). `openM` is not defined anywhere in the file and that is its only use. `openAcctExport('inv')` and `openAcctExport('pmt')` both throw `ReferenceError: openM is not defined`. Entry points: Invoices tab button (`index.html:315`) and Payments view button (`index.html:15734`). Working report modals use `G('ov-xxx').classList.add('on')` (`index.html:9484`, `:9633`, `:9750`). `closeM` exists (`index.html:5437`), so this is a typo-class miss, not a removed helper.

**D-2 — exporters read a line shape the app never saves.** `acctInvCSV` (`:13314`), `acctXeroCSV` (`:13360`), `acctQBCSV` (`:13383`) and `acctQualityCheck` (`:13416`) iterate `inv.lines` and read `l.cu`/`l.sku`. `saveInv()` writes `inv.lineItems` with `{rid,lid,desc,uom,qty,up,unitCost,lineType[,supId]}` (`index.html:8637`). Reproduced: a two-line real-shape invoice yields 0 data rows in Generic CSV, Xero and QB, and `acctQualityCheck`'s zero-value-line warning never fires. `acctInvJSON` (`:13352`) dumps whole invoices and is unaffected.

**D-3 — no format is pre-selected.** None of the five `name="acct-fmt"` radios is checked (`index.html:1073`-`1077`); Download with nothing ticked shows only a "Select a format" toast. Xero/QB are invoices-only and FreeAgent is payments-only but nothing stops or explains the wrong pairing except a late toast.

**Why tests missed both:** tests exercise the pure formatters with fixtures in the `lines`/`cu` shape (`tests/run.js:1607`-`1727`); nothing calls `openAcctExport` or `doAcctExport`. Same defect class as PO-GAP-005.

## 3. Requirements

**REQ-RPT-003-1 (modal opens).** `openAcctExport(entity)` opens `ov-acct-exp` by adding class `on` (the pattern of the other report modals). No `openM` helper is added. Both entry points open the modal with no console error.

**REQ-RPT-003-2 (default format and entity-aware options).**
- 2.1 Each time the modal opens, Generic CSV is selected, regardless of any earlier choice.
- 2.2 The five radios get ids `acct-fmt-generic-csv`, `acct-fmt-generic-json`, `acct-fmt-xero`, `acct-fmt-qb`, `acct-fmt-fa`. Options that do not apply to the selected entity are disabled (`disabled` property) and their wrapping `<label>` (given id `acct-fmt-label-<value>`) gets a `title` of `Invoices only` / `Payments only` and reduced opacity; the existing label text is unchanged. Xero and QuickBooks are disabled for Payments; FreeAgent for Invoices. The Entity `<select>` gets `onchange="acctExpEntityChanged()"` and EACH of the five radios gets `onchange="acctExpFormatChanged()"`. `acctExpFormatChanged()` only re-evaluates the cancelled-invoices notice (REQ-7.3). `acctExpEntityChanged()` (a) re-evaluates disabled state, (b) falls back to Generic CSV if the checked radio became disabled, (c) recomputes the warnings panel (REQ-7.7) and (d) shows or hides the cancelled-invoices notice (REQ-7.3). `openAcctExport()` calls the same function after setting the entity.
- 2.3 The "Unsupported format for this entity" toast remains as a backstop.
- 2.4 No other redesign of the modal.

**REQ-RPT-003-3 (line shape).** Every invoice exporter and `acctQualityCheck` iterate `inv.lineItems`; they use ONE line-source rule everywhere (REQ-3, 7.5, 8): the invoice's lines are `lineItems` if it is a non-empty array; otherwise the legacy `lines` array if that is a non-empty array (a "legacy-shape" invoice); otherwise the invoice has no lines. An empty `lineItems` therefore does not block the legacy fallback. The unit-cost field read is `unitCost`, falling back to `cu` only for a legacy-shape line. Applies to all four sites in D-2; the writer must grep the whole file for any other invoice-level `inv.lines` consumer and report the result (current result: none outside these four; the remaining `.lines` hits are Order Request, Quote, Purchase Order (the legacy `po.lines` migration, `index.html:3331`-`3339`) and Load Calculator (`_lcResult.lines`, `index.html:13934`) lines).

**REQ-RPT-003-4 (SKU).** SKU is the catalogue SKU when `lid` resolves in `DB.li`. If `lid` is blank or unresolved: a line read from the legacy `lines` array uses its own `sku` whenever the catalogue SKU is unavailable (`lid` unresolved or the catalogue record's `sku` blank); any other line exports an empty SKU. A SKU is never invented. ("Legacy" means only a line taken from the `lines` fallback array; demo-shaped lines are out of scope, see REQ-7.6.)

**REQ-RPT-003-5 (cost basis, Generic CSV).**
- 5.1 For a line taken from `lineItems`, per-line COGS uses the same rule as `cInv()`'s live path (`index.html:5440`): catalogue cost when `lid` resolves (any `lineType`; a blank/absent `lid` never resolves in the exporters, whereas `cInv()`'s `cogsLive` has no blank-`lid` guard, so a line whose `lid` key is absent (`undefined`) or is `''` could match an id-less catalogue record whose `id` is `undefined` or `''` respectively (a phantom record, very unlikely); such a case shows up as a parity mismatch under REQ-8: a test failure for a fixture, a reported item for real data), otherwise the line's `unitCost` (absent counts as 0, as `cogsLive` does). A line taken from the legacy `lines` fallback array uses its `cu` (cInv never reads `lines`/`cu`, so legacy invoices are outside the parity rule, REQ-8). Existing `Gross Profit` = line total minus this COGS; `Tax Amount` and `Line Total` are unchanged.
- 5.2 The Generic CSV gains `Unit Cost (stored on line)` (the line's `unitCost`; for a legacy line its `cu`; written as the raw number when it is a finite number, otherwise empty (so `undefined`, `null` and non-numeric strings are empty); for the REQ-5.3 predicate a `null` key counts as present, but for drift (REQ-8) a `null` is not a number and is not counted) and `Unit Cost (catalogue now)` (the raw catalogue `cost` when `lid` resolves and `cost` is a finite number; empty when `lid` does not resolve or the resolved record's `cost` is absent or non-numeric, in which case `cInv()` and therefore the line COGS use 0). Both new cost columns are written as raw unrounded numbers (no `toFixed`), so drift can be compared exactly; COGS/Gross Profit columns keep `toFixed(2)`. Drift (as defined in REQ-8) is thereby visible per line. Existing columns keep their relative order; the new columns are appended at the end, followed by `Line Type` and `Supplier` (REQ-6).
- 5.3 **Stored-COGS exception predicate (exact):** an invoice is a stored-COGS exception iff `lineItems` is non-empty AND no line has a `lid` that resolves in `DB.li` AND no line has `unitCost !== undefined` (a `null` counts as present, as in `cInv()` at `index.html:5489`-`5490`) AND `+calc_cogs > 0` (`index.html:5492`). For such an invoice `cInv().cogs` is the stored `calc_cogs` while every exported line COGS is `0.00`; it is handled by REQ-8, never silently zeroed.
- 5.4 `iCalc()`, `cInv()`, `calc_cogs` and `repairCalcFields` are not modified.

**REQ-RPT-003-6 (extra columns).** Generic CSV only: `Line Type` (`lineType`, default `product` when absent) and `Supplier` (`line.supId` resolved to a supplier name via `DB.sup`; if the line has no `supId`, OR its `supId` does not resolve in `DB.sup`, the catalogue entry's `supId` (via a resolving `lid`) is tried next; empty if still unresolved). Xero and QuickBooks gain no columns.

**REQ-RPT-003-7 (record selection, D2).**
- 7.1 **Where the filter lives.** One new pure function `acctExportSets()` returns the filtered `{invoices, payments}` and is the single source for `openAcctExport()` and `acctExpEntityChanged()` (warnings), `doAcctExport()` (all formats, including JSON) and the "nothing to export" checks. The formatters (`acctInvCSV`, etc.) stay pure and take already-filtered arrays, so tests can drive them directly and drive the filter through `acctExportSets()`.
- 7.2 **Demo identification.** An invoice or a payment is demo iff its `_demo` flag is truthy OR its immutable `id` is a string that starts with `demo-` (an absent or non-string `id`, as `isPhantomRecord` records have, is simply not demo and must never throw, since `acctExportSets()` runs when the modal opens). The id test is required because `saveInv()` does not carry `_demo` forward on re-save (open INV-GAP-012; `_demo` appears nowhere in `saveInv()`) whereas it preserves `id`; verified that every seeded demo invoice and payment carries both. Payments are classified on their own flag/id only; no payment-to-invoice resolution is added (§4). **Accepted residuals:** (1) a real payment recorded by the operator against a demo invoice gets a `uid()` id and no flag, so it is not filtered and its exported Invoice #/Payee come from the demo invoice (not expected in practice; payment lookups are not changed, §4); (2) a demo record that has been migrated to or refreshed from Cloud Data may lose both markers (REQ-9 forbids Cloud Data changes) and then exports like a real record; the claim "demo data never reaches an export" is therefore scoped to local data.
- 7.3 Cancelled invoices are included in all invoice exports; `Status` is visible in Generic CSV and JSON. Xero and QuickBooks have no status column, so a cancelled invoice would import there as a live receivable; a notice element `acct-exp-cancel-note` in the modal is re-evaluated by both `acctExpEntityChanged()` and `acctExpFormatChanged()` and is shown only when the selected entity is Invoices and the selected format is Xero or QuickBooks, stating that cancelled invoices are included and must be excluded in the accounting package; the same caveat goes in the release note (defined in §6) and user guide.
- 7.4 **Credit notes and goodwill credits** (`type` credit_note/goodwill_credit, or legacy `!type && isCN(num)`): today they yield no line rows in any line-level CSV, and that is preserved by skipping them explicitly in `acctInvCSV`/`acctXeroCSV`/`acctQBCSV`, whether or not a given record carries `lineItems` (one saved through the invoice form can; `saveCN()` writes `lineItems: []`, `index.html:12108`). They still appear in JSON. They are outside the parity rule and are ignored by every `acctQualityCheck` warning.
- 7.5 **Invoices with no lines** (per the REQ-3 line-source rule: no non-empty `lineItems` and no non-empty `lines`; a NEW invoice created by the Invoice CSV imports gets `lineItems: []` plus stored `calc_*` figures, `index.html:11369`, `:11709`; a new invoice pulled from Sheets has the key absent entirely because `FIELD_MAPS.inv` has no `lineItems` field, `index.html:5029`; a re-imported existing invoice keeps its own lines) produce no line rows. A legacy-shape invoice is NOT in this class: it exports through the fallback. This is not silent: `acctQualityCheck` gains a warning "Invoice X: no line items, not included in line-level CSV exports" (not raised for REQ-7.4 records), and the delivery report (defined in REQ-8) states the count of such invoices as NOT VERIFIED at merge, because it needs real data.
- 7.6 "No invoices/payments to export" is evaluated after the filter, so a demo-only dataset shows the empty toast. Demo invoices are not read by any exporter (they are filtered out first). For information only: `DINV-0001` uses a third line shape (`price`/`cost`/`sku` keys, `index.html:5630`); `DINV-0002` to `0005` use the real keys plus a stray `sku`.
- 7.6a **No line rows to export.** If, after the filter, a line-level format (Generic CSV, Xero or QuickBooks) would produce zero data rows (for example only credit notes, or only invoices with no lines), `doAcctExport()` does not download a header-only file: it shows the toast "No invoice lines to export (see warnings)" and does nothing else. JSON still downloads whenever the filtered set is non-empty.
- 7.7 **Warnings panel.** The demo and credit-note exclusion lives in `acctExportSets()` (demo) and inside `acctQualityCheck` (credit-note skip); `acctQualityCheck` is called by `openAcctExport()` and `acctExpEntityChanged()` over the REQ-7.1 filtered sets with its existing invoice-level rules (missing Incoterm, missing Payment Terms, zero-value line, no payments recorded) plus the REQ-7.5 warning, skipping REQ-7.4 records, with its existing `invId`-only payment match. For Entity = Invoices the panel shows these warnings; for Entity = Payments the panel is empty (there are no payment-level rules today and none are added).

**REQ-RPT-003-8 (COGS parity).** No new production function is added for this. **Tests:** a test-local helper in `tests/run.js` calls `acctInvCSV([inv])`, parses the output as CSV (strip the BOM, honour quoted fields; `parseImportCSV` may be reused) and sums the `COGS` column. Each fixture invoice is classified in this order: (1) REQ-7.4 record: skipped; (2) no lines per the REQ-3 line-source rule: **no-line** (REQ-7.5); (3) lines came from the legacy `lines` array: **legacy-shape**, not parity-tested; (4) stored-COGS exception per REQ-5.3: **stored-COGS**, not parity-tested; (5) otherwise **parity-tested**: `abs(sum - cInv(inv).cogs) <= 0.005 * n + 1e-9` where `n` is the number of line rows the invoice exports (`lineItems.length`), and the test FAILS on any mismatch. For fixtures in classes 2-4 the test asserts the class itself and the expected export outcome. A separate fixture where `calc_cogs` differs from the live figure asserts that `iCalc(inv).cogs` (which prefers `calc_cogs` on a truthiness test, `index.html:5594`-`5600`) and `cInv(inv).cogs` differ by more than the same tolerance, documenting why the displayed figure can differ from the export. **Real data (read-only, operator-run, POST-DEPLOY, NOT a merge gate):** real-data parity cannot be checked before the fix ships, because on the pre-fix build `acctInvCSV` returns header-only output for real-shape invoices. It is therefore a follow-up step: after the fix is deployed to the operator's production profile, the operator may run, in that profile's browser console, a recipe composed only of the new `acctExportSets()` (for the non-demo invoice set) and existing functions (`cInv`, `iCalc`, `acctInvCSV`, `parseImportCSV`, `DB.li`) that prints per invoice: its REQ-8 class (1-5), the exported line-COGS sum, `cInv().cogs`, `iCalc().cogs`, and the count of **cost-drift lines**. **Cost drift (the ACCT-GAP-004 trigger) is defined as:** a `lineItems` line (any `lineType`, since `cInv()` applies the catalogue cost to any resolving `lid`) whose `lid` resolves in `DB.li` and whose stored `unitCost` satisfies `typeof === 'number' && isFinite` (so `undefined`, `null` and numeric strings do not count), and whose catalogue `cost` is also such a number, that differs from the catalogue cost by more than 0.005, compared on the raw unrounded values. The recipe's text is delivered in a follow-up message after deployment, not in the merge-time delivery report and not in any repo file; it contains no data, and it prints only ordinal indexes, class numbers and numeric values (no invoice numbers, buyer names or descriptions), because its output is pasted into an AI session. The session cannot see the operator's console, so the operator pastes or relays the output into the session. **Until that happens, the merge-time delivery report states real-data parity, drift and the no-line invoice count as NOT VERIFIED (pending post-deploy run), ACCT-GAP-004 is created at merge in `docs/known-gaps.md` and the tracker with status Open-undetermined (aggregate wording only), and merge does not wait on it. The merge-time delivery report tells the operator to ask for the recipe after deploying (that request is the follow-up trigger). The relayed aggregate result is then recorded by a docs-only follow-up commit/PR to `docs/known-gaps.md` and the tracker, with no version bump, closing ACCT-GAP-004 as not-found or updating it with the aggregate drift count.** Once relayed, the result is recorded only as aggregate counts in `docs/known-gaps.md` (ACCT-GAP-004 opened or closed as not-found). **Disclosure channel:** "delivery report" (as defined here, used from REQ-7.5 onward) means this session's final delivery message to the operator at merge time, and "follow-up message" means any later session message to the operator. It is never committed, never placed in a PR body, issue or comment, and never written to a file in the repo (SEC-GAP-020). Anything that goes into the repo or a PR (the in-app changelog block, the release note, tracker rows, PR description, `docs/known-gaps.md`, `docs/version-history.md`, `CLAUDE.md`, `STACKD_CONTEXT.md`) contains only aggregate counts, never invoice numbers, buyer names or amounts, and every `tests/run.js` fixture is synthetic.
