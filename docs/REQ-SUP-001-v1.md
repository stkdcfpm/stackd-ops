# REQ-SUP-001-v1: Supplier Price Intelligence Retention & Reference View

## Business Context

Raised directly against an already-tracked strategic risk: `R-007` in `STACKD_CONTEXT.md` — "Supplier intelligence empty database" — whose current mitigation (`FM-3`, "manual data entry after every transaction") only captures supplier data *after* a deal closes. Every declined quote, every supplier a buyer was compared against but didn't choose, is discarded today with no mechanism to retain it.

The immediate trigger was a conversation about `REQ-QTE-001` Part B (RFQ supplier comparison — requirements-gated, not yet spec'd or built): the operator noted that RFQ comparison data is inherently pre-sales, and much of it is "thrown away" when a deal doesn't close — but asked whether it should instead be retained as market intelligence to build out the supplier network. **This REQ answers that question, and is deliberately scoped separately from Part B's comparison UI**, for a reason worth stating plainly: the app already holds substantial supplier pricing history *today*, independent of whether Part B is ever built — `DB.li[].priceHistory[]` (line-item cost/price versions), `DB.qt[].lines[].priceHistory[]` (per-quote-line cost/duty/margin versions, extended per-line by `REQ-QTE-001` Part A), and `DB.po[]` records (actual committed purchase costs). None of this is currently surfaced as supplier intelligence — it sits siloed inside individual Quote/Line Item/PO records, viewable only one record at a time.

**Scope decision (deliberate, stated up front):** this REQ is scoped as a **reference/reporting capability over data the app already retains**, not a new persistence mechanism. It does not depend on `REQ-QTE-001` Part B shipping. If/when Part B ships, its `rfqResponses[]` (including non-committed, non-converted responses — exactly the "pre-sales, would otherwise be thrown away" data the operator flagged) becomes one additional feed into the same view, not a separate system.

## GDPR Assessment

Favorable. All source data (Line Item cost/price, Quote line pricing, PO costs, and — once built — RFQ response terms) is commercial data about a supplier relationship, not personal data about a natural person. This REQ aggregates and displays only: supplier identity (`DB.sup.id`/`name`), product/spec description, price, currency, date, and source record type. It does not introduce, surface, or aggregate any Contact-level PII (name/email/phone) — a supplier's price history is shown attributed to the *Supplier* record, not to whichever individual happened to be the contact on a given deal. This sidesteps the "right to erasure" pressure personal-data retention would carry; the only retention question is commercial-data proportionality (see Open Questions).

## FM-1 Assessment

No new `K`/`DB` entity, no new field on any existing entity, no new Sheets sync mapping. This is a **pure read/aggregation view** computed on demand from `DB.li`, `DB.qt`, `DB.po` (and, once it exists, `DB.ord[].lines[].rfqResponses[]`) — the same category as the existing Aging Report / P&L Report (`REQ-RPT-001` G-02/G-03), which introduced no new persisted entity either. Falls under FM-1 category-1 (UI/reporting feature, no new localStorage entity). No council decision required.

**One narrow exception, flagged explicitly rather than assumed:** if/when `REQ-QTE-001` Part B ships, its own REQ (`REQ-QTE-001-v3`, REQ-QTE-001n) already commits `rfqResponses[]` to being local-only. This REQ does not change that commitment or reopen it — it only reads whatever Part B already persists. If Part B's own volume of non-converted responses turns out to need a retention cap (see Open Question 2), that cap is Part B's responsibility to define in its own spec, not this REQ's.

## Requirements

**REQ-SUP-001a (aggregation, read-only):** A new function collects every historical price point for a given Supplier across three existing sources — `DB.li[].priceHistory[]` entries where `li.supId` matches, `DB.qt[].lines[]` entries where `line.supId` matches (using each line's `priceHistory[]`), and `DB.po[]` records where `po.supId` matches — into one chronological list per supplier: `{ date, sourceType ('line_item'|'quote'|'po'), sourceRef (record num/id), product/desc, price, currency, status (e.g. quote's status, PO's status) }`. Purely computed at render time — nothing new is written to `DB`.

**REQ-SUP-001b (Supplier view integration):** The existing Supplier detail/summary panel (`openSup()`) gains a "Price History" section listing REQ-SUP-001a's aggregated result for that supplier, most recent first, with source-type badges (Line Item / Quote / PO) so the operator can see *why* a price point exists, not just the number.

**REQ-SUP-001c (staleness signal, mandatory — not optional):** Every displayed price point shows its age (e.g. "8 months ago") and any entry older than a configurable threshold (default 12 months, stored alongside other operator-configurable thresholds in `QR`/Settings, not hardcoded) is visually flagged as stale (matching the existing amber-warning visual language used elsewhere, e.g. `renderDispCurWarn()`'s staleness banner). This is a direct, deliberate response to the risk raised in this REQ's own review: presenting old pricing as current intelligence without an age signal would be actively misleading, not merely incomplete.

**REQ-SUP-001d (cross-supplier product view, secondary):** A second view, accessible from the same Price History section, lets the operator search/filter by product description or SKU across *all* suppliers' historical price points — not just one supplier at a time. This is the part that most directly serves "which supplier is actually best for this product," reusing REQ-SUP-001a's aggregation but grouped by product instead of by supplier.

**REQ-SUP-001e (RFQ integration point, forward-compatible only — not built here):** If `REQ-QTE-001` Part B ships in the future, its `rfqResponses[]` (including responses never committed/converted) becomes a fourth `sourceType` fed into REQ-SUP-001a's aggregation, explicitly including non-converted responses — this is the mechanism that actually answers the operator's original question (retaining "thrown away" pre-sales comparison data as intelligence). This REQ does not build that integration now (Part B doesn't exist yet); it specifies the aggregation function's shape (REQ-SUP-001a) so adding a fourth source later is a contained, additive change, not a redesign.

**REQ-SUP-001f (no export/sync of aggregated intelligence):** The aggregated view is for in-app reference only in this REQ's scope — no CSV export, no Sheets sync of the aggregated data. Existing per-record CSV exports (Line Items, Quotes, POs) already contain the underlying data; this REQ doesn't duplicate that via a new export path. If a "supplier intelligence export" is wanted later, that's a separate, explicitly-scoped REQ.

## Open Questions for Requirements-Gate / Spec-Gate

1. **Threshold defaults.** REQ-SUP-001c proposes a 12-month staleness threshold — confirm this matches how FPM actually re-quotes with suppliers (some categories, e.g. commodity pricing, may go stale much faster than 12 months; others, e.g. capital equipment, may not).
2. **Volume, once Part B exists.** REQ-SUP-001a's aggregation is a live computation over existing DB arrays — fine at current record counts. If Part B ships and generates many non-converted RFQ responses per Order Request line (the scenario that motivated this REQ), the aggregation's performance and `DB.ord`'s own storage growth become Part B's concern (per the FM-1 Assessment above), but this REQ's aggregation function should be written defensively (e.g., capped/paginated rendering) rather than assuming small N indefinitely.
3. **Multi-tenant data ownership (flagged, not resolved here).** If v3.0.0 goes multi-tenant, aggregated supplier pricing across unrelated tenants becomes a genuine data asset — and a genuine ownership question (is a supplier's price history *that tenant's* data, or does it become a shared/anonymized cross-tenant intelligence layer, which is closer to what `R-006`'s "prioritise data moat over feature moat" is actually gesturing at). Explicitly out of scope for this REQ, which is single-tenant/single-operator only, matching the app's current architecture — but worth a deliberate product decision before v3.0.0, not a default.
4. **"Best supplier" beyond price.** REQ-SUP-001d surfaces price comparison across suppliers for a product, but "best" isn't purely lowest price (lead time, reliability, cert status all matter, per the original RFQ conversation). This REQ intentionally stays price/history-only — blending in reliability signals is `REQ-RPT-001 G-09`'s territory (supplier performance tracking, still deferred to v3.0.x), not this REQ's.
