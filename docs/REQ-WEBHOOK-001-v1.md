## 0. How this REQ came to be scoped this way

Earlier this session, two deferred workstreams were named by the operator: "webhooks/automations for the shipment/invoice workflow" and "Contacts-setup-via-Excel." The operator chose to sequence in-app automation first (shipped as `REQ/SPEC-SHIP-001`, v2.9.86 — auto-created Shipment on Invoice Paid) and explicitly deferred *outbound* webhooks to a separate future REQ, because this app's no-server architecture means an outbound webhook fired from the browser has no delivery guarantee (see §0.1). This REQ is that deferred piece.

The concrete ask, given directly by the operator after a scoping exchange:

> "when a[n] [invoice] is marked approved [i.e. the existing 'Mark Buyer Approved' action on a Pro-forma invoice] should trigger an email to the buyer. also when this happens we should automate a workflow to email the invoice to the buyer." … "one [email], I want to build this [so it] can easily be replicated for other triggers in Make.com" … "email with pdf attached"

Two corrections surfaced during scoping, both confirmed against live code before writing this REQ, not assumed:
- The operator initially said "Purchase Order marked Approved." Purchase Orders have no such status (`index.html:2448` — the fixed set is `Draft/Sent/Deposit Paid/Settled/Cancelled`) and no buyer relationship at all (POs are FPM→Supplier; buyers only relate to Invoices via `Invoice.buyerId`). The operator confirmed the real trigger is the existing Invoice-level "Mark Buyer Approved" action (`saveInvApprove()`, `index.html:8539`), which fires only while an Invoice is at `Pro-forma` status.
- "Email the invoice" was confirmed to mean one email containing a PDF attachment of the invoice document, not two separate emails and not just structured data with no visual document.

Priority, as stated directly by the operator: this REQ is priority #1 of the three now-open post-`REQ-SHIP-001` items (this REQ, an "external agent with live platform data access" idea, and Contacts-via-Excel, in that order — the middle item unranked but not deprioritized, Contacts-via-Excel explicitly ranked last).

### 0.1 What was actually researched (with sources)

Before assuming Supabase (already in this app's stack for Cloud Data) could solve outbound-webhook reliability server-side, this was checked directly rather than answered from training-data recall:

- Supabase **Database Webhooks** fire an HTTP request via the `pg_net` Postgres extension when a table row changes — this runs inside Supabase's own infrastructure, not a browser tab, so it would survive a closed tab or an operator not being logged in. [Database Webhooks | Supabase Features](https://supabase.com/features/database-webhooks)
- However, **`pg_net` does not automatically retry a failed delivery** — this is a confirmed, still-open gap, not an assumption: [Webhook Retries · supabase Discussion #17664](https://github.com/orgs/supabase/discussions/17664), [Add retries · Issue #110 · supabase/pg_net](https://github.com/supabase/pg_net/issues/110). A retry would require a hand-built `pg_cron` job polling `net._http_response`, and that table only retains failure records for 6 hours. [pg_net: Async Networking | Supabase Docs](https://supabase.com/docs/guides/database/extensions/pg_net)

Decision made from this research (§1.2 Decision 7): **do not route this trigger through a Supabase Database Webhook in v1.** `saveInvApprove()` is a deliberate, low-frequency, interactively-clicked operator action (not a high-volume or externally-driven table change), so the browser-side fire-and-forget pattern this codebase already uses for `sendFwdReq()` is simpler, requires no new Postgres/Edge Function infrastructure, and has an equivalent (not worse) reliability profile for this specific trigger — "does the operator's own browser tab survive the few seconds after they click Mark Buyer Approved" is a materially different (and better) reliability question than "does an unattended background event guarantee delivery," and this trigger is always the former. A genuinely unattended, high-reliability-requirement trigger in the future (e.g., a nightly batch process) would warrant re-litigating this via Database Webhooks; this one does not.

## 1. Business context

### 1.1 What exists today (check-first)

All confirmed directly against live `index.html` before writing this REQ:

- **`sendFwdReq()`** (`index.html:13390`) — the only existing "send something to an external party" mechanism in this codebase. A single hardcoded webhook URL (`SS.fwdWebhook`, one Settings field, `saveFwdWebhook()` at `index.html:13406`), used only by the Shipment-forwarder "request an update" action. Payload is `{shipmentRef, message, ts}` — no PII, no financial data. Fire-and-forget: `await fetch(...)` wrapped in try/catch, a toast on success/failure, no retry. This is the direct precedent this REQ extends into a generic, multi-rule mechanism.
- **`saveInvApprove()`** (`index.html:8539`) — records `buyerApprovedAt`/`buyerApprovedBy`/`approvalMethod`/`approvalNote` on an Invoice when the operator confirms the buyer approved a Pro-forma invoice out-of-band (email/WhatsApp/WeChat/phone — never inside the app, per `REQ/SPEC-INTEG-001` Phase 2). It deliberately sends nothing today. This is this REQ's chosen trigger point.
- **No PDF generation anywhere in this codebase.** `prevInvDoc()` (`index.html:10011`) builds a complete HTML document as one local `var html` string, then wraps it in a `Blob`, opens it via `URL.createObjectURL()` in a new browser tab/window, and relies on the operator's own browser Print dialog (`window.print()`) to produce a PDF. There is no `jsPDF`/`html2canvas`/any binary-PDF library, consistent with `CLAUDE.md`'s "no CDN, no dependencies" policy (one deliberate, narrow exception: `vendor/supabase-js-v2.min.js`).
- **No email-sending capability anywhere in this codebase.** No SMTP, no transactional email API integration, no `mailto:`.
- **Buyer entity** (`DB.buy`, `REQ-BUY-001`) has an `email` field (`b.email`). `Invoice.buyerId` links to it. **`BUY-ADHOC`** (`index.html:9377`) is a real, live sentinel Buyer record — `{id:'BUY-ADHOC', email:'', ...}` — used as the fallback whenever an Invoice's `buyerId` is blank or unmatched (`BUY-GAP-002`, confirmed still-open). A meaningful fraction of real invoices in this app can resolve to a buyer with **no email address at all**.
- **`SEC-GAP-024`** already discloses `sendFwdReq()`'s arbitrary-webhook-target risk as an open, low-priority item — but that disclosure covers a payload with no PII and no financial data. This REQ's payload is categorically more sensitive (buyer name, email, invoice amounts) and needs its own explicit disclosure, not silent inheritance of the existing one (§1.3).
- **`SHIP-GAP-001`** (disclosed, not fixed, from `REQ-SHIP-001`) already establishes the precedent in this codebase for naming an async double-submit race as an accepted, disclosed limitation rather than something every new feature must re-solve. This REQ inherits the same disclosed limitation for the "Mark Buyer Approved" button's own submit path (§4).

### 1.2 Design decisions

**Decision 1 — a generic rule mechanism, not a second hardcoded webhook.** The operator explicitly asked for something "easily replicated for other triggers in Make.com." Cloning `sendFwdReq()`'s single-hardcoded-URL pattern a second time would not satisfy that — every future trigger would need its own new Settings field, its own new toggle function, and its own copy-pasted fetch call. Instead:
- `SS.webhookRules[]` — an array of `{id, trigger, url, enabled, createdAt}` records, stored the same way every other `SS.*` setting already is (`sv(K.ss, SS)`).
- A fixed, code-level `WEBHOOK_TRIGGERS` registry — `[{key, label}]` pairs. v1 ships exactly one entry: `{key:'inv_buyer_approved', label:'Invoice: Buyer Approved'}`. A future trigger (e.g. a Shipment status change) is added by (a) one new registry entry and (b) one `fireWebhookRules(key, payload)` call at the relevant existing save-function's call site — no schema change, no new Settings field, no new UI beyond the rule-creation dropdown automatically gaining the new option.
- Settings UI: a new "Automation Webhooks" list (in the existing Integrations card, alongside the pre-existing forwarder-webhook field and the Shipment auto-create toggle) — add/edit/delete rules; each rule picks its trigger from a `<select>` built from `WEBHOOK_TRIGGERS`, has a URL field (`https://` enforced, mirroring `saveFwdWebhook()`'s existing guard exactly), and an enabled checkbox.
- More than one enabled rule can target the same trigger key (e.g. testing two Make.com scenarios in parallel, or one production + one staging). Dispatch fires every matching enabled rule independently — one rule's failure must never suppress or abort another's (`Promise.allSettled` semantics, not a chain that stops at the first rejection).

**Decision 2 — payload carries data + rendered HTML, not an app-generated PDF.** This app has no PDF library and will not gain one for this feature (§1.1). `prevInvDoc()`'s existing HTML-building logic is refactored into a standalone, side-effect-free function — `buildInvDocHtml(inv)` — reusing the same HTML-building logic `prevInvDoc()` already runs internally; `prevInvDoc()` itself becomes a thin wrapper that calls it and then does its existing Blob/window-open behavior, so its own visible behavior is unchanged (a byte-identical-output regression test is required, not assumed — see AC). The webhook payload for `inv_buyer_approved` includes the resulting HTML (as `invoiceHtml`), so Make.com's own HTML-to-PDF/email module builds the attached PDF — this app never generates a PDF binary itself.

**Erratum (spec-gate round 2, extended round 4) — `buildInvDocHtml(inv)` returns an object, not a bare string.** Independent spec-gate review (round 2) found that a bare-string return would leave `saveInvApprove()` needing to independently compute `balanceDue` for the JSON payload, and the obvious independent computation (`cInv(inv).bal`) is not the same figure `invoiceHtml`'s own printed balance shows whenever a Credit Note is applied (`cInv().bal` subtracts CN deductions; `prevInvDoc()`'s own internal balance deliberately does not — CN deductions appear on the CN's own document, `index.html:10026`'s own comment). The fix, independently verified correct: `buildInvDocHtml(inv)` returns `{ html, grand, bal }` — reusing the exact same local `grand`/`bal` values the HTML body already computes, so the JSON payload and the printed document can never independently drift. This REQ's original text (this Decision, REQ-WEBHOOK-001d, the payload-shape snippet, and AC-10) was never updated to match at the time — a round-4 spec-gate review caught the same "SPEC redesign not reconciled into REQ text" pattern that produced AC-14's round-3 erratum, recurring a second time. Corrected here and at REQ-WEBHOOK-001d/the payload shape/AC-10 below, per the identical reasoning as that erratum: the SPEC's design is independently verified correct, so the REQ's stale text is what's fixed, not the working implementation.

**Correction from requirements-gate round 1 (finding 1):** `prevInvDoc()`'s first two body lines — `window._lastInv = inv; window._lastPO = null;` (`index.html:10012-10013`) — are **not** part of the HTML-building logic; they are load-bearing UX state consumed by the global `Ctrl+P`/`printDoc()` handler (`index.html:14610-14613`), which re-opens whichever document was last previewed. `buildInvDocHtml(inv)` must extract **only** the HTML-string-building body, starting after these two lines, and must never touch `window._lastInv`/`window._lastPO` — a webhook-triggered call must not silently hijack the operator's "reprint last document" shortcut to point at an invoice they never opened a preview of. `prevInvDoc(inv)` keeps the `window._lastInv`/`window._lastPO` assignments itself, then calls `buildInvDocHtml(inv)` for the string, then does its existing Blob/window-open behavior.

**Decision 3 — do not fire if there is no real buyer email.** If `inv.buyerId` is blank, equals `'BUY-ADHOC'`, or resolves to a `DB.buy` record whose `email` is blank, `fireWebhookRules('inv_buyer_approved', ...)` must not be called at all, and the operator sees a toast explaining why (mirroring `sendFwdReq()`'s existing "No webhook URL configured" toast pattern) — not a payload sent to Make.com with an empty recipient that fails silently three systems downstream.

**Decision 4 — fire-and-forget, no retry queue, in v1; must never block the approval record itself.** Same disclosed architecture constraint as `sendFwdReq()`/`SHIP-GAP-001`: if the browser tab closes moments after the click, or Make.com is briefly unreachable, that one delivery is lost with no retry. Out of scope for v1, named explicitly (§4) rather than silently downgraded. Corollary requirement: the webhook's own success/failure must never be allowed to roll back or block the approval record — the approval is written regardless of whether the notification succeeds.

**Correction (erratum 3, spec-gate round 5, finding of the identical "SPEC redesign not reconciled into REQ text" pattern as errata 1/2 — see §9h) — the ordering guarantee this Decision originally claimed does not hold.** The original text asserted the webhook fires "only after `saveInvApprove()`'s own persistence... has already succeeded." This is not achievable given `persistInvChange()`'s real contract (`index.html:6350-6388`, unchanged by this REQ): it returns silently — no throw, no return value — both when `ensureSbAuth()` is cancelled (`index.html:6352`) and when the Supabase `.update()` itself errors (`index.html:6386`, only a `console.warn`). `saveInvApprove()` has no success signal to check even if it wanted to. Spec-gate round 2 found this and disclosed it as `INV-GAP-005` (SPEC §8) rather than fixing it — correctly, since `persistInvChange()` is shared by 12+ call sites none of which check its success either, and giving it a real success/failure contract is separate, larger work outside this REQ's scope — but that disclosure was never propagated back into this Decision's own wording, which kept promising a guarantee the shipped design doesn't provide. Corrected: the webhook fires after `saveInvApprove()`'s persistence *call completes* (awaited, not raced), not after persistence is *verified* to have succeeded — for a Cloud Data operator hitting a cancelled login or a transient Supabase error at that exact moment, the webhook can fire (and the buyer be emailed) for an approval that was never actually written to the shared record. This is a real, disclosed, not-fixed limitation (§4), not a design this REQ endorses as correct — it is accepted for the same reason `INV-GAP-005` itself was accepted.

**Decision 5 (REVISED, requirements-gate round 1 finding 6) — new GDPR/security disclosure required, not inherited from `SEC-GAP-024`, and broader than the original draft stated.** This is the first outbound-webhook mechanism in this codebase carrying real personal data (buyer name, email) and financial data (invoice amounts, line items) to an operator-configured, arbitrary external URL — categorically more sensitive than `sendFwdReq()`'s shipment-ref-plus-free-text payload. The original v1 draft's disclosure named only buyer data and invoice financials; independent review found it missed a materially more serious item: `invoiceHtml` (part of the payload defined in REQ-WEBHOOK-001e) is produced by `buildInvDocHtml()`, which embeds `AS.bank` — **FPM's own company bank account details** (`index.html:10027`, `10143`, the same field shown in the "Payment Details" section of every invoice document) — into the rendered HTML. Every `inv_buyer_approved` webhook payload therefore carries FPM's own bank details to a third-party URL the operator configured, not just the buyer's data. This is arguably the more serious exposure of the two (payment-redirection-fraud-relevant data leaving the app's control), and the original disclosure's silence on it was a real gap, not a stylistic omission.

Requirements (revised):
- The rule-creation UI must show an explicit, inline notice naming **all** of what leaves the app for this trigger: buyer name and email, invoice financial data, and FPM's own bank account details (via the embedded `invoiceHtml`) — not just the first two.
- **Notice timing, clarified**: a one-time gate at rule-creation is not sufficient on its own, given this codebase's own existing precedent — `sendFwdReq()`'s GDPR disclosure (`index.html:766`, the persistent `<p>` note in the Forwarder Webhook card: "When a webhook URL is configured, shipment data...is posted to that endpoint...") is a **persistent, always-visible** note in the Settings → Integrations card, not a one-time creation-time modal. This REQ's disclosure must match that precedent: shown at creation time (so a rule cannot be added without it being seen) **and** persisted as a visible note next to the rule list for as long as any `inv_buyer_approved` rule exists, so an operator revisiting Settings weeks later is still reminded what that rule transmits, not just told once and never again.
- A new, explicit `SEC-GAP-025` entry is logged in `docs/known-gaps.md` at ship time (§1.3), not silently folded into the existing `SEC-GAP-024` entry, and its text must name the `AS.bank` exposure explicitly, not just buyer PII.

**Decision 6 (REVISED, requirements-gate round 1 finding 4 — original claim refuted) — fire only on a genuine unapproved→approved transition, not on every successful `saveInvApprove()` call.** The original v1 draft claimed every call to `saveInvApprove()` represents a new approval event. This is false: `invApprovalActionVisible(inv)` (`index.html:3169-3171`) gates the "Mark Buyer Approved" button on `inv.status === 'Pro-forma'` alone — it does **not** check `!inv.buyerApprovedAt` — so the button stays visible and clickable on an *already-approved* Pro-forma invoice. `openInvApprove()` (`index.html:8527-8536`) confirms this is a deliberate, supported UX: it pre-fills the form from the invoice's *existing* `approvalMethod`/`buyerApprovedBy`/`approvalNote`, clearly designed to let an operator correct a typo or amend a note on an approval that already happened, not exclusively to record a brand-new one. Under the original Decision 6, that correction click would silently re-fire the webhook and send the buyer a second, spurious copy of the invoice email.

Fix: capture whether the invoice was already approved **before** `saveInvApprove()`'s own mutation, and fire the webhook only on a genuine falsy→truthy transition of `buyerApprovedAt`:
```js
var wasApproved = !!inv.buyerApprovedAt;
inv.buyerApprovedAt = new Date().toISOString();
// ...persist...
if (!wasApproved) { /* resolve buyer, build payload, fireWebhookRules(...) */ }
```
This correctly fires on: a first-ever approval, and a re-approval after Phase 2's auto-clear-on-line-edit (which nulls `buyerApprovedAt`, making the next approval a genuine falsy→truthy transition again — AC-11 already covers this case). It correctly does **not** fire on: a same-invoice correction to the approver name/method/note while `buyerApprovedAt` was already truthy going in. This needs no new persistent field (unlike `REQ-SHIP-001`'s `autoCreatedFromInvIds[]`) — the pre-mutation read of the existing record's own field is sufficient, because `fireWebhookRules('inv_buyer_approved', ...)` can only ever be reached through `saveInvApprove()`, and `saveInvApprove()` has exactly one caller in the entire codebase: the "Mark Buyer Approved" button's `onclick` (`index.html:1254`, confirmed by an exhaustive `grep` for every call site).

**Correction from requirements-gate round 3 (finding B) — the reasoning above replaces an earlier, factually inaccurate claim.** An earlier draft of this Decision asserted `buyerApprovedAt` is "never touched by any path other than this one function and the preserve-only Cloud Data refresh." That characterization of the refresh path was wrong: `refreshInvFromSupabase()` (`index.html:6238-6297`) is **not** preserve-only — it wholesale-replaces `DB.inv` from Supabase's canonical row data (`buyerApprovedAt: row.buyer_approved_at || ''`), and runs automatically and frequently (including at the end of every ordinary `saveInv()` once Cloud Data is migrated, `index.html:8508`, plus 12 other call sites (13 live calls total across the file, confirmed by direct grep, excluding the function's own definition and two comment-only mentions)). Concretely, a device syncing a pre-existing already-approved invoice for the first time genuinely can see its local `buyerApprovedAt` flip from empty to a real timestamp via this path — "never set from empty" was false. The full-JSON-backup restore path (`index.html:12981`, entity list including `inv`) likewise wholesale-replaces `DB.inv`, also unenumerated in the earlier draft. Neither of these facts changes the actual conclusion, because — as stated above — the webhook can only fire through `saveInvApprove()` itself, and neither `refreshInvFromSupabase()` nor the backup restore ever calls it. But the *reason* Decision 6 is safe is "no bypass path calls `saveInvApprove()`," not "the bypass paths preserve the field" — the latter was an unverified assumption that happened not to matter, not a true supporting fact, and is corrected here rather than left standing.

**Decision 8 (new, requirements-gate round 2 finding) — the JSON payload's `buyer` object is minimized to `{id, name, email}`; `contactName`/`phone` are deliberately excluded.** Round 2 review found the original payload shape (REQ-WEBHOOK-001e) included `buyer.contactName`/`buyer.phone` — real fields on `DB.buy` (`index.html:9377`) — without either field appearing in any of this REQ's disclosure surfaces (Decision 5, §1.3, `SEC-GAP-025`, AC-14), a direct contradiction of §1.3's own stated bar that the disclosure must name "everything that leaves the app." Rather than widen every disclosure surface for two fields this trigger doesn't actually need — the workflow is "send one email to the buyer's email address," which needs only a name for the greeting and the email address itself, not a separate human contact name or phone number — the payload itself is minimized instead. This also narrows `SEC-GAP-025`'s own exposure surface, which is the better outcome when the choice is available at no functional cost. Note this does **not** eliminate all buyer-address-shaped PII from the transmission: `invoiceHtml` (Decision 2) still renders `inv.buyerAddr`/`inv.shipTo` (`index.html:10110-10112`), because an invoice document without a billing address is not a real invoice — that exposure is inherent to sending the actual invoice document by design, disclosed as part of category (2) in REQ-WEBHOOK-001b's revised notice text, not omitted.

**Decision 7 — browser-side fire, not a Supabase Database Webhook, for this trigger specifically.** See §0.1's research. Explicitly scoped to this trigger's own low-frequency, interactively-clicked nature — not a general policy against ever using Database Webhooks for a future trigger.

**Correction from requirements-gate round 1 (finding 5) — a real multi-device limitation, disclosed here rather than silently claimed away.** `SS.webhookRules` is confirmed local-only: `SS.*` is never included in the real `pullAll()` (`index.html:4950`, entity keys `['inv','cn','po']` plus a `_simpleEntsForBatch` list of `['sup','li','payments','sh','qt','co']`) or `pushAll()` (`index.html:5163`, `['sup','li','po','sh','qt','payments','co']`) sync entity lists, and is never migrated to or refreshed from Supabase anywhere in the Cloud Data layer — Settings, including any webhook rule, live in one browser's `localStorage` only, even when Cloud Data is fully configured and the underlying Invoice is shared across every device. Two consequences follow, both accepted as v1 limitations rather than solved (§4), because solving either properly means moving rule storage and trigger evaluation server-side — the exact Database Webhook redesign Decision 7 explicitly chose not to take on for this trigger:
- **Silent miss**: if the rule is configured on Device A's browser but a colleague on Device B is the one who actually clicks "Mark Buyer Approved" on the same Cloud-Data-shared invoice, the webhook never fires, with no error visible to anyone — the operator who set up the rule has no way to know it didn't run.
- **Cross-device double-fire**: if the same rule is independently configured on two different operators' browsers (a plausible first instinct — "let both of us have it wired up"), and Decision 6's fix (fire only on the local falsy→truthy transition) is evaluated independently by each browser against its own last-loaded copy of the record, two devices could each perceive a falsy→truthy transition for what is, from Make.com's perspective, the same logical approval — there is no cross-device deduplication in v1.

Both are named explicitly in §4 as accepted, disclosed limitations of the local-only rule-storage design — not fixed in v1, and not something an operator would discover except by noticing a missing or duplicate email.

### 1.3 GDPR / security note

`docs/known-gaps.md` gains a new entry, `SEC-GAP-025`, at ship time: an operator who creates an `inv_buyer_approved` webhook rule is configuring this app to transmit, to a third-party URL of the operator's own choosing (typically a Make.com scenario webhook), over HTTPS but with no further guarantee: (a) a named buyer's name and email address (deliberately minimized to just these two fields — Decision 8 — even though `DB.buy` also carries `contactName`/`phone`), (b) the full rendered invoice document via `invoiceHtml`, which necessarily carries this invoice's financial detail (amounts, line items) and the buyer's own name/billing address exactly as printed on the invoice, and (c) **FPM's own company bank account details**, also embedded in that same `invoiceHtml` field via `AS.bank` (`index.html:10027`) — the same data shown in the "Payment Details" section of every invoice document. There is no data processing agreement tracking, no confirmation the receiving endpoint is itself GDPR-compliant, and no way for this app to know or control what that endpoint does with the data afterward. This is opt-in only (a rule must be deliberately created; none exist by default), disclosed to the operator at rule-creation time and via a persistent note in the rule list thereafter, per Decision 5. This mirrors the acceptance basis already established for `SEC-GAP-002` (Sheets sync PII) and `SEC-GAP-024` (the narrower `sendFwdReq()` case) — accepted as a known, disclosed trade-off of this app's no-server architecture, not treated as a blocking defect, on the strength of that disclosure actually naming everything that leaves the app.

## 2. Requirements

### REQ-WEBHOOK-001a — `SS.webhookRules[]` schema + `WEBHOOK_TRIGGERS` registry
A new `SS.webhookRules` array, each entry `{id, trigger, url, enabled, createdAt}`. A new top-level `WEBHOOK_TRIGGERS` constant array of `{key, label}`, v1 containing exactly one entry: `{key:'inv_buyer_approved', label:'Invoice: Buyer Approved'}`.

### REQ-WEBHOOK-001b — Settings UI: Automation Webhooks rule list
New section in the existing Settings → Integrations card. Lists existing rules (trigger label, URL, enabled state, delete button). An "Add Rule" control: trigger `<select>` built from `WEBHOOK_TRIGGERS`, URL `<input>`, enabled checkbox. URL must start with `https://` (same guard as `saveFwdWebhook()`) or the save is rejected with a toast. Before a rule targeting `inv_buyer_approved` can be saved, an inline, un-skippable notice must be shown naming **all three** categories of data the rule will transmit: (1) buyer name and email (Decision 8 deliberately excludes contact name/phone from the JSON payload — see below); (2) the full rendered invoice document via `invoiceHtml` — financial detail, line items, and the buyer's own name/address exactly as shown on the invoice itself; and (3) FPM's own company bank account details, also embedded via `AS.bank` inside that same `invoiceHtml` (Decision 5). While any `inv_buyer_approved` rule exists, this same notice content must also render as a persistent, always-visible note next to the rule list — not shown only once at creation — matching `sendFwdReq()`'s existing persistent-disclosure precedent (`index.html:766`).

### REQ-WEBHOOK-001c — `fireWebhookRules(triggerKey, payload)` shared dispatch function
Looks up every `SS.webhookRules` entry where `trigger === triggerKey && enabled`. For each match, fires an independent `fetch(rule.url, {method:'POST', headers:{'Content-Type':'application/json'}, body: JSON.stringify(payload)})`, awaited via `Promise.allSettled` (never a chain that aborts remaining rules on one failure). **A matching rule counts toward the `failed` count in two distinct cases, both of which must be handled explicitly, not conflated: (a) the `fetch()` promise itself rejects (a network-level failure — DNS, connection refused, CORS), and (b) the `fetch()` promise fulfills but the resolved `Response`'s `.ok` is `false` (an HTTP error status such as 404 or 500) — a fulfilled promise with an error status must never be counted as `sent` just because the request completed.** Returns a summary (`{sent, failed}` counts). Must be callable with zero matching rules (a no-op, not an error) — a trigger existing in the registry with no rule configured for it yet is the normal, expected v1 state for every operator who hasn't set one up.

**Toast timing, clarified (requirements-gate round 1 finding 8 — the original draft left this ambiguous and self-contradictory):** the caller (`saveInvApprove()`) must **not** `await` `fireWebhookRules()` before showing its own existing "Buyer approval recorded" toast — that toast fires immediately, unchanged from today's behavior, regardless of webhook outcome. `fireWebhookRules()` itself is called without blocking the calling function's own completion (fire-and-forget from the caller's perspective, matching Decision 4's "must never block" requirement literally, not just in spirit); when its returned promise eventually resolves, a **second, separate** toast reports the `{sent, failed}` summary. A slow or unreachable Make.com URL therefore delays only that second toast, never the approval-recorded confirmation or any other UI interaction.

### REQ-WEBHOOK-001d — `buildInvDocHtml(inv)` extraction from `prevInvDoc()`
`prevInvDoc()`'s HTML-string-building body — `index.html:10014`–`10148` at time of writing, i.e. **everything after** the function signature at `10011` and the `window._lastInv`/`window._lastPO` assignments at `10012-10013` (explicitly excluded per Decision 2 — those two lines stay in `prevInvDoc()` itself) — is extracted into a standalone `buildInvDocHtml(inv)` function, with no DOM/window side effects, **returning `{ html, grand, bal }`** (Decision 2's erratum above) rather than a bare string. `prevInvDoc(inv)` itself becomes: keep its own `window._lastInv`/`window._lastPO` assignments, then `var built = buildInvDocHtml(inv);`, then its existing unchanged Blob/`window.open()` behavior using `built.html`. `prevInvDoc()`'s own externally-visible behavior (the opened tab's content, and its `window._lastInv`/`window._lastPO` side effect) must be unchanged before and after this refactor — an explicit regression test is required (§3, AC-10/AC-10b/AC-10c), not assumed from the mechanical nature of the change.

### REQ-WEBHOOK-001e — `saveInvApprove()` wiring
Before mutating `inv.buyerApprovedAt`, capture `var wasApproved = !!inv.buyerApprovedAt;` (Decision 6). After `saveInvApprove()`'s own persistence call (`await persistInvChange(inv, false)` on Cloud Data, or `sv(K.i, DB.inv)` locally) has *completed* — not necessarily *succeeded*, per Decision 4's erratum — and its existing "Buyer approval recorded" toast has fired unchanged, proceed only if `!wasApproved` (i.e. this call was a genuine unapproved→approved transition, not a correction to an already-approved record). If so, resolve the Invoice's buyer via the same `buyerId`-then-`BUY-ADHOC`-fallback logic already used elsewhere in this codebase (Decision 3's precondition). If a usable buyer email is found, build the payload (§ payload shape below) and call `fireWebhookRules('inv_buyer_approved', payload)` without awaiting it before returning (REQ-WEBHOOK-001c's toast-timing rule). If no usable buyer email is found, skip the call and toast an explicit reason (Decision 3) — a second, additional toast, never replacing the approval-recorded one. If `wasApproved` was already true, skip the webhook path entirely and silently — no additional toast, since a correction to an already-approved invoice is not an error condition.

**Payload shape:**
```json
{
  "trigger": "inv_buyer_approved",
  "invoice": { "id", "num", "status", "cur", "date", "grandTotal", "balanceDue", "buyerApprovedAt", "buyerApprovedBy", "approvalMethod", "approvalNote" },
  "buyer": { "id", "name", "email" },
  "lineItems": [ { "desc", "uom", "qty", "up", "lineTotal" }, ... ],  // lineTotal is pre-tax (qty×up); invoiceHtml's own rendered per-line total is tax-inclusive — deliberate, not a drift bug (spec-gate round 8)
  "invoiceHtml": "<buildInvDocHtml(inv).html — grandTotal/balanceDue above are buildInvDocHtml(inv).grand/.bal, the exact same values, never independently recomputed>",
  "ts": "<ISO timestamp>"
}
```

## 4. Explicitly out of scope for v1

- **No retry queue or delivery guarantee** beyond a single fire-and-forget `fetch()` attempt (Decision 4). A local pending-queue-with-retry-on-next-load is a possible future v2, named here, not built.
- **No PDF generation inside this app** (Decision 2) — Make.com's own HTML-to-PDF/email tooling is the intended consumer of `invoiceHtml`.
- **No trigger other than `inv_buyer_approved` ships in v1.** The registry pattern (REQ-WEBHOOK-001a) is designed to make a future trigger cheap to add, but none besides this one is built now — resist the temptation to "just add one more while we're in here."
- **No Supabase Database Webhook path** for this trigger (Decision 7) — a possible future re-evaluation for a different, genuinely unattended/high-volume trigger, not built here.
- **No double-submit / duplicate-click protection on the "Mark Buyer Approved" button itself.** This inherits the same disclosed, pre-existing async-race class as `SHIP-GAP-001` — a rapid double-click could theoretically fire the webhook twice for one logical approval. Disclosed, not fixed, consistent with the `REQ-SHIP-001` precedent for this exact risk class.
- **The webhook can fire for an approval that was never actually persisted, on a Cloud Data operator hitting a cancelled login or a transient Supabase error at the moment of approval (Decision 4 erratum, §9h; `INV-GAP-005`).** `persistInvChange()` has no success/failure signal for its caller to check, and giving the shared function one is separate, larger work outside this REQ's scope (12+ call sites, none of which check it either). Disclosed, not fixed — the buyer may receive an email confirming an approval that silently reverted on next reload for every other device sharing that invoice.
- **`SS.webhookRules` is local-only, with two real, disclosed multi-device consequences (Decision 7, requirements-gate round 1 finding 5) — not fixed in v1:**
  - **Silent miss**: a rule configured on one operator's browser never fires when a *different* operator, on a different device, clicks "Mark Buyer Approved" on the same Cloud-Data-shared invoice — with no error surfaced anywhere.
  - **Cross-device double-fire**: the same rule independently configured on two operators' browsers can each independently perceive the local unapproved→approved transition and both fire, since there is no cross-device deduplication.
  - Properly solving either requires moving rule storage and trigger evaluation server-side (a Supabase Database Webhook redesign) — an explicit, named future option, not built here.
- **The full-JSON-backup restore path** (`index.html:12986`, `if (data.settings) { SS = data.settings; sv(K.ss, SS); }`) wholesale-replaces `SS` — including `webhookRules` — from whatever backup file is loaded. Restoring an old backup can silently resurrect a since-deleted rule (reactivating a defunct third-party URL as a live PII-transmitting rule) or silently remove a rule that existed only on the device being restored onto. This is pre-existing restore behavior this REQ does not change, but is named here explicitly given the GDPR-sensitivity of what a resurrected rule would transmit; not fixed in v1.
- **No non-`saveInvApprove()` path can ever set `buyerApprovedAt` from empty or independently trigger the webhook** — confirmed directly against all four other mechanisms that touch this field, none of which call `saveInvApprove()` (and per Decision 6/§9c, that single fact is what actually makes this safe, not any claim about what each path preserves):
  - `saveInv()`'s own ordinary interactive edit-save (`index.html:8277-8282`) explicitly carries the existing record's `buyerApprovedAt`/`buyerApprovedBy`/`approvalMethod`/`approvalNote` forward unchanged.
  - CSV import, `processImport()` (`index.html:10824`), preserves the same four fields from the pre-existing record on a re-import.
  - "Import from Sheets," `processImportRecords()` (`index.html:11164`, called only from `importFromSheets()`/`importAllFromSheets()` — a one-time manual snapshot importer, distinct from the continuous `pullAll()` sync), preserves the same four fields identically.
  - The continuous Sheets sync, `pullAll()` (`index.html:4950`, Invoice merge at `4986-4997`), never even reads a `buyerApprovedAt` value from the pulled Sheet row in the first place: `unmapRec('inv', r)` only ever populates keys listed in `FIELD_MAPS.inv` (`index.html:4828`), which does not include `buyerApprovedAt` — so `mergePulledWithLocal()`'s `Object.assign({}, localMatch, pulledMapped)` (`index.html:4877`) always keeps the local value untouched, structurally, not by any explicit preserve-logic in this path.

**Correction from requirements-gate round 5 (finding, not caught in rounds 1-4) — the original bullet mislabeled its own citations.** It attributed `index.html:11164` to `pullAll()` under the heading "Sheets `pullAll()`," but that line is inside `processImportRecords()`/"Import from Sheets" — a different, one-time-snapshot mechanism from the continuous `pullAll()` sync this document correctly cites elsewhere (Decision 7, `index.html:4950`). It also silently folded `saveInv()`'s own edit-preserve path (`8277-8282`) into a bullet titled only "CSV import and Sheets," never naming it. The underlying safety conclusion was still true in every case, independently re-verified here — but the citations didn't establish it under their claimed names, which is exactly the class of error this document's own review history (§9-§9d) exists to catch and not repeat.
- **Editing an already-configured rule's URL does not retroactively resend any past payload.** Obvious, but stated for the record.
