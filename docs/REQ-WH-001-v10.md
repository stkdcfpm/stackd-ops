### 1.2 Design decisions (resolved with the operator before drafting further)

**Decision 1 (operator-selected) — The "goods ready" and "collected" dates live on `Shipment`, as two new fields, not on Order Request and not as a new standalone entity.** Shipment already models the pre-departure lifecycle (`etd`/`eta`, container type, docs status) and is where an operator tracking a container awaiting pickup would already be looking.

**Decision 2 (operator-selected) — EXW detection stays scoped to `Invoice.incoterm`; no incoterm field is added to Shipment or Order Request in this REQ.** Accepted limitation, with a specific asymmetry the operator should weigh: a Shipment auto-created from an already-Paid invoice (`autoCreateShipmentFromInvoice()`) has its EXW-ness resolvable immediately, since the triggering Invoice is linked by construction — but a Shipment an operator tracks *manually, before any Invoice is raised* (goods sitting in the seller's warehouse, not yet invoiced) gets no readout at all until an Invoice eventually appears with `incoterm:'EXW'`. That second case — storage accruing before invoicing — is plausibly the more common real-world trigger for wanting this estimate in the first place, and this REQ does not cover it until an Invoice exists. Revisit if it proves to matter in practice (§4).

**Decision 3 (operator-selected) — The rate model is a user-editable per-day rate plus a per-day-per-CBM rate, both added to `QR`/`QR_DEFAULTS`, not a new entity.** Mirrors how `lclPerCBM`/`fcl20GP`/etc. are already modeled — two numbers, not a multi-row table (unlike REQ-CONTAINER-001's `DB.containerProfiles`, which genuinely needed multiple rows).

**Decision 4 (operator-selected) — The calculated cost is a computed, never-persisted, on-screen estimate only; nothing is auto-written into any Invoice charge field.** The Shipment edit view shows a live-computed "Estimated Storage Cost" readout whenever the conditions in §2 WH-001c are met; the operator transcribes it into Invoice's existing free-form "Other Charges" field (`if-oth`, `index.html:1230`) by hand, if desired. No change to `vInv()`/`cInv()`/any Invoice totals logic.

### 1.3 What this REQ deliberately does NOT do

- Does not add an `incoterm` field to `Shipment` or `Order Request` (Decision 2) — EXW detection is Invoice-only, with the timing limitation that implies.
- Does not auto-write the computed estimate into any Invoice field (Decision 4) — it is a read-only, recomputed-on-render display, never a saved value, specifically so it never goes stale relative to "today" while a Shipment sits uncollected.
- Does not improve `Shipment.linkedInvs[]`'s own data integrity — this REQ consumes it exactly as it exists today (loose `num`-string array, per Gap 4), and does not duplicate or pre-empt REQ-SHIP-002's own, separate, not-yet-built fix for that relationship.
- Does not build a standalone "Storage Calculator" tool analogous to the Load Calculator — the estimate is computed and shown directly on the one Shipment record it concerns, since (unlike the Load Calculator's ad-hoc multi-invoice container-sizing problem) there is no cross-Shipment aggregation need here.
- Does not handle multi-currency storage rates beyond `QR`'s own existing `displayCurrency` convention — the new rate constants are plain numbers in whatever currency the operator's other `QR` rates are already in.
- Does not track a history/ledger of storage-cost estimates over time — only the current, live-computed figure is ever shown; nothing is logged.
- Does not change `DB.ord`'s `Processing`/`Fulfilled` stage semantics or add any date field there (Decision 1).
- Does not extend the AI assistant's `create_shipment` action (`handleAIAction()`, `index.html:12297-12304`) to set `goodsReadyDate`/`collectedDate` — that entry point pre-fills only `shf-ref`/`shf-op`/`shf-dp`/`shf-etd`/`shf-eta`/`shf-nt` today, and this REQ leaves it untouched; an operator using that path sets the two new fields by hand afterward, same as any other field the AI action doesn't cover.

### WH-001c — Shipment edit view: computed, live "Estimated Storage Cost" readout
Shown only when **both** of the following hold for the Shipment being viewed/edited:
1. `goodsReadyDate` is set.
2. At least one entry in `linkedInvs[]`, **deduplicated first** (see below), resolves to a real Invoice with `incoterm === 'EXW'`.

**Resolution step, run once before computing anything:** take `linkedInvs[]`, resolve each string via `DB.inv.find(function(inv){ return inv.num === numStr; })` (per Gap 4), discard entries that don't resolve (AC-10) or that resolve to a non-EXW Invoice (AC-9), then **deduplicate the remainder by resolved Invoice `id`** (not by the raw string) before summing CBM — this both handles an accidental duplicate/typo'd entry in `linkedInvs[]` itself (e.g. the same num pasted twice into the comma-separated `shf-invs` field) and is a deliberate, disclosed simplification for the separate case where two *different* Invoice records happen to share the same `num` (uniqueness is a save-time UI gate only — `vInv()`/`vBlurInvNum()`, `index.html:10632-10641` — not a structural guarantee; `findDuplicateInvNums()`, `index.html:6599`, exists precisely because duplicates can reach `DB.inv` via import/restore paths that bypass that gate): `.find()`'s first-match-in-array-order result is accepted as-is, consistent with how this app already treats that same risk class elsewhere (REQ-CONTAINER-001 §4's disclosed restore-path gaps).

When shown, computed fresh on every render (never persisted, never a saved field on `DB.sh` itself), using the resolved-and-deduplicated EXW Invoice set from above:
- `days = Math.max(0, Math.ceil((Date.parse(collectedDate || today()) - Date.parse(goodsReadyDate)) / 86400000))`, where `today()` is this codebase's own existing helper (`index.html:3073`: `() => new Date().toISOString().slice(0,10)`) — used here rather than `exportAgingCSV()`'s separate local-midnight idiom (`new Date(); setHours(0,0,0,0)`, `index.html:9337-9338`) because `today()` is the far more widely-used convention across the app and this REQ's inputs (`goodsReadyDate`/`collectedDate`) are themselves plain `YYYY-MM-DD` strings with no time component, matching `today()`'s own string shape exactly; `collectedDate` if set, else `today()`'s result, so the estimate keeps climbing for a Shipment still sitting uncollected.
- `totalCBM` = sum of `parseFloat((inv.cbm||'').replace(/[^\d.]/g,'')) || 0` (the exact existing parsing pattern, §1.1) across the resolved-and-deduplicated EXW Invoice set above — **not** across every linked Invoice regardless of incoterm, since only EXW cargo plausibly sits in the seller's own warehouse this way. **Disclosed simplification:** a Shipment with both EXW and non-EXW linked Invoices shows one blended figure covering only the EXW-side CBM; this REQ does not attempt to model whether EXW and non-EXW cargo on the same Shipment are physically co-stored or separately warehoused — if that distinction matters operationally, it is a candidate for a future REQ, not this one (§4).
- `estimatedCost = days * QR.storagePerDay + days * totalCBM * QR.storagePerCBMPerDay`.
- Displayed as a labeled, read-only line (e.g. "Estimated Storage Cost: $NNN.NN (N days × M.MM CBM)"), recomputed into the DOM on every render — reusing the same `innerHTML`-assignment *display mechanic* as the Load Calculator's `#lc-result` (`index.html:2628`, written via `.innerHTML` inside `runLoadCalc()`, `index.html:13470`) for how a plain-text computed line gets rendered into a target element; **not** an analogy for *when* it recomputes — `#lc-result` is actually click-triggered only (populated solely inside `runLoadCalc()`, cleared back to `''` every time `openLoadCalc()` opens the modal, `index.html:13429`), the opposite of this readout's own "always recomputed, every render" requirement, which has no existing precedent elsewhere in this app and is simply a direct consequence of this bullet's own normative text above, not something borrowed from the Load Calculator. Not the Quote form's `placeholder`-attribute ghost-text pattern either (a different, editable-input-hint mechanism, not an appropriate analogy for a standalone non-editable readout line).
- **Insertion point:** the readout is computed and its `innerHTML` set from inside `editShp()` (`index.html:13280`-adjacent, the function that renders the Shipment edit view with the record's current data) — not `openShp()` (new-Shipment path, where the conditions in bullet 1-2 above can never be met since there are no `linkedInvs[]` yet) and not `saveShp()` (write path, uninvolved in display). The target element is a new, empty `<div>` placed in the `ov-shp` modal's HTML immediately after the new `shf-ready`/`shf-collected` fields (`index.html:2579-2580`-adjacent, per WH-001a), given an id such as `shf-storage-cost`, left empty (`''`) by default so it renders nothing when the two display conditions aren't met.
