# REQ-WH-001 — Warehousing/storage cost estimate for ExWorks shipments

**Status:** v4 — round 3 independent review of v3 returned CONDITIONAL PASS with 0 blocking and 1 new advisory finding (A6), personally re-verified against live `index.html` and fixed here: v3's claim of "matching the precedent completely" was itself incomplete — the real `etd`/`eta` pattern in `vShp()` is four statements, not two: a format-validity pre-check that `return vErr(...)` on failure, each immediately followed by a `vOk(...)` call that clears the field's error state once it passes (`index.html:10726-10730`; same convention elsewhere, e.g. `vInv()`'s `index.html:10691-10694`). v3's `goodsReadyDate`/`collectedDate` checks specified the two `vErr`-returning guard clauses but omitted the two matching `vOk()` calls. Now added, with AC-2 extended accordingly. Round 3 also did a full fresh adversarial pass over the rest of the document (Cloud/Sheets touchpoint consistency, WH-001c's resolve-then-dedup ordering, AC-8's test-technique concreteness, a "fourth instance" hunt for the B1/A5/A6 defect pattern elsewhere in the doc) and found nothing else. See §9c for the round-3 findings log; §9b/§9 (rounds 2/1) are preserved unchanged below it.
**Type:** New fields on an existing Cloud-Data-synced entity (`DB.sh`) + new rate constants on an existing local-only settings object (`QR`) + a computed, never-persisted cost readout. **Unlike REQ-CONTAINER-001, this REQ does require a Supabase schema migration** — two new columns on the `shipments` table — because `DB.sh` is Cloud-Data-synced (REQ/SPEC-CLOUD-007) and `QR` is not.

## 1. Business context

### 1.1 What exists today (check-first)

- **Gap 1 — no warehousing/storage-cost concept exists anywhere.** Confirmed by a full-file, case-insensitive search for "warehous"/"storage" (as a business concept, not the unrelated browser-`localStorage`-quota "Storage Health" dashboard card and `checkStorageQuota()`, `index.html:258-263`) and "ExWorks"/"EXW" — no entity, field, rate constant, or calculator touches this today.
- **Gap 2 — no "goods ready for collection" or "collected" date exists on any entity.** `Shipment` (`DB.sh`) has `etd`/`eta` (`index.html:2579-2580`) — shipping-side dates, not warehousing ones. `Order Request` (`DB.ord`) has a `Processing → Fulfilled` stage transition (`ORD_TRANSITIONS`, `index.html:3228-3237`) — the closest existing *concept* to "goods ready," but no date field anywhere records when that transition happened or when goods were actually collected. `Invoice` has no comparable date field either.
- **Gap 3 — `incoterm` only exists on Invoice.** Confirmed absent from `DB.qt`/`DB.sh`/`DB.ord` schemas. `Invoice.incoterm` (`index.html:1192`, populated from `RD_INCOTERMS`, `index.html:4584-4598`) is a required field (`index.html:10584,10691-10692`) with `EXW` (`{code:'EXW',name:'Ex Works',...}`, `index.html:4585`) as a real, existing option.
- **Gap 4 — the only Shipment↔Invoice relationship is `Shipment.linkedInvs[]`, an array of free-text Invoice **`num`** strings, not ids — the same loose, unvalidated reference REQ-SHIP-002 (clean PASS, not yet implemented) already diagnosed and designed a fix for.** Confirmed by direct read: `saveShp()` (`index.html:13301-13326`) builds `linkedInvs` by splitting a comma-separated text field (`shf-invs`, `index.html:13304-13305`), and the demo seed stores Invoice *numbers* there (`index.html:5512`: `linkedInvs: ['DINV-0001']`), not ids. **This REQ must be built against this current, unvalidated shape — resolving an EXW-flagged invoice for a given Shipment means `DB.inv.find(function(inv){ return inv.num === numStr; })` for each string in `linkedInvs`, with no guarantee any given string actually resolves.** If REQ-SHIP-002 ships first, this REQ's own resolution logic should be revisited to use its hardened `linkedInvIds[]` instead — out of this REQ's own scope to anticipate.
- **Gap 5 — `Shipment` is Cloud-Data-synced (REQ/SPEC-CLOUD-007), with FIVE distinct touchpoints that must all be extended for any new field** — four for Supabase Cloud Data, plus one for the separate, independently-active Google Sheets sync, the same risk class REQ-SHIP-002 itself flagged (its own "4 Cloud Data touchpoints including the easily-missed `shRow` object inside `autoCreateShipmentFromInvoice()`") — expanded here to five after round-1 review found the fifth. Confirmed by direct read, all five:
  1. `saveShp()`'s own `shRow` object (`index.html:13358-13366`).
  2. The one-time Cloud-Data-migration push loop that inserts every existing local Shipment on first migration (`index.html:7463-7470`-adjacent).
  3. `autoCreateShipmentFromInvoice()`'s own `shRow` object, built when a Shipment is auto-created from a Paid invoice (`index.html:8947-8953`).
  4. `refreshShFromSupabase()`'s pull-side row→object mapping (`index.html:6298-6312`).
  5. **`FIELD_MAPS.sh` (`index.html:4914`) — the Google Sheets field map, not a cosmetic display label map.** `mapRec()`/`unmapRec()` (`index.html:4918-4948`) iterate `Object.keys(FIELD_MAPS.sh)` generically, so any key added to this object is automatically wired into the live Sheets push (`saveShp()`'s unconditional `await syncEnt('sh', shp)`, `index.html:13387`) and delete (`delEnt('sh', _shRef)`, `index.html:13404`), and into the generic Sheets pull loop (`pullAll()`, `index.html:5167`). **Consequence that must be disclosed alongside the Supabase migration (§2 WH-001a): adding `goodsReadyDate`/`collectedDate` to `FIELD_MAPS.sh` causes a new column to appear in the operator's linked Google Sheet the moment this ships — an external-system change, exactly like the Supabase migration, just to a different external system.** Unlike the four Supabase touchpoints, this one is "free" in the sense that no separate code change is needed beyond the one `FIELD_MAPS.sh` edit already planned in WH-001a — the risk here is not missing the wiring, it's failing to disclose its side effect.
  Missing any of the first four would silently drop the new fields on exactly one of: save, first-migration, auto-creation, or pull-refresh — the same failure class REQ-SHIP-002's own §1.1 named explicitly for this same function family. Missing the fifth's *disclosure* (not its wiring, which happens automatically) would surprise an operator with an unannounced new Sheet column.
- **Precedent for a small, user-editable rate-constants object: `QR`/`QR_DEFAULTS`, already fully wired for exactly this purpose.** `QR_DEFAULTS` (`index.html:4359`) is a flat object of editable shipping-rate constants (`fxGBPUSD`, `lclPerCBM`, `fcl20GP`, `fcl40HQ`, `originCharges`, `dgSurcharge`, `fpmAdmin`, etc.); `QR` (`index.html:4360`) is the live, localStorage-backed instance (`Object.assign({}, QR_DEFAULTS, ld('st_qr') || {})`), already round-tripped by three existing functions: `qteFillRates()` (`index.html:14776-14782`, populates the Settings form from `QR`), `ratesFromForm()` (`index.html:14784-14790`, reads the form back into a plain object), and `saveRates()` (`index.html:14792-14794`-adjacent, `Object.assign(QR, QR_DEFAULTS, ratesFromForm())` then persists). The new `shf-ready`/`shf-collected` inputs need their own entries in this same rules map for live feedback, in addition to (1)'s save-blocking check — both are required, neither substitutes for the other.
- **`inv.cbm` parsing precedent to reuse exactly.** Free-text field (e.g. "18 CBM"), parsed everywhere via `parseFloat((inv.cbm||'').replace(/[^\d.]/g,'')) || 0` (`index.html:13444`, already cited by REQ-CONTAINER-001 for the identical reason).

### 1.2 Design decisions (resolved with the operator before drafting further)

**Decision 1 (operator-selected) — The "goods ready" and "collected" dates live on `Shipment`, as two new fields, not on Order Request and not as a new standalone entity.** Shipment already models the pre-departure lifecycle (`etd`/`eta`, container type, docs status) and is where an operator tracking a container awaiting pickup would already be looking.

**Decision 2 (operator-selected) — EXW detection stays scoped to `Invoice.incoterm`; no incoterm field is added to Shipment or Order Request in this REQ.** Accepted limitation, with a specific asymmetry the operator should weigh: a Shipment auto-created from an already-Paid invoice (`autoCreateShipmentFromInvoice()`) has its EXW-ness resolvable immediately, since the triggering Invoice is linked by construction — but a Shipment an operator tracks *manually, before any Invoice is raised* (goods sitting in the seller's warehouse, not yet invoiced) gets no readout at all until an Invoice eventually appears with `incoterm:'EXW'`. That second case — storage accruing before invoicing — is plausibly the more common real-world trigger for wanting this estimate in the first place, and this REQ does not cover it until an Invoice exists. Revisit if it proves to matter in practice (§4).

**Decision 3 (operator-selected) — The rate model is a user-editable per-day rate plus a per-day-per-CBM rate, both added to `QR`/`QR_DEFAULTS`, not a new entity.** Mirrors how `lclPerCBM`/`fcl20GP`/etc. are already modeled — two numbers, not a multi-row table (unlike REQ-CONTAINER-001's `DB.containerProfiles`, which genuinely needed multiple rows).

**Decision 4 (operator-selected) — The calculated cost is a computed, never-persisted, on-screen estimate only; nothing is auto-written into any Invoice charge field.** The Shipment edit view shows a live-computed "Estimated Storage Cost" readout whenever the conditions in §2 WH-001c are met; the operator transcribes it into Invoice's existing free-form "Other Charges" field (`if-oth`, `index.html:1230`) by hand, if desired. No change to `vInv()`/`cInv()`/any Invoice totals logic.

### 1.3 What this REQ deliberately does NOT do

- Does not add an `incoterm` field to `Shipment` or `Order Request` (Decision 2) — EXW detection is Invoice-only, with the timing limitation that implies.
- Does not auto-write the computed estimate into any Invoice field (Decision 4) — it is a read-only, recomputed-on-render display, never a saved value, specifically so it never goes stale relative to "today" while a Shipment sits uncollected.
- Does not improve `Shipment.linkedInvs[]`'s own data integrity — this REQ consumes it exactly as it exists today (loose `num`-string array, per Gap 4), and does not duplicate or pre-empt REQ-SHIP-002's own, separate, not-yet-built fix for that relationship.
- Does not build a standalone "Storage Calculator" tool analogous to the Load Calculator — the estimate is computed and shown directly on the one Shipment record it concerns, since (unlike the Load Calculator's ad-hoc multi-invoice container-sizing problem) there is no cross-Shipment aggregation need here.
- Does not handle multi-currency storage rates beyond `QR`'s own existing `displayCurrency` convention — the new rate constants are plain numbers in whatever currency the operator's other `QR` rates are already in.
- Does not track a history/ledger of storage-cost estimates over time — only the current, live-computed figure is ever shown; nothing is logged.
- Does not change `DB.ord`'s `Processing`/`Fulfilled` stage semantics or add any date field there (Decision 1).

### WH-001a — New `Shipment` fields: `goodsReadyDate`, `collectedDate`
Two new date fields, same `<input type="date">` shape as `etd`/`eta`. Added to:
- Shipment form HTML, immediately after the existing ETD/ETA fields (`index.html:2579-2580`-adjacent): new `shf-ready`/`shf-collected` date inputs.

- `openShp()`'s clear-on-new block (`index.html:13267`-adjacent): `if(G('shf-ready')) G('shf-ready').value=''; if(G('shf-collected')) G('shf-collected').value='';`.
- `editShp()`'s pre-fill (`index.html:13288`-adjacent): `G('shf-ready').value=s.goodsReadyDate||''; G('shf-collected').value=s.collectedDate||'';`.
- `vShp()` (`index.html:10717-10732`): add inline, early-`return`/`vOk` checks directly inside the function body, matching `etd`/`eta`'s existing FOUR-statement pattern completely (format-validity pre-check with `vErr`, THEN its matching `vOk`, THEN cross-field comparison with `vErr`, THEN its matching `vOk` — lines 10726-10730) — not just the two `vErr`-returning guard clauses alone:
  1. Format-validity pre-check + `vOk` (mirrors lines 10726-10727/10728's shape): `if (goodsReadyDate && (!RX.date.test(goodsReadyDate) || isNaN(new Date(goodsReadyDate).getTime()))) return vErr('shf-ready', 'Goods Ready Date is not a valid date'); if (goodsReadyDate) vOk('shf-ready'); if (collectedDate && (!RX.date.test(collectedDate) || isNaN(new Date(collectedDate).getTime()))) return vErr('shf-collected', 'Collected Date is not a valid date');`
  2. Cross-field "not before" check + `vOk` (mirrors lines 10729-10730's exact shape): `if (collectedDate && goodsReadyDate && new Date(collectedDate) < new Date(goodsReadyDate)) return vErr('shf-collected', 'Collected Date cannot be before Goods Ready Date (' + goodsReadyDate + ')'); if (collectedDate) vOk('shf-collected');`
  NOT a call to `vBlurDateAfter()`, which `vShp()` never uses (§1.1). The `vOk()` calls matter only in the narrow case of a Save triggered without an intervening field `blur` (e.g. Enter-to-submit) — `wireBlurValidation()`'s own onblur rules (below) already call `vOk()` on blur in ordinary mouse-driven use — but this is the same completeness this codebase's own precedent (`vShp()`'s `etd`/`eta`, and `vInv()`'s `index.html:10691-10694`) always maintains, so it is specified here rather than left as a silent gap.
- `wireBlurValidation()`'s rules map (`index.html:10593-10594`-adjacent): separately add `'shf-ready': function(){ vBlurDate('shf-ready','Goods Ready Date'); }` and `'shf-collected': function(){ vBlurDateAfter('shf-collected','shf-ready','Collected Date','Goods Ready Date'); }` for live onblur feedback — this is in addition to, not instead of, the `vShp()` inline check above.
- `FIELD_MAPS.sh` (`index.html:4914`, the Google Sheets field map, §1.1 Gap 5 item 5): `goodsReadyDate:'Goods Ready Date', collectedDate:'Collected Date'` added. **This automatically wires both fields into live Sheets push/pull via `mapRec()`/`unmapRec()` — no further code change needed for Sheets, but a new "Goods Ready Date" / "Collected Date" column will appear in the operator's linked Google Sheet as soon as this ships.** This must be disclosed to the operator as a second external-system change, alongside the Supabase migration below.
- **All four Supabase Cloud Data touchpoints from §1.1 Gap 5, not a subset:**
  1. `saveShp()`'s `shRow` (`index.html:13358-13366`): `goods_ready_date: shp.goodsReadyDate || null, collected_date: shp.collectedDate || null,` added.
  2. The one-time migration push loop (`index.html:7463-7470`-adjacent): same two keys added to that `insert()` call's row object.
  3. `autoCreateShipmentFromInvoice()`'s `shRow` (`index.html:8947-8953`): `goods_ready_date: null, collected_date: null,` added — a Shipment auto-created from a Paid invoice has neither date yet by definition.
  4. `refreshShFromSupabase()`'s pull mapping (`index.html:6298-6312`): `goodsReadyDate: row.goods_ready_date || '', collectedDate: row.collected_date || '',` added to the mapped object.
- **Supabase schema migration required:** two new nullable `date` columns, `goods_ready_date` and `collected_date`, on the `shipments` table — the one piece of this REQ that touches Postgres schema directly, and the reason this REQ's **Type** line differs from REQ-CONTAINER-001's "no Supabase migration" framing. Follows this repo's existing `supabase/migrations/NNNN_<description>.sql` naming convention (confirmed: `0001_suppliers_buyers.sql` … `0009_quotes_ins_rate.sql`); `0008_shipments_trade_docs.sql` is a directly analogous precedent (new columns added to this same `shipments` table). Exact DDL deferred to SPEC.

### WH-001b — New `QR`/`QR_DEFAULTS` rate constants: `storagePerDay`, `storagePerCBMPerDay`

### WH-001c — Shipment edit view: computed, live "Estimated Storage Cost" readout
Shown only when **both** of the following hold for the Shipment being viewed/edited:
1. `goodsReadyDate` is set.
2. At least one entry in `linkedInvs[]`, **deduplicated first** (see below), resolves to a real Invoice with `incoterm === 'EXW'`.

**Resolution step, run once before computing anything:** take `linkedInvs[]`, resolve each string via `DB.inv.find(function(inv){ return inv.num === numStr; })` (per Gap 4), discard entries that don't resolve (AC-10) or that resolve to a non-EXW Invoice (AC-9), then **deduplicate the remainder by resolved Invoice `id`** (not by the raw string) before summing CBM — this both handles an accidental duplicate/typo'd entry in `linkedInvs[]` itself (e.g. the same num pasted twice into the comma-separated `shf-invs` field) and is a deliberate, disclosed simplification for the separate case where two *different* Invoice records happen to share the same `num` (uniqueness is a save-time UI gate only — `vInv()`/`vBlurInvNum()`, `index.html:10632-10641` — not a structural guarantee; `findDuplicateInvNums()`, `index.html:6599`, exists precisely because duplicates can reach `DB.inv` via import/restore paths that bypass that gate): `.find()`'s first-match-in-array-order result is accepted as-is, consistent with how this app already treats that same risk class elsewhere (REQ-CONTAINER-001 §4's disclosed restore-path gaps).

When shown, computed fresh on every render (never persisted, never a saved field on `DB.sh` itself), using the resolved-and-deduplicated EXW Invoice set from above:
- `days = Math.max(0, Math.ceil((Date.parse(collectedDate || today()) - Date.parse(goodsReadyDate)) / 86400000))`, where `today()` is this codebase's own existing helper (`index.html:3073`: `() => new Date().toISOString().slice(0,10)`) — used here rather than `exportAgingCSV()`'s separate local-midnight idiom (`new Date(); setHours(0,0,0,0)`, `index.html:9337-9338`) because `today()` is the far more widely-used convention across the app and this REQ's inputs (`goodsReadyDate`/`collectedDate`) are themselves plain `YYYY-MM-DD` strings with no time component, matching `today()`'s own string shape exactly; `collectedDate` if set, else `today()`'s result, so the estimate keeps climbing for a Shipment still sitting uncollected.
- `totalCBM` = sum of `parseFloat((inv.cbm||'').replace(/[^\d.]/g,'')) || 0` (the exact existing parsing pattern, §1.1) across the resolved-and-deduplicated EXW Invoice set above — **not** across every linked Invoice regardless of incoterm, since only EXW cargo plausibly sits in the seller's own warehouse this way. **Disclosed simplification:** a Shipment with both EXW and non-EXW linked Invoices shows one blended figure covering only the EXW-side CBM; this REQ does not attempt to model whether EXW and non-EXW cargo on the same Shipment are physically co-stored or separately warehoused — if that distinction matters operationally, it is a candidate for a future REQ, not this one (§4).
- `estimatedCost = days * QR.storagePerDay + days * totalCBM * QR.storagePerCBMPerDay`.
- Displayed as a labeled, read-only line (e.g. "Estimated Storage Cost: $NNN.NN (N days × M.MM CBM)"), recomputed into the DOM on every render — the same pattern as the Load Calculator's own always-on, recompute-on-render result block (`#lc-result`, `index.html:2628`, populated via `.innerHTML` inside `runLoadCalc()`, `index.html:13470`), not the Quote form's `placeholder`-attribute ghost-text pattern (a different, editable-input-hint mechanism, not an appropriate analogy for a standalone non-editable readout line).

## 3. Acceptance criteria

- **AC-1:** `saveShp()` persists `goodsReadyDate`/`collectedDate` from the new form fields; `openShp()` clears them on a new Shipment; `editShp()` pre-fills them from the record being edited.
- **AC-2:** `vShp()` rejects a malformed `goodsReadyDate`/`collectedDate` (format pre-check) and rejects a `collectedDate` earlier than `goodsReadyDate` (cross-field check); each passing check clears the field's error state via `vOk()`, mirroring the existing ETD/ETA checks' full four-statement shape exactly — not just the two `vErr`-returning guard clauses alone.
- **AC-3:** With Cloud Data migration active (`_sb` set, `st_sh_cloud_migration_ts` present), saving a Shipment with both new dates round-trips them through `saveShp()`'s Cloud branch and back through `refreshShFromSupabase()` correctly.
- **AC-4:** The one-time Cloud Data migration push correctly carries forward `goodsReadyDate`/`collectedDate` for every pre-existing local Shipment that has them set.
- **AC-5:** A Shipment auto-created from a Paid EXW invoice (`autoCreateShipmentFromInvoice()`) is created with both new date fields present and null/blank, not missing entirely, whether or not Cloud Data migration is active.
- **AC-6:** `QR_DEFAULTS` includes `storagePerDay`/`storagePerCBMPerDay`; `qteFillRates()` populates the two new Settings inputs from `QR`; `ratesFromForm()`/`saveRates()` correctly read and persist operator edits to them; `expAll()`/`doImport()` round-trip them as part of `QR`'s existing wholesale export/restore, with no additional code.
- **AC-7:** The Estimated Storage Cost readout does **not** appear on a Shipment with no `goodsReadyDate` set, nor on a Shipment whose every linked Invoice (resolved via `linkedInvs[]`) is non-EXW or fails to resolve to a real Invoice at all.
- **AC-8:** The readout **does** appear, with a correct `days`/`totalCBM`/`estimatedCost` figure, for a Shipment with `goodsReadyDate` set and at least one resolved EXW-incoterm linked Invoice. Tested using this codebase's own existing fixture technique for date-dependent calculations — fixture dates built as offsets from the real `new Date()` at test time (matching `tests/run.js:6316-6334`'s aging-bucket tests), not a mocked/stubbed clock, which this codebase has no precedent for anywhere in `tests/run.js`. Covers both: `collectedDate` set to a fixture date a known N days after `goodsReadyDate` (expects `days === N` regardless of when the test runs), and `collectedDate` unset (expects `days` computed against `today()`'s real value at test time, via a `goodsReadyDate` fixture built as an offset from `new Date()` — e.g. "N days ago" — so the expected `days` is computable without mocking anything).
- **AC-9:** `totalCBM` in the readout sums only the EXW-incoterm linked Invoices' `cbm`, excluding any non-EXW linked Invoice's `cbm` from the total, even when both are linked to the same Shipment.
- **AC-10:** A `linkedInvs[]` entry that does not resolve to any real `DB.inv` record (a dangling reference, per Gap 4) is silently skipped in the EXW-resolution/CBM-summation logic, not treated as a crash or as a false EXW match.
- **AC-11:** Editing `storagePerDay`/`storagePerCBMPerDay` in Settings changes the readout's `estimatedCost` on the next render, with no stale caching.
- **AC-12 (new):** A `linkedInvs[]` array containing the same Invoice `num` string twice (operator typo/paste duplication) does not double-count that Invoice's `cbm` in `totalCBM` — the resolve-then-dedup-by-`id` step (§2 WH-001c) collapses it to one contribution.
- **AC-13 (new):** Adding `goodsReadyDate`/`collectedDate` to `FIELD_MAPS.sh` is confirmed to round-trip correctly through `mapRec()`/`unmapRec()` for Shipment's existing Sheets push/pull path (`syncEnt`/`delEnt`/`pullAll`), with no crash and no corruption of the unrelated `linkedInvs` array-join/split handling (`unmapRec()`'s existing SH-GAP-002 fix, `index.html:4939-4946`) that lives in the same function.

## 4. Explicitly out of scope for v1
